## 0. 一句话

**拓扑不用重做，缺的是领域。** `web → backend → MQ → worker → 上游` 这个形状是对的；
不合理的只有 `account.service.ts` / `new-api-billing-ops.ts` 这两块——它们不是我们的领域，是 new-api 的远程投影。

## 1. 背景

### 1.1 触发事件

new-api 独立出去，从「我们的用户系统承载者」变成「上游供应商」，只给我们一把统一 key。

这推翻了 **[ADR-0062](../adr/0062-new-api-account-center-and-quota-billing.md)：采用 new-api 账户中心与 quota 计费**——
该 ADR 明确要求「Node 不创建或维护 `users`、`user_credits`、credits ledger」「quota 是唯一余额真相」。
new-api 独立后这两条都不再成立，我们必须自建账户与账本。

### 1.2 现状（带证据）

**① 身份 100% 是 new-api 的投影**

```ts
// backend/libs/shared/types/authenticated-user.ts
export type AuthenticatedUser = {
  userId: string;       // new-api 的 id
  status: "enabled";    // 写死
  isAdmin: boolean;     // new-api role >= 10
  username: string;     // "new-api 账户用户名"
  email: string | null; // "new-api 账户邮箱，登录时快照"
};
```

登录/注册/改密全部透传 new-api（`backend/libs/shared/account/account.service.ts:38-61`）；
角色判定用 new-api 的枚举魔数（`backend/libs/infra/guard/auth.guard.ts:15-16`：`ADMIN_ROLE_THRESHOLD = 10`）。

**② 计费：预扣有值，结算恒 0，权威在 new-api**

| 环节 | 状态 | 证据 |
|---|---|---|
| 预扣 | 有估算值（IK7G9X 接入 estimator，从 new-api `/api/pricing` 拉） | `generation-command-repo.ts:271` |
| 结算 | **恒为 0，无任何生产调用点** | 全仓 grep `actualAmountFen:` 在 `persistence/` 外零命中 |
| worker-java | **明确不在范围** | `ImageJobProcessor.java:416`「修正一：不传 actualAmountFen（结算不在范围）」，同款注释散在 6 个文件 |
| 真扣费 | **new-api** | worker 用用户 `sk-` 调上游，new-api 按用户 quota 扣 |

我们自己没有权威账本，只有影子记录（`cost_reservations` / `cost_adjustments`）。

**③ 凭证（sk-）渗透面**

不只生成链路。`image-enhancements` / `image-cutouts` / `audio-trims` / `media-extract` 每一类能力服务
都有同款注释「请求方 sk- 明文冻结进 job，worker 直接取用」，落库在 `generation_jobs.provider_credential`
（`backend/prisma/schema.prisma:103`，明文）与 `user_info.provider_credential`（`:103`）。

**可以继承的锚点**（来自 `billing-units-contract.md`，继续有效）：

| 锚点 | 值 | 本设计如何处理 |
|---|---|---|
| **积分定义** | **1 元 = 15 积分**（1 积分 ≈ 0.0667 元 ≈ 6.67 分） | ⚠️ **变更**（原契约 10:1） |
| **记账单位** | **积分（整数）** | ⚠️ **变更**（原为「分」——15:1 下分不整除） |

**本设计只做人民币，无汇率、无 USD 概念。** new-api 的 quota 是它的内部记账单位，
与我们只剩两处交集：① 上游成本目录直接记人民币；② 对账时按它给的人民币账单核对总额。
运行时不参与任何 quota 换算。

## 2. 目标与非目标

### 目标

1. **一套自有用户体系**：账号、登录、会话、会员、RBAC，与 new-api 完全隔离。
2. **一套自有计费体系**：积分账户、复式账本、版本化定价、预扣/结算/返还。
3. **服务边界清晰到语言可替换**：契约用 protobuf，任何服务换语言不改契约。
4. **切换期不双重扣费**。

### 非目标

- 不做通用规则引擎（Drools / CEL / JSONata / new-api 的 `tiered_expr`）
- 不做分布式事务（Seata / 2PC）
- 不引入第三种语言（polyglot 限定 TypeScript + Java）
- 现在就分库分表（只预留分片键）
- 现在就上 APISIX / Higress（开放 API 上线时再上）

## 4. 服务划分与语言

| 服务 | 语言 | 独立理由 |
|---|---|---|
| 接入网关 | Higress / APISIX（开放 API 后）<br>nginx（现阶段，只做 TLS + 路由） | 横切能力收敛 |
| **identity-svc** | **TypeScript**（NestJS + Fastify） | 所有服务依赖它，挂了全挂 → 必须独立伸缩、独立灰度 |
| **business-api** | **TypeScript**（NestJS + Fastify） | 业务变更最频繁，团队原生 |
| **billing-svc** | **Java**（Spring Boot 3 + ZGC） | 钱的服务：无精度陷阱、复用 worker-java 的 JVM 能力、保守栈用于少变逻辑 |
| generation-worker | **Java**（已有） | 不改 |
| RocketMQ | 已有 | 不改 |

### 拆不拆的判据

**拆服务的理由是「故障域不同」或「伸缩曲线不同」，不是「听起来像微服务」。**

| 候选 | 拆？ | 理由 |
|---|---|---|
| identity-svc | ✅ | 横切依赖，故障域全局 |
| billing-svc | ✅ | 钱、强一致、写热点、财务直读、在每次生成必经路径上 |
| pricing-svc（从 billing 拆） | ❌ | **扣费依赖定价 → 故障域相同**。定价是「数据 + 纯函数」，纯函数不需要进程 |
| business-api 拆成 project/asset/generation | ❌ | 无独立伸缩曲线，拆了只把本地事务变成分布式事务 |

### ⚠️ 红线变更申请（D3 已定：Java）

**决策 D3 已定：billing-svc 用 Java。**

这需要修改红线 #10（「除 `worker-java` 外禁止新增 Java 产品运行时」）——Java 产品运行时从 **1 个变 2 个**。
这是**改决策不是改实现**，须走 ADR，且 ADR 里要一并说明新增的 `java/libs` 共享模块。

### Java 运行时的复用结构（当前不存在，需先建）

**现状**：全仓只有一个 `worker-java/pom.xml`，**没有任何共享 Java 模块**。

```
java/                          ← 新增聚合目录
├── pom.xml                    ← packaging=pom，modules: libs / worker / billing
├── libs/                      ← 新增：共享基础设施
│   ├── config/                DataSourceConfig · RocketMqConfig 范式
│   ├── gateway/               NewApiHttpSupport · NewApiErrorClassifier
│   ├── error/                 统一错误体系
│   └── mybatis/               MyBatis-Plus 用法范式 + BaseEntity
├── worker/                    ← 由 worker-java/ 迁入，改为依赖 libs
└── billing/                   ← 新增，依赖 libs
```

**⚠️ 搬迁代价（要认这笔账）**：`worker-java/` → `java/worker/` 会动到
**全部路径引用 + 火山流水线的构建配置**。这笔成本换的是长期结构对称。

> **不做的事**：不叫 `java/libs`（已否），不走「源码复制起步再收敛」——
> 复制必然分叉，既然要搬就一次到位。

### 复用的边界：复用基础设施，**不复用进程**

> **❌ 不要把 billing 做进 `worker-java` 进程。**

| | generation-worker | billing-svc |
|---|---|---|
| 定位 | **执行面**：长任务、按 job 消费 MQ、claim/fencing/recovery | **控制面**：被同步调用（Hold 50ms 预算）、强一致 |
| 数据 | 直连 generation DB | 自有 billing DB |
| 失败 | 崩溃可重启、可重投（有 recovery） | **不允许失败**，钱 |
| 发版 | 频繁 | 极少 |

**故障域完全不同**：worker 崩了不该让扣费停摆；billing 发版不该打断正在跑的视频任务。

### 复用清单（具体到文件）

| worker-java 的资产 | billing 要不要 | 处理 |
|---|---|---|
| `Dockerfile` · `docker-settings.xml` · 构建链路 | **要** | **复用** ← 真实价值 |
| `config/RocketMqConfig.java` | **要**（消费 job 事件） | 抽 `java/libs` |
| `gateway/NewApiHttpSupport.java` · `NewApiErrorClassifier.java` | **要**（对账时调 new-api） | 抽 `java/libs` |
| `infrastructure/mapper/*` 的 MyBatis-Plus 用法 | 要 | **范式约定**，不复制代码 |
| `domain/error/*` 错误体系 | 要 | 抽约定 |
| `config/DataSourceConfig.java` | 要（自有库） | 薄 boilerplate，抽或复制 |
| `domain/contract/*`（生成域契约枚举） | **不要** | billing 不该依赖生成域 |
| `application/processor/*`（执行逻辑） | **不要** | 完全无关 |

## 5. 认证方案

### 决策：认证放应用层，网关只做 TLS / 路由 / 限流

```
【现阶段】
   nginx  ── 只做 TLS 终结 + 反代 + limit_req ── 不碰认证
     │
     ▼
   business-api  ── 验签（共享 Guard，注入 X-User-Id）
     │  内网 gRPC，端口不对外
     ▼
   identity-svc · billing-svc · worker

【开放 API 上线时】
   APISIX  ── jwt-auth（零 IO 验签）+ key-auth（API Key 配额）+ limit-req
     │
     ▼
   各服务（应用层 Guard 保留作为纵深防御）
```

### 为什么不用 nginx `auth_request` 做认证

| # | 问题 |
|---|---|
| 1 | **每请求多一跳同步 RPC**——在 200ms 预算里白烧 |
| 2 | **identity-svc 变硬单点**——它挂 = 全站 401 |
| 3 | **OPTIONS 预检被拦**——CORS preflight 不带 cookie，要打补丁 |
| 4 | **WebSocket upgrade 有坑**——我们已有 realtime |
| 5 | **`X-User-Id` 是伪造面**——任何绕过 nginx 的内网路径都能伪造身份 |
| 6 | **破坏统一错误契约**——鉴权失败返回 nginx 错误页，非 [ADR-0083](../adr/0083-unified-error-codes-and-projection.md) 结构化错误 |
| 7 | **鉴权逻辑被切两半**——role/status 判断在 identity，拦截在 nginx |

**核心矛盾**：nginx 做认证的唯一收益是「少写一个 Guard」，而那个 Guard 是**共享代码**
（放 `packages/auth-guard` 或 NestJS 共享模块，装一次全服务用）。为省这点事换 7 个坑，不值。

### 具体做法

1. `packages/auth-guard`——把现有 `auth.guard.ts:35-95` 抽成共享包，各 TS 服务 `useGlobalGuards()`
2. 内网服务信任 `X-User-Id`，但靠**网络隔离**保证（gRPC 端口不对外），不靠「没人绕过 nginx」
3. Java 侧（billing-svc）一个 Spring `HandlerInterceptor` 验同一个 token
4. nginx 继续做它擅长的：TLS、路由、`limit_req`

## 6. 用户体系（identity）

### 6.1 与 new-api 的隔离边界

**new-api 从「账户中心」降级为「上游供应商」，与火山引擎同级——一个客户号，一把 key，没有用户概念。**

因此**删除**（不是改造）：

| 目标 | 规模 |
|---|---|
| `backend/libs/shared/account/account.service.ts` | 169 行，整删 |
| `backend/libs/core/new-api-billing-ops.ts` | 480 行，用户/日志/admin 部分删光 |
| `generation_jobs.provider_credential` | 概念删除 |
| `session.service.ts` 的 `sk` 字段 | 删除 |
| `auth.guard.ts:61-77` 回源复核 role/status | 删除 |
| `credential.ts` / `parseBearerToken` | 删除 |
| `user_info` 表 | 整表删除（它就是 sk- 存放表） |
| `cost-estimator.ts:48` 查 new-api `/api/pricing` | 改查本地 catalog（`billing_pricing_catalogs`） |

**唯一交集**：`bw_external_refs` 里一个 new-api 客户号，纯对账用，不参与鉴权。

### 6.2 表结构

```
bw_users                    账号主体
  id · **username(UNIQUE，登录凭据)** · password_hash · email · **phone(NULL-able)**
  · status · avatar · created_at
bw_linked_accounts          第三方绑定（一对多）
  user_id · provider(github|discord|oidc|wechat|telegram|linuxdo) · provider_uid · union_id
bw_memberships              会员
  user_id · tier(free|basic|pro|max) · started_at · expires_at · status
bw_roles                    角色
bw_user_roles               用户↔角色
bw_login_logs               登录日志
bw_verification_codes       验证码（已有 verification_codes 迁移）
bw_external_refs            外部系统映射（new-api 客户号）
```

`roles` / `user_roles` 替代 `auth.guard.ts:15` 的 `role >= 10` 魔数；
`memberships` 替代单布尔 VIP——会员等级要参与定价折扣。

#### 登录方式（**分阶段，已核实**）

| 标识 | 状态 | 说明 |
|---|---|---|
| `username` + `password` | ✅ **当前主用** | 存量用户全走这条（new-api 侧只有 username） |
| `email` + `password` | ✅ 已支持 | 与上共用入口（单一标识输入） |
| **手机号 + 验证码** | ⏸️ **后续** | 发码已通（`POST /auth/send-code`）；**登录未接**（`loginWithCode` 零调用者） |

**两条硬事实**（核实自 `blue-whale-api/model/user.go` 与 `backend/libs/core/auth/`）：

1. **new-api 的 `User` 结构体没有 `phone` 字段** → **存量用户没有手机号可迁**
2. **`username` 是登录凭据，不是手机号**

**因此**：`phone` 设计为 **NULL-able UNIQUE**，
手机号登录是**渐进增强**（绑定过的用户多一种登录方式），**不是存量迁移的前提**。
详见 [迁移 runbook §1.1](2026-09-24-迁移与切换runbook.md)。

## 7. 计费体系（billing）

### 7.1 单位口径（已定：单币种人民币，积分 15:1）

**锚点：1 元 = 15 积分**（1 积分 ≈ 0.0667 元 ≈ 6.67 分）

| 层 | 单位 | 说明 |
|---|---|---|
| 用户账本 | **积分（整数）** | 权威单位 |
| 定价目录 | **积分（整数）** | 运营按积分定价 |
| 充值 | ¥ → 积分 | 固定档位，15 积分 / 元，保证整数到账 |
| 支付边界 | 分（¥0.01） | **只在支付回调出现，不进账本** |
| 上游成本 | ¥ | new-api 给我们的账单是人民币 |

#### D1 修正：账本改用「积分」，不用「分」

原方案（账本用「分」）在 15:1 下**不再成立**：

```
1 积分 = 100 ÷ 15 = 6.666… 分   ← 不是整数
```

若账本用「分」，定价就被迫按 300 分（=3 元）的倍数走，**无法表达「1 张图 = 2 积分」**。
反过来若账本用「积分」，充值 5 元 = 75 积分、10 元 = 150 积分，**都是整数**。

**结论：账本直接用整数积分。** 15:1 的粒度（1 积分 ≈ 6.67 分）比原契约的 10:1 **更细**，
足够表达任何一次生成，**不需要小数积分、不需要辅助单位**。

> 约束：**充值档位金额必须使积分为整数**——5/10/50/100 元天然满足；
> 0.5 元 = 7.5 积分则不行。`billing_products` 保存时校验。

**只做人民币，无汇率。** 落地时删除：
- `cost_reservations.exchange_rate_version`（`backend/prisma/schema.prisma:641`）
- `billing_products` 不设任何 `exchange_rate` 字段
- `billing-units-contract.md` 的「两条换算链路」全部作废，**收敛为一条：积分 ↔ 元（15:1）**

**new-api 的 quota 不再参与我们的计价。** 它是上游内部单位，与我们只有两处交集：
① 上游成本目录 `billing_provider_cost_entries` 直接记人民币；
② 对账时按 new-api 给的人民币账单核对总额，不做 quota 换算。

### 7.2 积分批次（credit_lots）

**GeekAI 的 `vip_info_text` 写着「赠送算力当月有效」，但全库无任何有效期字段——它想做但做不到。**
批次结构是唯一解法。

```
billing_credit_lots
  user_id · source · amount · remaining · frozen · expires_at · biz_id
                      ↑ 总量      ↑ 剩余    ↑ 冻结中

  可用 = remaining - frozen

  source            来源          默认有效期
  ├─ register       注册赠送      30 天
  ├─ daily          每日登录赠送  当日 23:59:59
  ├─ invite         邀请奖励      30 天
  ├─ redeem         兑换码        按码配置
  ├─ purchased      充值本金      永久（expires_at = NULL）
  ├─ bonus          充值赠送      按套餐 credits_expire_days
  ├─ subscription   会员周期赠送  当期
  ├─ gift           运营赠送      按配置
  └─ compensation   事故补偿      按工单
```

**`bonus` 与 `purchased` 必须拆成两个批次**（见 §7.5）——有效期不同、财务口径不同、
退款时只退本金。`bonus`（充值赠送）也区别于 `gift`（运营赠送）。

- **余额**：`SUM(remaining - frozen) WHERE expires_at IS NULL OR expires_at > now()`
- **过期不需要定时任务**——`WHERE` 条件天然排除；后台只需异步补「过期确认分录」用于对账

#### 扣减顺序（严格，三级 tie-break）

1. **`expires_at ASC`** —— 先过期先扣，`NULL`（永久）排最后
2. **同 `expires_at` 时按 source 优先级**：
   `compensation > bonus > gift > daily > invite/register > redeem > subscription > purchased`
   —— **先消耗平台赠送的，后消耗用户付费的**
3. **同 source 时按 `id ASC`** —— 先获得的先扣

> 第 1 条在「赠送有期、购买永久」的场景下**自动实现「先花送的」**（赠送的先过期）。
> 第 2 条只处理有效期相同（尤其都是永久）时的退化情况——**必须显式定，不能靠默认顺序**。

#### 冻结模型（批次无损）

预扣走 `frozen`，**不直接扣 `remaining`**：

| 阶段 | 操作 |
|---|---|
| 提交预扣 | `frozen += x`（按上述顺序分配到多个批次） |
| 完成结算 | `frozen -= x`，`remaining -= actual` |
| 失败返还 | `frozen -= x`（`remaining` 不动） |

**关键：返还时原批次原封不动**——剩余量和有效期都不变。
若改用「先扣掉、返还时新建批次」，返还的积分会带上**新的有效期**，
与用户应得的权益不符（用户会凭空获得一次有效期重置）。

> **并发**：跨批次扣减是多行更新，需事务 + 行锁。
> 但同一用户的真实并发是个位数，`SELECT … FOR UPDATE` 锁该用户的 lots 完全够——
> 争用范围天然是单用户，不是全库（对比 GeekAI 的全局 `sync.Mutex`）。

### 7.3 复式账本（ledger_entries）

```
billing_ledger_entries
  id · user_id · account(wallet|revenue|cost|receivable)
  direction(debit|credit)
  biz_type · biz_id · amount
  idempotency_key UNIQUE
  balance_after              ← 逐笔可验证，对账时能定位到哪一笔算错
  remark · created_at
```

**幂等键**：`hold:{jobId}` / `settle:{jobId}` / `refund:{jobId}` / `daily:{userId}:{date}` / `redeem:{code}`

**批次是唯一权威。** 不设物化余额表——余额直接从批次聚合（见 §8 并发模型），
**一处权威，不会有不一致**。

#### 用户可见流水 ≠ 内部账本（关键设计）

**new-api 会把一次消费写成 2 条记录**：预扣一条、差额结算一条（`delta>0` 记 `LogTypeConsume`，
`delta<0` 记退款）。用户看到「扣了 40」+「退了 10」，**两次感知**。

**本设计：一个业务动作 = 用户只看到 1 条。**

```
内部（不可变，append-only）        用户可见（可变投影，一个 biz 一行）
billing_ledger_entries            billing_user_transactions
├─ hold:{jobId}      +40          ┌─────────────────────────────┐
├─ settle:{jobId}   -40 / +30     │ 视频生成 · seedance-2.5       │
└─ （refund 同理）                 │ 预扣 40 → 实际 30             │  ← 同一行
                                   │ 状态：pending → done          │
                                   └─────────────────────────────┘
```

```sql
billing_user_transactions
  id · user_id
  direction        -- in（充值/赠送/退回） | out（消费/过期）
  type             -- consume | recharge | bonus | daily | invite | redeem
                    -- | refund | expire | compensation
  biz_type · biz_id        -- job / order / code
  title                    -- 展示文案快照（「视频生成 · seedance-2.5 1080p 5s」）
  amount                   -- **最终值**（consume 记实际消耗）
  reserved_amount          -- **仅 consume**：预扣值，内部字段，**用户 API 不返回**
  status                   -- pending（处理中） | done
  catalog_version          -- 仅 consume，定价版本快照
  created_at · settled_at
  UNIQUE(user_id, type, biz_id)     ← 一个 job 只可能有一行
```

**生命周期**：

| 时机 | 用户看到（**永远一个金额**） |
|---|---|
| 提交（Hold 成功） | **新建一行** `pending`：「处理中 · 预计消耗 40 积分」 |
| 完成（Settle） | **UPDATE 同一行** `done`：「已完成 · 消耗 30 积分」 |
| 全部失败 | **UPDATE 同一行** `done`：「本次未消耗」 |
| 部分成功 | 同一行，金额 = 成功 slot 的总额 |
| 展开详情 | 规格参数 + 最终金额。**不出现「预扣」字样，不并列两个数字** |

#### 硬规则：任何用户可见界面，永远只出现一个金额

| 状态 | 显示 |
|---|---|
| `pending` | 「处理中 · 预计消耗 40 积分」 |
| `done` | 「已完成 · 消耗 30 积分」 |

数字从 40 变成 30——用户自然理解为「实际比预计少」。
**不需要、也不允许出现两个数字并列。**

| ❌ 禁止 | ✅ 允许 |
|---|---|
| 「预扣 40，实扣 30，退回 10」 | 「消耗 30 积分」 |
| 「扣费 40」+「退款 10」两条 | 一行，金额 30 |
| 「预扣」这个词出现在任何用户端 | 「处理中」/「已完成」 |

**接口层面**：用户端 API **不返回 `reserved_amount`**——那是内部字段，
只对客服/运营后台可见（用于回答「为什么我的余额变了」）。
`billing_user_transactions.reserved_amount` 保留，但**不出现在任何用户响应里**。

**两张表的分工**：

| | 内部账本 | 用户流水 |
|---|---|---|
| 可变性 | **append-only，永不改** | 可变（pending → done） |
| 粒度 | 每个借贷动作一行 | **每个业务动作一行** |
| 用途 | 财务、审计、对账 | 用户明细、客服查询 |
| 权威性 | **权威** | **投影，可随时从账本重建** |

> 因为流水表是**可从账本重建的投影**，所以它的「可变」不构成一致性问题——
> 不是一个事实存两处，而是「权威 + 缓存」的关系。重建脚本按 `biz_id` 聚合账本即可。
>
> 退款同理：**不新建一行**，只更新原行的 `amount` 与 `status`。
> 用户看不到「扣了又退」，只看到「本次未消耗」。

### 7.4 定价（版本化 JSON 目录）

**定价不是行表，是一份版本化的 JSON 文档**——定价规则要整体发布、整体回滚，行表做不到原子。
运营改价 = **改 JSON + 发布**，不发版、不改表、不重启。

```
billing_pricing_catalogs
  catalog_version · status(draft|active|retired) · document(JSON)
  schema_version · document_hash · effective_from · published_by/at
```

计费模型是 **`等效数量 × 基准单价`** 的倍率制（对齐 new-api）：
**只有一个基准价，其他维度全是「相对基准的倍率」**——调价时只改 `basePrice` 一处。
一套结构覆盖图片 / 视频 / 音频 / 文本 / 按次全部形态，**没有任何模态特殊分支**。

**折扣不在 catalog 里**，拆成两张独立 live 表（`billing_promotions` 营销活动 ·
`billing_member_discounts` 会员折扣）——它们的变更频率、生命周期、回滚粒度与基础计价完全不同。

> **完整设计**（JSON 结构 · 计算管线 · 折扣解析 · 三层校验 · 发布流程 · 生效性校验）
> 见 [计费逻辑详细设计](2026-09-24-计费逻辑详细设计.md) §2.5 与 §4.5。
> **此处不重复，避免两处漂移。**

**两个入口**：

```java
long holdCredits(PricingRequest req);   // 预扣：规格确定时精确，有不确定维度才取上界
long actualCredits(UsageReport usage);  // 结算：按实际用量 + 成功的 slot 数
```

**预扣不是无脑取上界。** 分两种情况：

| 请求 | 预扣 |
|---|---|
| 规格全确定（`duration=5` · `size=2k` · `n=1`） | **精确价** —— 差额通常为 0 |
| 存在不确定维度（智能时长 `duration=-1`） | 该维度**取模型允许的最大值** |

**为什么能和 new-api 不一样**：new-api 的 MediaKit 时长类工具入参是 URL，
提交时拿不到真实时长（`dto/channel_settings.go:26-28` 的 `MediaKitDefaultMinutes` 就是为此），
所以**它只能估算，差额是常态**。而我们的视频规格在提交时**已经确定**。

**我们的差额是例外**，只来自三处：
1. 部分成功（slot 失败）
2. 智能时长实际产出 ≠ 请求
3. 缓存命中（火山缓存计费更便宜）

> **宁可多冻结不可少冻结**——但不要**无谓地**多冻结。
> 用户可用余额被占用是真实体验损失，粗上界会让「预计消耗」永远偏高。

#### 与 new-api 的机制差异（容易混淆，单列）

| | new-api | 本设计 |
|---|---|---|
| 预扣语义 | **直接扣用户 quota**（`DecreaseUserQuota`，`service/task_billing.go:94-102`） | **冻结** `frozen += x`，`remaining` 不动 |
| 结算 | `delta = actual − pre`，正补负退，直接改 quota | `frozen -= x`；`remaining -= actual` |
| 用户账面 | 提交时**总余额**就少了，事后补回 | **可用余额**少，**总余额不变** |
| 预扣精度 | 估算 → **差额常态** | 规格精确 → **差额例外** |
| 谁算价 | 网关自己（定价在网关） | billing-svc（worker 只报用量） |

**「冻结」比「直接扣」好在哪**：能区分「用户花掉的钱」和「暂时占用的钱」——
报表准确（冻结不是收入）、退款语义清晰（解冻即退，不产生一笔新流水）。
代价是实现多一列 `frozen`、扣减要跨批次。

**发布前完整性校验**：轴空间必须全覆盖，缺一即拒绝发布。
轴空间从 `generation_model_capability.supported_sizes / supported_durations / supported_aspect_ratios`
（`backend/prisma/schema.prisma:198-200`）推导——**方向：business → billing 只读订阅**。

> **这条直接对着两个已发生的 bug 设计**：
> 「seedream 矩阵配一半」（无完整性约束）和「sizes 小写 `1k` vs matrix 大写 `1K` 导致空表」（无规范化）。
> 根因是**同一份规格语义有两个事实来源**。

### 7.5 运营能力

```
billing_products    充值套餐（扩展已有 topup_tiers）
  name · price(¥) · credits · bonus_credits · credits_expire_days
  sales · sort_num · enabled · start_time · end_time
billing_orders      订单
billing_redeems     兑换码
  user_id(nullable=通用码) · name · credits · code · enabled · redeemed_at · expire_at
billing_invite_logs 邀请奖励
  inviter_id · invitee_id · credits_awarded
billing_daily_grants 每日赠送（UNIQUE(user_id, grant_date) 幂等）
billing_api_keys    开放 API Key
  user_id · key_hash · name · enabled · last_used_at · quota_limit
```

#### 发放时点与触发（幂等键）

| source | 触发时机 | 幂等键 | 默认有效期 |
|---|---|---|---|
| `register` | 注册事务内 | `register:{userId}` | 30 天 |
| `daily` | **登录成功事件** + 每日兜底定时任务 | `daily:{userId}:{date}` | **当日 23:59:59** |
| `invite` | 被邀请人首次完成有效行为 | `invite:{inviteeId}` | 30 天 |
| `redeem` | 兑换码核销 | `redeem:{code}` | 按码配置 |
| `purchased` | 支付回调 | `order:{orderNo}` | **永久** |
| `bonus` | 支付回调（与本金同事务） | `order:{orderNo}:bonus` | 按套餐 |
| `subscription` | 订阅生效日 + 每周期首日 | `sub:{subId}:{period}` | 当期 |
| `compensation` | 运营 / 事故工单 | 运营指定 | 按工单 |

- **每日登录**：登录事件触发，`billing_daily_grants` 用 `UNIQUE(user_id, grant_date)` 兜底幂等——
  一天登录十次只发一次。事件丢失时由每日兜底任务补发。
- **连续签到加成**：登录事件带 `streak_day`（连续天数），规则可配（如第 7 天 ×2）。
  `billing_daily_grants` 记 `streak_day` 供展示与运营分析。
- **充值赠送拆两个批次**：`purchased`（本金，永久，计入收入）+ `bonus`（赠送，按套餐有效期，计入成本）。
  **退款只退本金。**

#### 积分过期机制

| 环节 | 做法 |
|---|---|
| **判定** | 纯查询条件 `expires_at IS NULL OR expires_at > now()`，**无状态** |
| **无定时删除** | 不需要扫表删过期积分——`WHERE` 天然排除。**避免锁表与量级爆炸** |
| **对账确认** | 后台异步补一条「过期确认分录」（`biz_type=expire`），纯为账本完整性 |
| **用户可见** | 明细列表按批次展示「X 积分将于 Y 日过期」；前端可做临期提醒 |
| **临期提醒** | 读 `expires_at` 在 N 天内的批次（索引 `idx_lots_user_expiry`），走站内信/邮件 |
| **过期不可逆** | 过期积分不恢复；用户投诉处理走 `compensation` 批次，**不改历史行** |

> **为什么不做定时任务删除**：定时任务会锁表、会因漏跑导致数据不一致、
> 且「已过期但还在表里」和「已删除」在业务上等价。
> 用查询条件表达过期，**永远不会有一致性问题**。
>
> 这也是 GeekAI 的反面：它的 `users.power` 是单数字，**装不下有效期**，
> 所以文案写了「赠送算力当月有效」却从未实现。

## 8. 关键路径与计费场景

```
【价格预览】高频 · 本地算 · 允许乐观
   web ─▶ business-api ─▶ 本地规则副本 ─▶ credits
                              ▲ MQ 版本失效推送

【提交生成】同步 · P99 < 200ms
   business-api ─ 1. 校验参数/素材/并发配额（本地）
                ─ 2. Hold(userId, jobId, req) ─▶ billing-svc
                │        幂等 hold:{jobId}
                │        按 expires_at ASC 扣 billing_credit_lots
                │        frozen += max，写 ledger（含 balance_after）
                │◀── {holdId, catalogVersion}
                ─ 3. 写 generation_jobs + 冻结 catalog_version（本地事务）
                ─ 4. 发 MQ：generation.submit
                ─ 5. 返回 jobId

【执行与结算】异步 · 最终一致
   worker-java ─ claim ─▶ 调 new-api(统一 key) ─▶ 写终态 + usage
                                                       │
                                     MQ: generation.job.completed / failed
                                                       ▼
                                       billing-svc ─ 幂等 settle:{jobId}
                                                     ─ 按冻结版本 × usage 算实际
                                                     ─ 多退少补 → 写账本 → 缓存失效
```

**并发模型**：

扣减要跨多个批次，**不是单行操作**——

```sql
-- 事务内：锁该用户的全部有效批次
SELECT id, remaining, frozen, expires_at, source
  FROM billing_credit_lots
 WHERE user_id = #{userId} AND (expires_at IS NULL OR expires_at > NOW())
 ORDER BY expires_at IS NULL, expires_at ASC, source_priority ASC, id ASC
   FOR UPDATE;
-- 逐批次 frozen += x，直到扣满；扣不满 → 回滚，余额不足
```

**争用范围是单用户**（同一用户并发提交是个位数，业务语义上本就该串行），
不是全库（对比 GeekAI 的全局 `sync.Mutex`，见附录 A）。

> **不设 `wallet_snapshots` 物化表。** 余额直接从批次聚合
> （`SUM(remaining - frozen)`，走 `idx_lots_user`，10 个批次以内微秒级）——
> **一处权威，不会有不一致**。展示层用 Redis 缓存 + 写时失效。

### 8.1 视频生成全流程（含扣费）

> 为什么单列一节：视频是**唯一同时具备「长耗时 + 规格决定价格 + 可能部分成功」**的任务类型，
> 扣费的分支最多。图片/音频/mediakit 都是它的简化版。

#### 阶段 0 · 价格预览（前端，本地算）

```
用户选：模型 seedance-2.5 · 分辨率 1080p · 时长 5s · 张数 1
   │
   ▼ business-api 读本地规则副本（catalog_version 由 MQ 广播失效）
   │
   ▼ maxCredits(req)  ← 取规格上界，不是实际值
   │
   └─▶ 前端显示「预计消耗 N 积分」
```

**只在有不确定维度时才取上界**：视频参数在提交时**已经确定**（分辨率/时长/张数都是用户选的），
预扣通常就是精确价。唯一的不确定维度是**智能时长**（`duration=-1`）——那时按模型最大时长预估。

（对比 new-api：它的 MediaKit 时长类工具入参是 URL，**提交时拿不到真实时长**，
只能用一个默认分钟数估算，所以差额是常态。我们的差额是例外。）

#### 阶段 1 · 提交（同步，P99 < 200ms）

```
① 参数校验（本地，无 RPC）
   ├─ 模型能力矩阵：generation_model_capabilities 是否支持该 分辨率/时长/比例
   ├─ 素材合规：引用素材是否已过审
   └─ 并发配额：该用户进行中任务数是否超限（按会员等级）

② Hold(userId, commandId, maxCredits) ──▶ billing-svc      ← 同步，50ms 超时
   │  幂等键 hold:{commandId}          ← 用客户端 commandId，不是 jobId
   │  按 §7.2 顺序跨批次 frozen += x
   │  写 billing_ledger_entries（biz_type=hold, balance_after）
   │  写 billing_user_transactions（status=pending, reserved_amount=x）← 用户可见那一条
   │  返回 { holdId, catalogVersion }
   │
   ├─ 余额不足 → 402，直接返回，**不创建任何 job**

③ 本地事务写 job
   ├─ generation_jobs（status=queued, input, 冻结 catalog_version）
   └─ generation_output_slots × N（status=pending）  ← 计费粒度是 slot

④ 发 MQ：generation.submit（带会员等级 → 优先级）

⑤ 返回 { jobId, 预计消耗 N 积分 }
```

**幂等键用 `commandId` 而非 `jobId`**：这样 Hold 可以在 job 写入之前发生。
Hold 成功但 ③ 失败 → 用户重试时 `hold:{commandId}` 幂等命中，直接重新写 job，
**不需要跨服务补偿，不需要写「先建后删」的垃圾 job**。

#### 阶段 2 · 排队与执行（worker-java）

```
claim：UPDATE generation_jobs
          SET status='processing', lease_owner=#{worker}, fencing_token=fencing_token+1
        WHERE id=#{jobId} AND status='queued' AND fencing_token=#{seen}
        ← 0 行 = 被别的 worker 抢走，放弃

调 new-api（**统一 key**，不再是用户 sk-）→ 拿 provider_task_id
轮询 / 回调，直到终态
每完成一个 slot：generation_output_slots.status = succeeded/failed + asset_id
写 generation_job_usage（原始用量：秒数 / 张数 / 分辨率 / cached_units）
置终态：succeeded | partially_succeeded | failed | cancelled
发 MQ：generation.job.completed
```

#### 阶段 3 · 结算（billing-svc 消费 MQ，异步）

```
事件：generation.job.completed { jobId, status, slots, usage }
   │
   ▼ 幂等键 settle:{jobId}
   ▼ 读 job 上冻结的 catalog_version  ← **不是当前版本**
   ▼ actualCredits(slot[] × usage)   ← 按「成功」的 slot 计费
   │
   ├─ succeeded            → 收 N 份（全部 slot 成功）
   ├─ partially_succeeded  → 收 M 份（M = succeeded 的 slot 数）
   ├─ failed               → 收 0 份，全额返还
   └─ cancelled            → provider_task_id IS NULL → 全额返还
                             provider_task_id 非空 → 上游可能已计费，按策略（见下）
   │
   ▼ frozen -= hold；remaining -= actual
   ▼ 写 billing_ledger_entries（biz_type=settle）        ← 内部账本，多条
   ▼ **UPDATE billing_user_transactions 同一行** ──────── ← 用户可见，**始终一条**
       status=done, amount=actual, settled_at=now()
   ▼ Redis 余额缓存失效
```

**按 slot 计费，不是按 job** —— 这是 `partially_succeeded` 能正确结算的前提，
也是拆镜头（fan-out）能公平收费的前提。

**`cancelled` 但已派发**：上游已经消耗了算力，不能全额退。
策略由 catalog 的 `refundPolicy` 配置：全额退 / 按比例退 / 不退，**默认按比例退**。

#### 阶段 4 · 异常与补偿路径

| 情况 | 处理 | 谁负责 |
|---|---|---|
| worker 崩溃，lease 过期 | 另一 worker 重新 claim（`fencing_token` 保护，旧 worker 写不进） | worker |
| job 卡 processing 超 `execution_deadline_at` | recovery 判 `failed` → 发 MQ → 触发 Refund | worker |
| MQ 事件丢失 / billing 当时不可用 | **billing 兜底扫描**：找 `held` 超 2h 未 settle 的预留 → 查 job 实际状态 → 补 Settle/Refund | billing |
| 结算时 job 尚未终态 | 幂等重投，等下次事件 | billing |
| `actual > hold`（理论不该发生） | 允许扣到 0，差额记 `account=receivable`，**同时告警**（说明 maxCredits 算漏了） | billing |
| 用户提交后立刻退款 | 走 Refund 幂等键，与 Settle 互斥（同一 `jobId` 只能有一个终局） | billing |

**兜底扫描是必需的**，不是可选：MQ 重投有次数上限（你们已有 18 次进 DLQ 的配置），
超限后必须有人兜底。billing 自己扫自己的表，不依赖外部。

#### 阶段 5 · fan-out（拆镜头等一对多任务）

```
父 job（type=video_scene_split）
  │  Hold(总上界 N × 单价)          ← 父 job 一次性冻结
  ├─ 子 job 1 ─┐
  ├─ 子 job 2 ─┼─ 只执行 + 写 usage，**不 Hold / 不 Settle**
  └─ 子 job N ─┘
  │
  ▼ 父 job 全部子任务终态后
  Settle(Σ 子 job 实际用量)          ← 父 job 统一结算
```

**父 job 统一 Hold、统一 Settle**，子 job 只上报用量。理由：
- 子 job 各自 Hold 会导致「部分子任务因余额不足而失败，用户拿到半个视频」——体验不可接受
- 一次冻结、一次结算，**用户看到的是「这个任务花了 N 积分」**，可解释

前端聚合展示：父 job 的 `Σ` 消耗即用户看到的数字。

#### 完整时序图

```
web ─▶ business-api ─▶ billing-svc        worker-java        new-api
 │         │                │                  │                │
 │  预览   │◀── 本地规则 ────┤                  │                │
 │◀────────┤                │                  │                │
 │         │                │                  │                │
 │  提交   │── Hold ───────▶│                  │                │
 │         │◀─ {holdId,ver} ┤                  │                │
 │         │  写 job+slots  │                  │                │
 │         │── MQ submit ─────────────────────▶│                │
 │◀─ jobId ┤                │                  │                │
 │         │                │    claim ────────┤                │
 │         │                │                  │── 统一 key ───▶│
 │         │                │                  │◀─ task_id ─────┤
 │         │                │                  │   轮询…         │
 │         │                │                  │── 终态 + usage  │

```

### 8.2 Agent / LLM 会话计费（与视频**根本不同**）

**为什么不同**：视频的价格在提交时就确定；LLM 的 token 数**提交时完全不可知**。

| | 视频 | Agent / LLM |
|---|---|---|
| 价格确定性 | 提交时**确定** | **不可知**（输出多长取决于模型） |
| 预扣 | 精确值 | 只能取粗上限，或**不预扣** |
| 产出 | 一次性（几个 slot） | **流式**，token 持续产生 |
| 结构 | 单层 | **多层**：会话 → 多次 LLM 调用 → 嵌套工具调用 |

#### 决策：不按会话预扣，改为「会话预算熔断 + 每次调用实时扣」

```
会话开始（AgentRun 创建）
  ├─ 检查 可用余额 >= 最小阈值（如 10 积分）—— 不通过则拒绝发起
  └─ 写 billing_user_transactions 一行（biz_id = agentRunId, status=pending）

每次 LLM 调用完成（流式结束时上游回 usage）
  ├─ 算 credits（input / output / cached 三档单价）
  ├─ **立即扣**：写账本 + `UPDATE ... SET amount = amount + ?` 累加到上面那一行
  └─ 扣后若可用余额 < 阈值 → **中断会话**，提示积分不足

嵌套工具调用（agent 生成图片 / 视频）
  ├─ 那个 job 有自己的 Hold / Settle（内部账本照常）
  └─ 但**用户可见流水归到同一个 agentRunId**，累加到同一行
```

#### 五条设计要点

| # | 要点 | 理由 |
|---|---|---|
| 1 | **按 AgentRun 聚合，不是一个 LLM 调用一条** | 符合 §7.3「用户只看一条」。用户视角是「这一轮对话花了 12 积分」 |
| 2 | **不是 Hold，是实时扣** | token 不可预知，Hold 只能取极大上限，会长时间占用用户余额 |
| 3 | **累加用 `UPDATE ... SET amount = amount + ?`** | 同一行反复更新，天然幂等（配 `callId` 去重表） |
| 4 | **熔断：余额低于阈值就中断，不允许扣成负数** | LLM 无法"少输出一点"，只能中断 |
| 5 | **嵌套工具调用归户到会话** | 用户在会话里生成了图，看到的是「会话消耗」，不是额外一条 |

**为什么不用「会话级 Hold 一个上限」**：上限 = `max_context × 最大输出`，通常是实际消耗的 5–10 倍。
用户开一个会话就被冻结几百积分，体验极差。

**单价口径**：catalog 里 LLM 的 `terms` 逐维定价——
`[{ name:"in", quantityFrom:"usage.p", unitPrice:2 }, { name:"out", quantityFrom:"usage.c", unitPrice:8 },
  { name:"cacheRead", quantityFrom:"usage.cr", unitPrice:1 }]`，
`unitDenominator: 1000000`（每百万 token）。
缓存读取走独立维度单价（不是 modifier 折扣）。

> **幂等**：每次 LLM 调用带 `callId`，账本幂等键 `llm:{agentRunId}:{callId}` 兜底——
> 上游重试或 MQ 重投不会重复累加。**不需要额外的去重表**，复用 `billing_ledger_entries` 的幂等键唯一索引。

### 8.3 图片 / 音频 / MediaKit（视频的简化版）

**同一套流程**（Hold → 执行 → Settle），差异只在**定价维度**与**完成速度**：

| 能力 | 计价单位 | 定价维度 | 相对视频 |
|---|---|---|---|
| 图片生成 | `per_image` | 模型 × 尺寸档 × 张数 | 更快，差额更少 |
| 图片编辑（抠图/扩图/擦除/超分） | `per_call` / `per_megapixel` | 模型 × 操作类型 | 单次，几乎无差额 |
| **视频生成** | `per_second` | 模型 × 分辨率 × 时长 | **基准** |
| 音频生成 | `per_second` / `per_call` | 模型 × 时长 | 同视频 |
| 音视频处理（抽音频/分音轨/擦字幕/拆镜头） | `per_second` / `per_call` | 模型 × 时长 | **fan-out 例外**（拆镜头走 §8.1 阶段 5） |

**图片多张**：`expected_output_count = N` → N 个 slot → 按成功的 slot 数收费，与视频同构。

**MediaKit 类（入参是 URL、拿不到时长）**：这是**唯一**会遇到「无法精确预扣」的场景。
但**不要照搬 new-api 的默认值硬估**（`MediaKitDefaultMinutes`）——正确做法是：

```
提交时先探测时长（异步，几秒）→ 拿到真实时长 → holdCredits → 入队
```

探测失败再退化为「按默认值估算 + 差额常态」。

### 8.4 充值支付全流程

```
用户选套餐 billing_products
   │
   ▼ 创建订单 billing_orders（status=pending，orderNo 唯一）
   ▼ 调 blue_whale_pay（jeepay）→ 返回支付页 / 二维码
   │
   ├─ 超时未支付（order_pay_timeout，默认 600s）→ 关单，不产生任何积分
   │
   ▼ 用户支付 → pay server 回调 billing-svc
   ├─ 验签失败 → 拒绝
   ├─ 幂等键 order:{orderNo}:paid 命中 → 直接返回成功（**重复回调安全**）
   └─ 事务内：
        ├─ 订单 status = paid
        ├─ 发批次 source=purchased（本金，永久）
        ├─ 发批次 source=bonus（赠送，按套餐 credits_expire_days）
        ├─ 写 billing_ledger_entries（biz_type=recharge）
        └─ 写 billing_user_transactions 一行：「充值 · 100 元套餐 · +1500 积分」
```

**三条硬规则**：

1. **幂等键是 `orderNo`，不是支付网关的流水号** —— 网关会重发多次，且可能换流水号
2. **本金与赠送拆两个批次** —— 有效期不同、财务口径不同（收入 vs 成本）、**退款只退本金**
3. **只信服务端回调，不信前端跳转** —— 用户从支付页跳回成功页 **≠** 支付成功

**退款**：只退 `purchased` 批次剩余部分；已消费的不退；`bonus` 批次直接作废。

### 8.5 会员订阅

```
订阅生效（首次购买 / 续费）
  ├─ 写 bw_memberships（tier / started_at / expires_at）
  ├─ 发当期积分：source=subscription，expires_at = 当期结束
  │    幂等键 sub:{subId}:{period}
  └─ 用户流水一行：「会员 · Pro 月度 · +1000 积分（本月有效）」

每周期首日（定时任务）→ 续发下期（同幂等键，重复跑安全）

到期未续费
  ├─ 会员状态 → expired
  ├─ 定价折扣失效（回到 free tier 系数）
  └─ **不影响已有积分批次** —— 它们按各自的 expires_at 走
```

**关键**：**会员等级只影响「定价折扣」与「并发配额」，不影响积分本身。**
会员积分就是「按周期发放的普通批次」，与其他 source 同构——**不要做特例**。

### 8.6 管理后台与运营

| 能力 | 要点 |
|---|---|
| **定价发布** | dry-run 全矩阵试算 → diff 预览 → `effective_from` → 广播失效。**回滚 = 重新激活旧版本**，不删数据 |
| **人工调整积分** | 必须走 `compensation` 批次 + **关联工单号** |
| **用户查询** | 余额 / 持有批次（含临期）/ 流水 / 按 job 反查账本分录 |
| **退款补偿** | 只更新 `billing_user_transactions` 原行 + 写账本，**不新建流水行** |
| **审计** | `bw_admin_logs`：谁、何时、改了什么、改前改后 |
| **权限** | RBAC：`billing:price:publish` · `billing:credit:grant` · `identity:user:disable` |
| **对账入口** | 上游账单 vs 明细账差异列表；账本自检结果 |

> **硬规则：禁止直接改批次余量。** 所有积分变动必须**经账本**产生对应分录。
> 否则账本与批次分叉，而对账时无法定位差异来源。

### 8.7 对账与报表

**三个层次，每天跑**：

| 层次 | 对什么 | 不平怎么办 |
|---|---|---|
| **① 账本自检** | `Σ billing_ledger_entries` vs `Σ billing_credit_lots.remaining` | 按 `user_id` 二分定位到具体分录 |
| **② 内部一致性** | `billing_cost_reservations` 里 `held` 超时未 settle/refund 的 | 补结算；仍不平则告警 |
| **③ 上游对账** | new-api 给的人民币账单 vs `billing_provider_usage` 汇总 | 差异列表，人工核查 |

**毛利报表**：`Σ 用户消费 − Σ 上游成本`，按模型 / 能力 / 时段聚合。

- 收入侧：`billing_ledger_entries` where `account = revenue`
- 成本侧：`billing_provider_cost_entries`

**上游账单粒度不足时**：如果 new-api 只给日/总额（不给按调用明细），
③ 只能对**总额**，**按用户归因只能靠自己上报的 usage**。
这是必须接受的——也正因如此，`billing_provider_usage` 必须记 `upstream_request_id`，
否则连抽样核查都做不到。

## 9. 命名规范

### 现状诊断

**已有约 70% 的表使用模块前缀**——问题不是「没有前缀」，是「30% 没跟上 + 单复数混乱 + 同名词分裂」。

| 问题 | 实例 |
|---|---|
| ① 单复数不一致 | `generation_jobs`(复) vs `generation_model_capability`(单)；`conversations`(复) vs `conversation_messages` |
| ② 同名词分裂 | **3 个 skill**（`skill` / `creative_skill` / `user_skill`）、**3 个 asset**（`assets` / `material_assets` / `shared_assets`）、2 个 user（`users` / `user_info`） |
| ③ 无名空间 | `verification_codes` · `command_idempotency` · `homepage_hero` · `storyboard_previews` |

### 规范

```
① 表名一律复数
② 前缀 = 归属（= 未来库名）         bw_ / billing_ / generation_
③ 外键 = 单数表名_id               user_id · generation_job_id · order_id
④ 关联表 = 两表名复数 _ 连接        bw_user_roles
⑤ 唯一索引 uk_{表}__{列} · 普通索引 idx_{表}__{列}
⑥ 时间/软删/乐观锁沿用              gmt_create · gmt_modified · is_delete · version
⑦ 禁止同名词分裂
```

> ② 的 `bw_` 是**产品前缀**，不是限界上下文：身份域一度用 `identity_`（ADR-0117 §2），
> 但它不自解释——`identity_users` 看不出是哪个产品的库，而本产品的库 / 只读账号 / 会话
> cookie 早已是 `bw_`（`bw_billing` / `bw_readonly` / `bw_session`）。已收敛为 `bw_`。
> `billing_` / `generation_` 仍是限界上下文前缀，不改。

### 改名成本（已核实）

**Prisma 的 `@@map` 能把模型名和表名解耦，但本仓没走这条路**：模型名一律等于表名
（`schema.prisma` 全仓零 `@@map`），所以改名必须连 `prisma.<表>` 的调用点一起改。
实测 `identity_* → bw_*` 这一轮动了 21 个 TS 文件（机械替换，无逻辑改动）。

真正的额外成本在手写 SQL 与 **worker-java**。已核实 worker-java 实际接触的表：

```
assets · generation_jobs · generation_model_capability · generation_output_slots
material_assets · project_asset · project_events
scene_card_generation_records · storyboard_previews · user_info
```

**worker-java 不碰 `users` / `verification_codes` / `topup_tiers` / `cost_*`** → 这些表改名零 Java 改动。

| 现名 | 建议 | 碰 Java? | 成本 |
|---|---|---|---|
| `users` | `bw_users` | ❌ | 低 |

## 11. 跨进程契约（Buf proto）

### 为什么必须先定

多语言下 `packages/contracts` 的 TS 类型**不能作为跨服务契约**。契约中立后，
任何服务换语言都只是重写实现，不改契约——**这是护城河**。

```
packages/contracts/
  proto/
    common/v1/types.proto         Credits · SpecAttr · 分页
    billing/v1/billing.proto      ★ RPC 面：Hold · QueryBalance · ListTransactions
    billing/v1/usage.proto        UsageLine（worker → billing，经 MQ）
    billing/v1/events.proto       MQ 事件：job.completed · catalog.activated
    identity/v1/identity.proto    VerifySession（应用层 Guard 调）
  gen/
    ts/    ← TypeScript 服务消费
    java/  ← Java 服务消费（billing-svc / worker-java）
```

用 **Buf** 管理 + CI 强制 breaking change 检测。手写 TS 类型不再跨服务使用。

### ⚠️ RPC 面很小 —— **结算不走 RPC**

| 交互 | 方式 | 为什么 |
|---|---|---|
| **提交预扣** | **同步 gRPC**（50ms 预算） | 必须当场知道余额够不够 |
| **完成结算** | **MQ 事件** | 异步，不阻塞任何用户请求 |
| **失败返还** | **MQ 事件** | 同上 |
| 余额查询 | gRPC（读） | 数据主权，不跨服务直连 DB |
| 流水列表 | gRPC（读） | 同上 |
| **价格预览** | **本地算，不 RPC** | business-api 持有 catalog 只读副本 |

**只有 `Hold` 在用户等待路径上。** 其余全是异步或本地。
这是 200ms 预算能守住的原因。

### billing/v1/billing.proto

```protobuf
syntax = "proto3";
package billing.v1;

// 同步 RPC 面。**结算 / 返还走 MQ 事件（见 events.proto），不在此。**
service BillingService {

  // 预扣。**在用户等待路径上 —— 调用方超时预算 50ms。**
  // 幂等键 hold:{command_id}；重复请求返回首次结果 + duplicated=true。
  rpc Hold(HoldRequest) returns (HoldResponse);

  // 余额与持有批次（用户可见）。允许短缓存（Redis，写时失效）。
  rpc QueryBalance(QueryBalanceRequest) returns (QueryBalanceResponse);

  // 用户可见流水（**一业务一行**，见 §2.3）。
  rpc ListTransactions(ListTransactionsRequest) returns (ListTransactionsResponse);
}

message HoldRequest {
  int64  user_id           = 1;
  string command_id        = 2;   // ★ 幂等键来源——**客户端生成，不是 job_id**
  int64  job_id            = 3;
  string model_id          = 4;
  string task_type         = 5;
  map<string,string> specs = 6;   // 原始规格，billing 内部 normalize
  string title             = 7;   // 展示文案快照（写进用户流水）
}

message HoldResponse {
  int64 reserved_credits = 1;
  int32 catalog_version  = 2;   // ★ 调用方须冻结进 job
  bool  duplicated       = 3;   // 幂等命中（重复请求）
}

message QueryBalanceRequest { int64 user_id = 1; }

message QueryBalanceResponse {
  int64 available_credits = 1;   // Σ(remaining − frozen)
  int64 frozen_credits    = 2;
  repeated ExpiringLot expiring = 3;   // 临期批次（前端「X 积分将于 Y 日过期」）
}

message ExpiringLot {
  int64  credits    = 1;
  string expires_at = 2;   // ISO8601
  string source     = 3;   // register | daily | ...（决定展示文案）
}

message ListTransactionsRequest {
  int64  user_id   = 1;
  int32  page_size = 2;
  string page_token = 3;   // 游标分页，不用 offset
  string type_filter = 4;  // 可选：consume | recharge | ...
}

message ListTransactionsResponse {
  repeated UserTransaction items = 1;
  string next_page_token = 2;
}

// ★ 用户可见流水。**注意：不含 reserved_amount**（§2.3.1 硬规则）。
message UserTransaction {
  string id        = 1;
  string type      = 2;   // consume | recharge | bonus | daily | ...
  string direction = 3;   // in | out
  string title     = 4;   // 「视频生成 · seedance-2.5 1080p 5s」
  int64  amount    = 5;   // **最终值，唯一金额**
  string status    = 6;   // pending | done
  string created_at = 7;
  string settled_at = 8;  // 仅 done 时非空
}
```

> **`UserTransaction` 里没有 `reserved_amount`。**
> 用户端 API 不返回预扣值（§2.3.1）——它只对客服/运营后台可见。

### billing/v1/usage.proto

```protobuf
syntax = "proto3";
package billing.v1;

message UsageLine {
  string model_id  = 1;
  string task_type = 2;

  // ★ key 与 catalog 的 baseUnit / dims / multipliers 使用**同一套封闭枚举**
  //   （usage.p · usage.seconds · usage.succeededSlots · usage.referenceCount · ...）
  //   好处：配置与上报天然对齐 —— 不会出现「配了某个维度但没人上报」
  map<string, int64> quantities = 3;

  map<string, string> specs = 4;   // 规范化前的原始规格

  string upstream_request_id   = 5;   // ★ 对账桥
  int64  upstream_cost_credits = 6;   // 上游实际收我们的（毛利分析）
  UsageSource usage_source     = 7;
}

enum UsageSource {
  USAGE_SOURCE_UNSPECIFIED = 0;
  UPSTREAM  = 1;   // 上游返回的 usage —— **权威**
  ESTIMATED = 2;   // 自己估算 —— 结算时**告警**（§4.5 计费准确四规则之一）
}
```

**两条硬约定**：

1. **`catalog_version` 存 job 上，不由 worker 回显** ——
   worker 不该知道价格，也不该参与版本管理。
2. **`upstream_request_id` + `upstream_cost_credits` 是对账桥** ——
   没有这两项，上游账单和明细永远对不上。

### 错误语义

| gRPC 状态 | 业务码 | 场景 | 调用方行为 |
|---|---|---|---|
| `FAILED_PRECONDITION`<br>（映射 HTTP 402） | `INSUFFICIENT_CREDITS` | 余额不足 | **拒绝创建 job**，提示充值 |
| `INVALID_ARGUMENT` | `UNPRICEABLE` | 该 (model, task, specs) 算不出价 | **拒绝**，告警（**定价漏配**） |
| `UNAVAILABLE` | `BILLING_UNAVAILABLE` | billing 不可用 | **快速失败，不重试**（见下） |

**`duplicated = true` 不是错误** —— 幂等命中时返回 `OK` + 首次结果，调用方据此继续。

#### ⚠️ billing 不可用时必须 **fail closed**

```
billing 挂了 → 返回 503 → business-api **拒绝提交**（不是放行）
```

**钱的服务宁可少卖，不可错卖。** 放行等于允许无限透支，事后无法追回。
文案上对用户表现为「服务繁忙，请稍后再试」，而不是"扣费失败"。

| 规则 | 说明 |
|---|---|

## 12. 管理端 API 契约

> **HTTP/JSON，不是 gRPC** —— 这是 `business-api` 暴露给管理端 UI 的 REST 接口。
> 内部它转发到 `identity-svc` / `billing-svc`。
> 浏览器只访问同源 `/api/**`，**永远不直接连内部服务**。

### 12.1 权限点（RBAC）

权限点存在 `bw_roles.permissions`（JSON 数组），Guard 校验：

| 权限点 | 能力 | 建议角色 |
|---|---|---|
| `pricing:read` | 查看定价目录与版本 | 运营 |
| `pricing:edit` | 编辑草稿、校验、看 diff | 运营 |
| **`pricing:publish`** | **发布 / 回滚** | 定价负责人 |
| `promotion:write` | 建/改/启停**营销活动** | **运营** |
| `memberdiscount:write` | 改**会员折扣** | 定价负责人 |
| `credit:read` | 查任意用户余额、流水、账本 | 客服 |
| **`credit:grant`** | **人工调整积分** | 财务 / 主管 |
| `recon:read` | 看对账与毛利 | 财务 |
| `identity:user:disable` | 封禁 / 解禁用户 | 客服主管 |

**关键分工**：`promotion:write` 给运营（高频、影响面小），
`pricing:publish` 给定价负责人（低频、影响全部收入）。**这是拆表带来的权限分层。**

**`GET .../ledger` 是客服的核心工具** —— 它返回带 `balance_after` 的逐笔分录：

```json
{
  "entries": [
    { "bizType": "hold",   "account": "frozen", "direction": "credit",
      "amount": 40000, "balanceAfter": 40000, "bizId": "10086", "at": "..." },
    { "bizType": "settle", "account": "frozen", "direction": "debit",
      "amount": 40000, "balanceAfter": 0,     "bizId": "10086", "at": "..." }
  ]
}
```

**`POST /credits/grant` 的四条硬约束**：

```json
{
  "userId": 42,
  "credits": 50000,           // mc
  "source": "compensation",   // 只能用工单类 source
  "expireDays": 30,
  "ticketNo": "IK1234",       // ★ 必填，关联工单
  "reason": "生成失败补偿"
}
```

1. **`ticketNo` 必填** —— 无工单不予调整
2. **`source` 只能是 `compensation` / `gift`** —— 不能伪装成 `purchased`（否则污染收入口径）
3. **只新建批次，禁止改已有批次的 `remaining`** —— 所有变动必须经账本产生分录
4. **写 `bw_admin_logs`** —— 谁、何时、给谁、多少、为什么

> **第 3 条是硬规则**：直接改批次余量会让账本与批次分叉，**对账时无法定位差异来源**。

### 12.7 通用约定

| 项 | 约定 |
|---|---|
| **分页** | 游标分页（`page_token` / `next_page_token`），**不用 offset**——超时未结算的预留会不断新增，offset 分页会漏 |
| **错误** | 对齐 [ADR-0083](../adr/0083-unified-error-codes-and-projection.md) 统一错误码 |
| **审计** | **所有写操作**（`PUT`/`POST`/`DELETE`）写 `bw_admin_logs`，含变更前后对照 |
| **幂等** | 写操作接受 `Idempotency-Key` header；重复请求返回首次结果 |
| **鉴权** | 走 §5 的应用层 Guard（`identity.VerifySession` 拿 `tier` / 权限） |

## 13. 可观测性与告警

> 计费系统出问题**往往不是崩，而是「悄悄算错」**——服务全绿，但钱算错了，
> 一个月后对账才发现。
> 所以这一节的重点不是「服务活着吗」，而是 **「有没有算错」**。

### 13.1 三层可观测

| 层 | 工具 | 关键 |
|---|---|---|
| **指标** | Prometheus（Java 用 Micrometer · Node 用 prom-client） | 每服务暴露 `/metrics` |
| **日志** | 结构化 JSON → Loki / ES | 必带 `traceId` / `userId` / `jobId` |
| **链路** | OpenTelemetry → Collector → Jaeger / Tempo | **跨语言必须统一**（§4 多语言前提之一） |

**TraceID 透传链**：

```
网关生成 → HTTP header → gRPC metadata → MQ message header → worker → billing
```

**任何一跳丢了 TraceID，跨语言排查就不可能。** 这条是 §4「多语言三个前提」的落地。

### 13.2 计费核心指标

**★ 标记的三个是「算错钱」信号——阈值是 `> 0`，不是比例。**

| 指标 | 含义 | 阈值 | 级别 |
|---|---|---|---|
| ★ `billing.pricing.unpriceable_total` | **算不出价的请求** | **> 0** | P1 |
| ★ `billing.settle.overflow_total` | **`actual > reserved` 次数** | **> 0** | P1 |
| ★ `billing.reconcile.unbalanced_users` | **账本与批次不平的用户数** | **> 0** | **P0** |
| `billing.catalog.load_failure_total` | catalog 加载失败 | > 0 | **P0** |
| `billing.hold.latency_p99` | Hold 延迟 | > 100ms | P1 |
| `billing.hold.fail_rate` | 预扣失败率（**不含**余额不足） | > 1% | P1 |
| `billing.settle.lag_seconds` | 事件产生 → 结算完成 | > 300s | P1 |
| `billing.reconcile.pending_holds` | 超时未结算的预留数 | > 100 | P2 |
| `billing.provider.estimated_usage_ratio` | 估算 usage 占比 | > 5% | P2 |
| `billing.hold.insufficient_rate` | 余额不足占比 | **突增** | P2 |
| `billing.discount.relaxed_total` | 命中的折扣数与预期不符 | — | P2 |

**为什么这三个是 `> 0` 而不是比例**：

| 指标 | 出现一次意味着 |
|---|---|
| `unpriceable` | **定价漏配** —— 某个 (模型, 规格) 组合没配价格，用户提交被拒 |
| `settle.overflow` | **`holdCredits` 算漏维度** —— 预扣少算，结算才发现要补扣 |
| `unbalanced_users` | **有分录写错了** —— 账本与批次分叉，必须立刻人查 |

**一次都不该出现。出现即代码/配置有 bug。**

### 13.3 告警分级与响应

| 级别 | 触发 | 响应时限 | 谁 |
|---|---|---|---|
| **P0** | 账本不平 · catalog 加载失败 · Hold 全挂 | **立即**（电话） | 值班 |
| **P1** | 算不出价 · `actual > reserved` · Hold 失败率 > 1% · 结算延迟 > 5min | 15 分钟 | 值班 |
| **P2** | 超时预留堆积 · 估算 usage 占比高 · 余额不足突增 | 工作时间 | 计费负责人 |
| **P3** | 缓存命中率下降 · 毛利率异常 | 周报 | 运营 |

**告警文案必须带上下文** —— 不能只报「有 N 个不平」，要带：

```
[P0] 账本不平用户数 = 3
  首个：userId=42, ledgerSum=50000, lotsSum=45000, delta=5000
        疑似分录 id=991234（balance_after 断裂）
        traceId=abc123  jobId=10086
  排查入口：/api/admin/recon/ledger-check
```

**能被 5 分钟内定位的告警才有价值。**

### 13.4 日志规范

计费相关日志必须结构化且带足上下文：

```json
{ "level": "warn", "ts": "2026-09-24T14:22:01+08:00", "traceId": "abc123",
  "userId": 42, "jobId": 10086, "modelId": "seedance-2.5", "taskType": "text2video",
  "event": "billing.settle.overflow",
  "reservedMc": 40000, "actualMc": 45000, "gapMc": 5000 }
```

**绝不记**：

| ❌ | 原因 |
|---|---|
| 用户 `sk-` | 已不存在，但旧代码还在传，**改造时要删干净** |
| 完整手机号 | 只记后 4 位（`138****1234`） |
| 上游密钥 / TOS 签名 URL | 泄露面 |
| 完整身份证明文 | 合规 |

### 13.5 对账是「最慢的告警」，但最可靠

指标是近实时的、可能漏；**对账是全量的、一定会发现**。三层都要有：

| 层次 | 频率 | 发现什么 |
|---|---|---|
| 指标告警 | 实时 | 延迟、错误率、算不出价 |
| **预留兜底扫描** | 10 分钟 | 卡住的预留（→ 补结算或返还） |
| **每日对账** | 每天 | **账本不平、上游账单差异** |

**只有指标告警 = 漏；只有对账 = 慢一天。** 两者都要。

### 13.6 billing 不可用时的降级与识别

```
billing 挂 → Hold 返回 503 → business-api **拒绝提交**（fail closed，§11）
```

**监控要能区分两种「Hold 失败」**：

| 现象 | 判断 | 处置 |
|---|---|---|
| `hold.fail_rate` 高 **且** `billing.up == 0` | billing 挂了 | 拉起 / 扩容 |
| `hold.fail_rate` 高 **但** `billing.up == 1` | **代码 bug 或 DB 问题** | 查慢查询 / 查异常栈 |
| `hold.insufficient_rate` 突增 | **可能是定价配错**（价格突然变贵） | 查最近的 catalog 发布 |

**第三行容易被忽略**——用户突然集体"余额不足"，第一反应是充值问题，
**实际上往往是刚发布了一个把价格调高很多的 catalog**。

### 13.7 业务仪表盘（给运营看，不是给运维看）

| 图表 | 用途 |
|---|---|
| 日活充值用户 / 充值金额 | 营收 |
| 积分消耗量（按模型 / 能力） | 产品热度 |
| **毛利率**（收入 − 上游成本，按模型） | **哪些模型在亏钱** |
| 活跃活动及其影响面 | 营销效果 |
| 余额分布 / 零余额用户数 | 转化机会 |

**「哪些模型在亏钱」这张图最重要** —— 它是定价决策的唯一依据。

### 13.8 容量口径与分片触发条件

**先算清楚量级，再决定要不要分片。**

| 指标 | 估算口径 | 量级 |
|---|---|---|
| **扣费写入 QPS** | 生成任务提交数 ÷ 60（瞬时峰值 ×3） | 生成产品远低于 100/s |
| **余额查询 QPS** | DAU × 每人每天 5 次 ÷ 86400 | **比写高 10–100×，但走缓存** |
| **账本行数/年** | 每次任务约 4–6 条分录 | 百万级，MySQL 无压力 |
| **批次行数/年** | 每次发放 1 行 | 百万级 |

**单进程 Node/Java + 连接池的实测吞吐**：扣费事务（若干 UPDATE + INSERT）约 **2k–8k TPS**，
瓶颈在 MySQL 单库，不在应用。

**当前设计对应的容量上限**：

| 量级 | 处理 |
|---|---|
| 扣费 < 2k TPS | **单库单进程够**，当前设计直接可用 |
| 2k–10k TPS | 调优：连接池、`FOR UPDATE` 的锁粒度、只读副本 |
| **> 10k TPS** | **触发分片**（`user_id` 为分片键） |

**分片触发条件（满足任一才做）**：

1. 扣费 QPS 持续 > 10k
2. 单表 `billing_ledger_entries` > 5 亿行
3. 扣费事务 P99 > 50ms 且**确认瓶颈在 DB 行锁**（而非慢查询）

**在触发之前，不做分片。** 分片会让跨用户查询（对账、报表）变复杂——
**没有量级支撑的分片是纯负债。**

> 表结构**已经按 `user_id` 组织**（所有 billing 表都有 `user_id` 且索引前缀是它），
> 所以**真到那天，分片是配置级的事，不是重构**。

## 14. 分期与切换

### 硬约束：deadline 是 new-api 独立那一天

只要 worker 还用用户 `sk-`，new-api 就继续替我们扣费。
new-api 独立后统一 key 到位，**sk- 链自动断，new-api 停止扣用户的钱**——
**那一刻我们必须能自己扣，否则用户白嫖。** 这是外部事件，不是我们能排期的。

### 双重扣费风险

| 时序 | 结果 |
|---|---|
| 今天（sk- 在，billing 无） | new-api 扣 → 用户扣**一次** ✅ |
| **billing 上线但 sk- 还在** | 我们扣 + new-api 扣 → **扣两次** ❌ |
| sk- 断链，billing 就位 | 只有我们扣 ✅ |

**billing 上线必须和 sk- 断链同时发生，不能有中间态。**

### 分期

| 阶段 | 内容 | 周期 | 并行 |
|---|---|---|---|
| **P0** | 冻结边界：不再新增读 new-api 用户/日志的代码 | 0 | — |
| **P1** | `identity-svc`：表 + 会话 + 三方登录 + RBAC + 登录日志 | 2 周 | 与 P2 并行 |
| **P2** | `billing-svc` 骨架：`credit_lots` + `ledger_entries` | 3 周 | 与 P1 并行 |
| **P3** | `billing_pricing_catalogs`（JSON 目录）+ 计算管线 + 折扣 + 三层校验 + 发布流程 | 2 周 | — |
| **P4** | 运营面：products / redeems / invite_logs / daily_grants / api_keys | 1.5 周 | — |
| **P5** | **断 sk- 链**（删 `provider_credential`、worker 改统一 key） | 1 周 | } 必须同时 |
| **P6** | **billing 权威生效**（结算从 new-api 收回自建） | 1 周 | } |
| **P7** | 抽服务 / 分片（按需，不提前做） | — | — |

**P1–P4 是准备期，P5+P6 是切换期，两者之间不能留缝。**

### 存量处理（已定）

- **身份**：一次性 ETL。**密码 hash 可直接复用，存量用户无需重置密码。**
  new-api 用的是标准 **bcrypt**（`bcrypt.GenerateFromPassword(pwd, bcrypt.DefaultCost)`，
  `blue-whale-api/common/crypto.go:23-32`），hash 格式 `$2a$10$…` 共 60 字符；
  现有 `bw_users.password` 沿用 `VarChar(63)`，**刚好装得下**。
  校验侧：Java 用 Spring Security `BCryptPasswordEncoder`，TS 用 `bcrypt` npm 包，两端都能验同一 hash。
- **余额**：**不对接，历史余额线下处理。** 我们的体系按标准从零起算，不从 new-api 迁入任何 quota；
  切换日之后的新消费走自有账本。

> 这条降低了最大风险：**没有余额迁移，就没有双写期、没有对账差异。**
> 代价是切换日需要一个明确的运营动作（线下给存量用户补/清），**必须与 P5/P6 同日执行**。

## 15. 风险与待决项

### 风险

| 风险 | 缓解 |
|---|---|
| 切换期双重扣费 | P5 与 P6 同时，中间不留缝（**不存在中间态**，见 runbook §3.1） |
| 上游账单粒度不足 | 上游可能只给日/总额。**按用户归因会失去上游校验**，只能靠自己上报的 usage——这是必须接受的 |
| 初始定价 | 切换前必须配好 catalog 全量规则；**漏配 = 提交时算不出价被拒**。发布前 dry-run + 轴完整性校验兜底 |
| 切换日运营动作 | 存量余额线下处理必须与 P5/P6 **同日**执行，口径需提前定 |
| worker-java 直连 DB | 改表名要改 Java SQL（已核实只有 10 张表） |
| billing 用 Java 需改红线 #10 | 走 ADR；有 TypeScript 零成本替代 |
