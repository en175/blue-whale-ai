## 0. 核心命题：正确性是**不变量**，不是输出值

普通业务测「输入 A → 输出 B」。**计费不行**——因为：

- 操作序列是**任意交错**的（hold/settle/refund/recharge/expire 会随机组合）
- 穷举序列不可能
- **但正确性是一个全局性质**：*无论经历什么操作序列，账本永远平衡*

**所以主力应该是「不变量测试」，不是「用例测试」。**

| | 用例测试 | **不变量测试** |
|---|---|---|
| 覆盖 | 我想得到的路径 | **所有路径** |
| 发现 | 我预期的错 | **我没想到的错** |
| 工具 | JUnit 断言 | **jqwik 属性测试** |

**两者都要，但重心在不变量。**

## 2. 不变量清单（**最重要的一节**）

**这十条在任何操作序列后都必须成立。测试就是反复验证它们。**

### 账本不变量

| # | 不变量 | 断言 |
|---|---|---|
| **I1** | **复式平衡** | 每个 `biz_id` 的分录，**借贷合计相等** |
| **I2** | **用户级平衡** | `Σ(借 wallet) − Σ(贷 wallet) == Σ lots.remaining` |
| **I3** | **`balance_after` 连续** | 同一 `(user, account)` 按时间序：`prev.balance_after ± amount == cur.balance_after` |

### 批次不变量

| # | 不变量 | 断言 |
|---|---|---|
| **I4** | **量级约束** | `0 ≤ frozen ≤ remaining ≤ amount`，**任何时刻** |
| **I5** | **余额口径** | `Σ remaining` == 用户总持有积分（含冻结） |

### 流水不变量

| # | 不变量 | 断言 |
|---|---|---|
| **I6** | **一业务一行** | `(user_id, type, biz_id)` 唯一 |
| **I7** | **金额一致** | `status=done` 时，`amount` == 对应 `settle` 分录的金额 |
| **I8** | **用户可见性** | 用户端 API 响应**不含** `reserved_amount` |

### 幂等不变量

| # | 不变量 | 断言 |
|---|---|---|
| **I9** | **重复无害** | 任意操作**重复执行 N 次**，账本状态与执行 1 次相同 |
| **I10** | **预留终态唯一** | 每个 `cost_reservations` 只会是 `held → settled` 或 `held → released`，**不会都发生** |

**I2 是最强的那个** —— 它一条就覆盖了「扣了没记」「记了没扣」「记错科目」等一整类 bug。

## 3. 属性测试（Property-Based）★

### 3.1 为什么必须用属性测试

```
用例测试：我写 hold→settle，断言余额 = 15
属性测试：随机生成 200 个操作的交错序列，断言 I1–I10 全部成立
```

**后者能发现你根本没想到的组合**：
- 部分批次在 hold 与 settle 之间过期
- 同一 commandId 重复提交
- settle 与 refund 竞态
- 充值与消费交错

### 3.2 用 jqwik（Java）

```java
class BillingInvariantProperties {

    @Property(tries = 500)
    void 任意操作序列后账本仍然平衡(@ForAll("operationSequence") List<BillingOp> ops) {
        long userId = fixture.createUser(fen(100_000));   // 10 万积分

        for (BillingOp op : ops) {
            try {
                executor.apply(op, userId);
            } catch (InsufficientCreditsException expected) {
                // 余额不足是预期内的运行时结果，不是失败
            }
        }

        // ── I2 用户级平衡：最有价值的一条
        long ledgerNet = ledgerRepo.netFor(userId, Account.WALLET);
        long lotsSum   = lotRepo.sumRemaining(userId);
        assertThat(ledgerNet).isEqualTo(lotsSum);

        // ── I3 balance_after 连续
        assertBalanceAfterIsContiguous(userId);

        // ── I4 批次量级约束
        for (CreditLot lot : lotRepo.findAll(userId)) {
            assertThat(lot.frozen()).isBetween(0L, lot.remaining());
            assertThat(lot.remaining()).isLessThanOrEqualTo(lot.amount());
        }

        // ── I6 一业务一行
        assertThat(utxRepo.countRows(userId)).isEqualTo(utxRepo.countDistinctBiz(userId));

        // ── I10 预留只有一个终态
        for (CostReservation r : reservationRepo.findAll(userId)) {
            assertThat(r.status()).isIn(HELD, SETTLED, RELEASED);
        }
    }

    /** 操作生成器：随机交错所有可能的动作 */
    @Provide
    Arbitrary<List<BillingOp>> operationSequence() {
        return Arbitraries.oneOf(
                holds(),          // 含：金额随机、commandId 随机/复用
                settles(),        // 含：actual < = > reserved
                refunds(),
                recharges(),      // 含：本金 + 赠送两批次
                dailyGrants(),
                lotExpiry()       // 中途让某些批次过期
        ).list().ofMinSize(10).ofMaxSize(200);
    }

    /** I9 幂等：把同一序列跑两遍，状态应完全相同 */
    @Property(tries = 200)
    void 重复执行同一序列状态不变(@ForAll("operationSequence") List<BillingOp> ops) {
        long u1 = fixture.createUser(fen(100_000));
        long u2 = fixture.createUser(fen(100_000));

        ops.forEach(op -> ignoreInsufficient(() -> executor.apply(op, u1)));
        ops.forEach(op -> ignoreInsufficient(() -> executor.apply(op, u2)));
        ops.forEach(op -> ignoreInsufficient(() -> executor.apply(op, u2)));   // 第二遍

        assertThat(snapshot(u1)).isEqualTo(snapshot(u2));   // 含批次、账本、流水
    }
}
```

### 3.3 收缩（Shrinking）是它的杀手锏

jqwik 发现失败后会**自动收缩到最小反例**：

```
❌ 不变量 I2 失败（200 个操作后不平，delta=5000）
🔍 收缩后最小反例：
   [GrantDaily(userId, 2026-10-01, 5000),
    Hold(userId, "c1", 3000),
    LotExpiry(userId, /* 让 daily 批次过期 */),
    Settle("c1", actual=3000)]
```

**四条操作就复现了** —— 手工构造这个反例要很久。

## 4. 各层测什么

### 4.1 单元（纯函数）

| 测什么 | 关键用例 |
|---|---|
| **扣减顺序** | 三级 tie-break：`expires_at` → `source 优先级` → `id` |
| **规格归一化** | 大小写、键序、空白、多余字段 |
| **定价公式** | 等效数量计算、`dims` 加权、`multipliers` 连乘、`unitDenominator` |
| **折扣解析** | 会员内取最优 · 营销内取最优 · `stackMode` 两分支 · `floorFactorBp` 底线 |
| **时段命中** | 周几 · **跨天时段**（22:00→06:00）· 时区边界（23:59 / 00:00）· 无时段=全天 |
| **舍入** | `roundHalfUp` 在 `.5` 边界的取值 |
| **`basePrice` 解析** | 常数 / 按轴查表 / **查不到抛异常（不降级为 0）** |

### 4.2 集成（真 DB，真事务）

| 场景 | 断言 |
|---|---|
| `hold → settle`（三类：<、=、>） | 各自的分录正确且**借贷平衡** |
| `hold → refund` | `remaining` **未变**、批次 `expires_at` **未变** |
| **并发 `hold` 同一用户** | N 线程并发，最终余额正确、无超扣 |
| 跨批次扣减 + 中途批次过期 | 按 `allocations` 精确解冻 |
| 重复 `hold` / `settle` / `refund` | 返回首次结果，账本不变 |
| 充值回调重复 / 乱序 / 验签失败 | 幂等 + 状态机保护 |
| 订单超时关闭后收到迟到回调 | 拒绝 |

**并发测试要点**：

```java
@Test
void 同用户并发预扣不会超扣() throws Exception {
    long userId = fixture.createUser(fen(100));      // 100 积分
    int threads = 32;

    var results = runConcurrently(threads,
            i -> billingService.hold(userId, "cmd-" + i, jobId(i), fen(10), 1));

    long succeeded = results.stream().filter(Result::ok).count();
    assertThat(succeeded).isEqualTo(10);                      // 100 / 10 = 10 个成功
    assertThat(lotRepo.availableOf(userId)).isZero();          // 正好扣完，不超
    assertThat(ledgerRepo.netFor(userId, Account.WALLET)).isEqualTo(fen(100));
}
```

### 4.3 契约

| 检查 | 工具 |
|---|---|
| **proto breaking change** | `buf breaking --against '.git#branch=master'` |
| **TS / Java 生成物对拍** | 同一 `.proto` 生成两端，字段号与类型必须一致 |
| **usage 维度枚举一致性** | catalog 的 `baseUnit`/`dims`、proto 的 `quantities` key、`QuantityRegistry` **三方一致** |

> **第三方一致性**是「配了但没人上报」的结构性防线（架构设计 §11）。

### 4.4 对账（**故意制造不平**）

正向测「对上了」没用，**要测「对不上时能不能定位」**：

```java
@Test
void 账本与批次不一致时能定位到具体分录() {
    long userId = fixture.createUser(fen(100));
    ops.hold(userId, "c1", fen(30));
    ops.settle(userId, "c1", fen(20));

    // ★ 故意破坏：直接改一条分录的 amount（模拟历史脏数据）
    ledgerRepo.forceUpdateAmount(/* 最后一条 settle 分录 */, fen(999));

    var report = reconcileService.checkLedger(userId);

    assertThat(report.unbalanced()).hasSize(1);
    assertThat(report.unbalanced().get(0).suspectEntryId())   // ★ 必须能指出是哪一笔
            .isEqualTo(/* 被改的那条 id */);
    assertThat(report.unbalanced().get(0).reason()).isEqualTo("balance_after 断裂");
}
```

**同理要测**：
- 预留超时未结算 → 兜底扫描能补
- 上游账单与 `provider_usage` 差异 → 能列出

### 4.5 端到端

真实起服务跑通一条链（**金标验收，不能只跑 mock**）：

```
注册 → 充值到账 → 提交生成（预扣）→ worker 执行 → 结算 → 查流水
```

**断言用户视角**：

```
提交后：流水 1 条，status=pending，显示「预计消耗 19 积分」
完成后：**仍是 1 条**，status=done，显示「消耗 15 积分」
       用户 API 响应里**没有** reserved_amount 字段
```

## 5. 开闭验证（设计模式的回归测试）

架构设计 §4.6 声称「加折扣来源 / 加校验规则不用改引擎」。**这个声称要测**：

```java
@Test
void 新增折扣来源不需要改已有代码() {
    // 注册一个测试用的 Provider
    var ctx = new AnnotationConfigApplicationContext();
    ctx.registerBean(TestCouponProvider.class);          // 只加这一个 Bean
    ctx.register(DiscountResolver.class, ...);

    var resolver = ctx.getBean(DiscountResolver.class);
    var result = resolver.apply(pricingCtx, fen(100));

    assertThat(result.appliedDiscounts())
            .extracting(AppliedDiscount::source)
            .contains("coupon");                          // 新来源生效
}
```

**「不改任何已有测试就能通过」是这条设计的验收标准。**
做不到就说明抽象漏了，要重开 ADR-0116。

## 6. 金标套件（与 worker / 上游对账）

### 6.1 为什么需要

`worker-java` 直连 DB 写 `generation_job_usage`，billing 消费它算钱。
**两边对「用量」的理解可能漂移**（ADR-0084 已登记这个风险）。

### 6.2 做法

```
① 用真实任务跑一批（覆盖各模态 × 各规格）
② 记录：worker 上报的 quantities  vs  billing 实际用的 quantities
③ 断言：逐字段相等
```

**任何字段不等 = 有人的契约理解错了。**

### 6.3 上游 usage 的核对

```
抽样 N 个已结算 job：
  billing 算的 credits  vs  按 upstream 返回的原始 usage 手工算一遍
断言相等（允许舍入差异 ≤ 1 积分，但要统计比例）
```

**`usage_source=estimated` 的必须单独统计** —— 那批本身就是不准的，占比要 `> 5%` 就告警（架构设计 §13）。

## 7. CI 门禁

| 阶段 | 跑什么 | 失败 |
|---|---|---|
| pre-commit | 单元测试 + 格式 | 阻止提交 |
| PR | ① 单元 ② 集成 ③ 契约 | 阻止合并 |
| **PR（计费相关改动）** | **+ jqwik 属性测试 500 次** | 阻止合并 |
| 每日 | ④ 对账夹具 + ⑥ 金标套件 | 告警 |
| 发版前 | ⑤ 端到端 + `--stage pr` 发布门禁 | 阻止发布 |

> 按仓库现有约定（红线 #12）：**收口与 PR 前都由选择器按影响面决定层级**，
> 计费模块属于产品影响路径，走 PR 门禁。

## 8. 验收清单

**上线前必须全部通过：**

- [ ] I1–I10 十条不变量在 500 次随机操作序列下成立
- [ ] `hold → settle` 三类（<、=、>）分录正确且借贷平衡
- [ ] `hold → refund` 后批次 `remaining` 与 `expires_at` 均未变
- [ ] 32 线程并发 `hold` 同用户，余额精确、无超扣
- [ ] 重复 `hold`/`settle`/`refund` 幂等（状态与执行一次相同）
- [ ] 制造账本不平 → 自检能**指出具体分录 id**
- [ ] 制造卡住的预留 → 兜底扫描能补结算
- [ ] 用户端 API 响应**不含** `reserved_amount`
- [ ] 用户流水的 `amount` 与账本一致，且**一个业务动作只有一行**
- [ ] `usage` 维度枚举三方一致（catalog / proto / `QuantityRegistry`）
- [ ] `buf breaking` 通过
- [ ] 新增 `DiscountProvider` / `ValidationHandler` 子类，**不改已有测试即可通过**
- [ ] 端到端真实链路跑通，金标验收（不是只跑 mock）
- [ ] `usage_source=estimated` 占比 < 5%

## 附：测试数据构造的坑

| 坑 | 规避 |
|---|---|
| 时间相关测试不稳定 | **注入 `Clock`**，不要用 `Instant.now()`。文档里所有 `submitAt` / 过期判定都走它 |
| 随机种子不可复现 | jqwik 失败时**记录 seed**，CI 日志里保留 |
| 测试库被上一次污染 | 每个用例**独立事务回滚**；并发用例用独立 user |
| 批次过期靠等 | 构造时**直接给定 `expires_at`**（过去/未来），不要 sleep |
| 折扣时段测试跨零点 | 用固定 `Clock` 显式构造 `22:30` / `06:30` / `23:59:59` |
