## 0. 先看清要迁什么

### 0.1 现状：**两张用户表并存**

| 表 | 归属 | 关键字段 | 实际用途 |
|---|---|---|---|
| `users`（Go，new-api） | `blue-whale-api` 仓库 | `username`(uniq) · `password`(bcrypt) · `email` · **`quota`** · `role` · `status` · 6 种第三方 id · `aff_*` 邀请体系 | **实际登录 + 实际扣费** |
| `users`（Prisma，Node） | 本仓 `backend/prisma` | **`phone`(uniq)** · `password` · `status` | 手机登录写了一半，**没接通** |

> 这正是 `docs/research/2026-07-30-arch-open-questions.md` 的 **Q2**：
> 「手机流程的 Prisma 库和 new-api 的 users 表是**两套库**，用户数据会分裂。」

**迁移的本质 = 把这两张表合并成一张 `identity_users`。**

### 0.2 new-api `users` 的真实字段（`blue-whale-api/model/user.go`）

| 字段 | 类型 | 迁到哪 |
|---|---|---|
| `id` | int | `identity_external_refs.external_id`（**保留映射**） |
| `username` | varchar(20) uniq | `identity_users.username` |
| `password` | varchar | `identity_users.password_hash`（**bcrypt 直接搬**） |
| `display_name` | varchar(20) | `identity_users.username`（若 username 不可读时兜底） |
| `role` | int（1=普通，10=管理） | `identity_user_roles`（**不再用魔数**） |
| `status` | int（1=启用，2=禁用） | `identity_users.status` |
| `email` | varchar(50) | `identity_users.email` |
| `github_id` / `discord_id` / `oidc_id` / `wechat_id` / `telegram_id` / `linux_do_id` | varchar | **`identity_linked_accounts`**（六行，provider 区分） |
| `quota` | int32 | ❌ **不迁**（见 §2） |
| `used_quota` / `request_count` | int | 只进对账报表，不入库 |
| `group` | varchar | ❌ 不迁 |
| `aff_code` / `aff_count` / `aff_quota` / `aff_history_quota` / `inviter_id` | | `billing_invite_logs`（**只迁已完成发放的**，见 §1.5） |
| `deleted_at` | 软删 | **过滤掉**（迁活人） |
| `setting` | text | 人工判断，默认丢弃 |
| `remark` | varchar | `identity_users` 备注（可选） |
| `allowed_systems` | varchar | ❌ 不迁（这是 new-api 的多系统白名单，我们不再共用） |
| `created_at` / `last_login_at` | int64（秒） | `gmt_create` / 最后登录 |

## 1. 阶段一：存量身份 ETL

### 1.1 ✅ 已核实的事实（**R1 / R2 已解决**）

| # | 结论 | 证据 |
|---|---|---|
| **R1** | new-api 的 `username` **不是手机号**——它**根本没有 `phone` 字段** | `blue-whale-api/model/user.go` 的 `User` 结构体无 phone；`controller/user.go:205` 注册只收 `username` + `email` |
| **R2** | 两张表**没有关联键**，但**不需要关联**——Node `users` 表**基本是空的** | `loginWithCode`（`backend/libs/core/auth/login-with-code.ts:33`）**导出但零调用者**；`upsertUser(phone)` 从未被触发。发码通了（`auth.controller.ts:93`），**用码登录没接** |

**因此：ETL 只需迁 new-api 一张表，不存在「合并」问题。**

> **这修正了两个早期假设**：
> ① 手机号**不是存量迁移的前提**（new-api 侧根本没有手机号数据）；
> ② Node 的 `users` / `user_info` 表**没有真实数据可迁**。
>
> **手机号登录是「后续新增能力」**，与迁移解耦——见 §7 D10。

### 1.2 迁移范围

```sql
-- 只迁「活着的、有使用记录的」用户
SELECT * FROM users
 WHERE deleted_at IS NULL
   AND ( used_quota > 0 OR quota > 0 OR last_login_at > 0 );
```

**不迁**：从未登录且零余额的僵尸账号（占比通常很高，迁移它们只是搬运垃圾）。

> 僵尸账号的处理：不删，留在 new-api。它们若回来登录，走 §1.6 的「新用户注册」路径。

### 1.3 导入语句

**`username` 是登录凭据，`phone` 留空**（存量用户没有手机号，后续自行绑定）：

```sql
INSERT INTO identity_users (username, phone, email, password_hash, status, gmt_create)
SELECT
    u.username,
    NULL,                                        -- ★ 存量用户无手机号（new-api 没有该字段）
    NULLIF(u.email, ''),
    u.password,                                  -- ★ bcrypt hash 原样搬，不用重置密码
    CASE u.status WHEN 1 THEN 'NORMAL' ELSE 'DISABLED' END,
    FROM_UNIXTIME(u.created_at)
  FROM users u
 WHERE u.deleted_at IS NULL
   AND u.username <> ''
   AND (u.used_quota > 0 OR u.quota > 0 OR u.last_login_at > 0);
```

**密码 hash 不需要任何转换** —— new-api 用标准 bcrypt（`bcrypt.DefaultCost`=10），
`$2a$10$…` 共 60 字符，我们 `password_hash VarChar(63)` 装得下，Java/TS 两端都能校验。
**存量用户不需要重置密码。**

**例外**：若 `deleted_at IS NULL` 但 `username` 为空的行（脏数据），跳过并记录。

### 1.4 第三方绑定（**六个 provider**）

new-api 的 `User` 有六种第三方 id，**逐 provider 插行**：

```sql
INSERT INTO identity_linked_accounts (user_id, provider, provider_uid)
SELECT nu.id, 'github', u.github_id
  FROM users u
  JOIN identity_map m ON m.new_api_id = u.id
  JOIN identity_users nu ON nu.id = m.new_user_id
 WHERE u.github_id <> '';
-- 其余 discord / oidc / wechat / telegram / linux_do 同理
```

**`identity_linked_accounts.provider` 的取值范围**（对应 new-api 的六个字段）：

| provider | new-api 字段 |
|---|---|
| `github` | `github_id` |
| `discord` | `discord_id` |
| `oidc` | `oidc_id` |
| `wechat` | `wechat_id` |
| `telegram` | `telegram_id` |
| `linuxdo` | `linux_do_id` |

> **微信绑定的迁移要产品确认**（§7 D10）——new-api 侧是 `wechat_id`，
> 但蓝鲸自己的微信登录可能用的是另一套 openid，两者不一定同源。

### 1.5 邀请体系

new-api 的 `aff_code` / `aff_count` / `aff_quota` / `aff_history_quota` / `inviter_id`：

| 字段 | 处置 |
|---|---|
| `aff_code` | 迁到 `billing_redeems`（若有未使用的邀请码） |
| `inviter_id` | 迁到 `billing_invite_logs.inviter_id`（映射到新 id） |
| `aff_history_quota` | **已实际发放过**的部分 → 作为历史记录迁入 |
| `aff_quota`（剩余额度） | ❌ **不转为积分**——它从未真正发出去 |

> **`aff_quota` 的处置要产品确认**——见 §7 D7。

### 1.6 ETL 执行步骤

```
① 备份
   mysqldump new-api 库 users 表 → TOS + 本地

② 建映射表（**保留作审计**，不删）
   CREATE TABLE identity_map (
     new_api_id  INT PRIMARY KEY,
     new_user_id BIGINT,
     gmt_create  DATETIME
   );

③ 干跑（dry-run，只统计不写库）
     待迁入 N 个（有使用记录且未软删）
     跳过 M 个（僵尸账号 / username 为空）
     username 冲突 K 个
   ★ 人工审阅这份报告后才继续

④ 正式导入（事务内）
   INSERT identity_users（§1.3）
   INSERT identity_linked_accounts（§1.4）
   INSERT identity_user_roles（按 new-api 的 role：10 → admin，其余 → user）
   INSERT identity_map

⑤ 抽样校验
   随机 100 个用户：**用原密码登录** → 断言成功
```

**幂等**：脚本可重复执行（`INSERT ... ON DUPLICATE KEY UPDATE`）。
**可回滚**：`identity_map` 保留了双向映射，出问题可追。

### 1.7 验收

- [ ] 迁入数量与干跑报告一致
- [ ] **随机抽样 100 个用户，用原密码能登录**（验证 bcrypt 复用成功）
- [ ] 第三方绑定数量与 new-api 侧逐 provider 比对一致
- [ ] `identity_map` 行数 == 迁入用户数
- [ ] **没有**两个 `identity_users` 指向同一个 `new_api_id`
- [ ] **没有**两个 `identity_users` 的 `username` 重复
- [ ] 跳过列表已人工确认（僵尸账号确实是僵尸）
- [ ] `phone` / `email` 全为 NULL 或有效值，**无空字符串**

## 2. 阶段二：存量余额处置（**线下，不对接**）

**ADR-0115 决策 11：存量余额不对接，线下处理。**

| 项 | 做法 |
|---|---|
| new-api 的 `quota` | **不导入** `billing_credit_lots` |
| 用户实际应得的余额 | **运营线下核对后，用 `POST /api/admin/credits/grant` 人工补发** |
| 补发的 `source` | `compensation`（**不能伪装成 `purchased`**，否则污染收入口径） |
| 补发批次的有效期 | 建议给**较长有效期**（如 1 年），避免用户觉得被吞了 |

**为什么不对接**：
- 没有余额迁移 → **没有双写期 → 没有对账差异**
- 代价是切换日需要一次运营动作，**必须与切换同日执行**

**运营动作清单**：

```
① 切换前一周：导出 new-api 所有 quota > 0 的用户与余额
② 按 1 元 = 15 积分（或你们定的换算）折算
   注：new-api 的 quota 是 USD 锚点（500,000 quota = $1），
       折算需先定汇率口径——见 §7 待决项 D8
③ 生成补发清单（user_id, credits, 工单号）
④ 切换当日：批量调 /api/admin/credits/grant
⑤ 抽样核对：N 个用户的余额与预期一致
```

> **D8 是硬缺口**：`500,000 quota = $1` → 我们只做人民币。
> 折算需要一个「美元 → 人民币」口径，**而 ADR-0115 决策 3 说取消汇率**。
> 所以这是一次性折算，**不引入运行时汇率**——口径需产品/财务定。

## 3. 阶段三：切换（P5 + P6 **同时**）

### 3.1 为什么必须同时

| 时序 | 结果 |
|---|---|
| 今天（sk- 在，billing 无） | new-api 扣 → 用户扣**一次** ✅ |
| **billing 上线但 sk- 还在** | 我们扣 + new-api 扣 → **扣两次** ❌ |
| sk- 断链，billing 就位 | 只有我们扣 ✅ |

**中间态不存在。** 所以：

```
P5（断 sk- 链）  ┐
                 ├─ 同一个发布窗口，一次完成
P6（billing 生效）┘
```

### 3.2 切换前的对账（**按需跑，不需要特殊模式**）

```
拉上游某段时间的扣费记录（上游本来就有，随时可查）
  │
  └─ 对同一个 job，用我们的 catalog 重算一遍（billing 的 Quote RPC，只算不扣）
       │
       └─ 比差异 → 差异 > 1% → 停下，修定价
```

**不需要影子模式，也不需要我们自己再记一份。** 上游的记录就是历史；
我们的价随时可重算——目录是版本化的，`loadVersion` 能复现任意历史版本的价。
多攒一份只会在两处维护同一件事。

> ⚠️ **本节原先写的「每日比对：我们算的 vs new-api 扣的」预设了一个错误前提**：
> 它假设「我们的价应该和它扣的一致」。但**定价是我们自己定的**——用户该付多少由
> catalog 说了算，与上游收我们多少无关。
>
> 对账真正能回答的是「同一批任务，用户在新旧两套体系下各付多少、差多少」，
> 这是**产品口径**问题（切换后用户会不会觉得贵了/便宜了），不是「我们算错了没有」。
>
> 「我们算得对不」由另外两件事保证：**发布时的 dry-run + 轴空间覆盖校验**（§3.3 步骤 8），
> 以及上线后的 `billing.pricing.unpriceable` 指标（§13）。

### 3.3 切换窗口步骤

| 步 | 动作 | 检查 | 失败怎么办 |
|---|---|---|---|
| 1 | **公告**：停服窗口（建议 30 分钟，低峰期） | — | — |
| 2 | 冻结新生成提交（返回「维护中」） | — | — |
| 3 | 等待进行中任务全部终态（或超时判失败） | `SELECT count(*) FROM generation_jobs WHERE status IN ('queued','processing')` == 0 | 超 15 分钟 → 强制判失败并返还 |
| 4 | **停 worker**（`worker-java` 缩容到 0） | Pod 数 = 0 | — |
| 5 | **跑 ETL**（§1.7 ④） | §1.8 验收全过 | **回滚：不启动新服务，恢复原状** |
| 6 | **发存量余额**（§2） | 抽样核对通过 | 同上 |
| 7 | **启动 identity-svc + billing-svc** | 健康检查通过 | 同上 |
| 8 | **发 catalog**（定价目录） | `POST /pricing/publish` + dry-run 通过 | 同上 |
| 9 | **切换 worker 配置**：删 `provider_credential` 逻辑，改用统一 key | 起 1 个 Pod 跑通一个任务 | **回滚：恢复旧镜像** |
| 10 | **恢复提交** | 端到端跑一次真实生成 | — |
| 11 | 观察 30 分钟 | §13 的三条 P0 指标全为 0 | 未归零 → **执行回滚** |

### 3.4 回滚（**必须能在 5 分钟内完成**）

```
回滚触发条件（任一）：
  ✗ 账本不平（billing.reconcile.unbalanced_users > 0）
  ✗ 算不出价（billing.pricing.unpriceable > 0）
  ✗ 结算异常（billing.settle.overflow > 0）
  ✗ 端到端跑不通

回滚步骤：
  ① 冻结提交
  ② 停 identity-svc / billing-svc
  ③ worker 换回旧镜像（用统一 key 的那版 → 换回用 sk- 的那版）
  ④ 恢复 new-api 扣费（它一直没停，只是我们不再用它了）
  ⑤ 恢复提交
  ★ 存量数据不回滚（identity / billing 的数据留着，修好再来）
```

**关键**：**回滚不回滚数据，只回滚流量**。
因为 ETL 是幂等的、可重跑的；而回滚数据会引入新的不一致。

### 关于 D10：手机号登录（**后续能力，与迁移解耦**）

**已核实的现状**：

| 项 | 状态 |
|---|---|
| 发短信验证码 | ✅ 已接通（`POST /auth/send-code`） |
| **用验证码登录** | ❌ **未接入**（`loginWithCode` 导出零调用者） |
| new-api 侧的手机号数据 | ❌ **不存在**（`User` 结构体无 phone 字段） |

**因此手机号登录上线时**：

- **不需要迁移任何手机号**（没有源数据）
- 存量用户继续用 `username` / `email` 登录，**不受影响**
- 想做手机号登录的用户**主动绑定**（复用 `identity_verification_codes` 的 `scene=bind`）
- **不要强制绑定** —— 存量用户没有手机号不是你强制他们的理由

**这是渐进增强，不是替换。**

### 关于 D11：微信绑定

new-api 的 `wechat_id` 与蓝鲸自己的微信登录**不一定同源**（openid 是按 appid 分的）。
如果两边的 appid 不同，**迁过来的 `wechat_id` 无法直接用于蓝鲸的微信登录**。

**核实方法**：比对 new-api 的公众号/开放平台 appid 与蓝鲸侧的是否一致。
不一致 → **不迁微信绑定**，让用户重新绑。
