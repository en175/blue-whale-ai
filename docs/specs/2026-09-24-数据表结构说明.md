## 0. 通用约定

### 0.1 三种整数单位（**全库零浮点**）

| 单位 | 含义 | 用在 |
|---|---|---|
| **mc**（微积分） | 1 积分 = 1000 mc | **所有金额列** |
| **bp**（万分比） | `9000` = 90% | 折扣系数 |
| **permille**（千分比） | `1200` = 1.2 倍 | 倍率 |

**为什么金额不用浮点也不用「分」**：见《计费逻辑详细设计》§1。

### 0.2 每条业务表都有的四个字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK AUTO_INCREMENT | 主键 |
| `gmt_create` | DATETIME | 创建时间 |
| `gmt_modified` | DATETIME | 最后修改时间（`ON UPDATE CURRENT_TIMESTAMP`） |
| `version` | INT | 乐观锁版本号 |

**`is_delete`（TINYINT 软删）只在字典/配置类表上**——流水与账本类**禁软删**（append-only）。

### 0.3 索引命名

| 前缀 | 含义 | 例子 |
|---|---|---|
| `uk_{表}__{列}` | 唯一索引 | `uk_lots__grant_key` |
| `idx_{表}__{列}` | 普通索引 | `idx_lots__user_expiry` |

### 0.4 归属与来源标记

每张表标注三项：

- **归属**：哪个服务的库（identity / billing / generation）
- **来源**：🆕 新建 · 🔧 改造已有 · ✅ 已有
- **本期**：✅ 本期落地 · ⏸️ 后续（文本相关）

## 1. identity 域（9 张）

### 1.1 `identity_users` 账号主体

> **归属** identity · **来源** 🔧 改造 `users` · **本期** ✅

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 用户 ID。**全系统的权威用户标识**（`bw_user_id`） |
| `username` | VARCHAR(50) UNIQUE | ★ **登录凭据**（主用）。**存量用户靠它登录** |
| `password_hash` | VARCHAR(63) NULL | **bcrypt hash**（`$2a$10$…` 共 60 字符）。沿用 new-api 的算法，**存量密码可直接复用**（ADR-0115 决策 11） |
| `phone` | VARCHAR(20) UNIQUE **NULL** | 手机号。**可空**——**存量用户没有**（new-api 侧无此字段，见 §1.1.2）；绑定后可用于手机号登录 |
| `email` | VARCHAR(128) UNIQUE **NULL** | 邮箱。可作为登录标识（与 `username` 二选一输入） |
| `status` | VARCHAR(20) | `NORMAL` / `DISABLED` / `DELETED` |
| `avatar` | VARCHAR(255) NULL | 头像 URL |
| `gmt_create` / `gmt_modified` / `version` | | 通用字段 |

**约束**

- `username` 唯一 —— **它是当前的登录凭据**
- `phone` 唯一**但可空** —— 多个 NULL 不冲突；绑定后唯一
- `email` 唯一**但可空** —— 同上
- **不含 role**：角色走 `identity_user_roles`（替代原 new-api 的 `role >= 10` 魔数）
- **不含余额**：余额在 `billing_credit_lots`（替代原 new-api 的 `users.quota`）

#### 1.1.1 登录方式（**分阶段**）

| 标识 | 状态 | 说明 |
|---|---|---|
| `username` + `password` | ✅ **当前主用** | 走的是「单一标识输入」——前端一个框，后端先当 username 试，再当 email 试 |
| `email` + `password` | ✅ **当前已支持** | 与上面共用同一入口（ADR-0062 决策 9） |
| **手机号 + 验证码** | ⏸️ **后续** | **发码已通**（`POST /auth/send-code`），**登录未接**（`loginWithCode` 无调用者） |

**关键：手机号不是登录前提。** 存量用户用 `username` 登录，
将来手机号登录上线后，**绑定过手机号的用户**多一种登录方式（渐进增强，不是替换）。

#### 1.1.2 手机号从哪来（**没有存量数据**）

已核实（`blue-whale-api/model/user.go`）：

- new-api 的 `User` 结构体**没有 `phone` 字段**，注册只收 `username` + `email`
- 所以 **new-api 侧完全没有手机号数据可迁**

因此 `phone` 只能靠：

1. **用户主动绑定**（后续做绑定入口，复用 `identity_verification_codes` 的 `scene=bind`）
2. 新注册用户可以直接手机号注册

#### 1.1.3 与现状的差异

| 原 `users`（Prisma，Node） | 现在 |
|---|---|
| `phone VarChar(20) UNIQUE`（**NOT NULL**） | → **NULL-able**（存量用户没有） |
| `username VarChar(50)`（无唯一约束） | → **UNIQUE**（提为登录凭据） |
| `password VarChar(63) NULL` | → `password_hash`（语义更明确） |
| — | 新增 `email` |
| `user_info.provider_credential`（sk- 存放） | **整表删除** |

## 2. billing 域（18 张）

### 2.1 `billing_credit_lots` 积分批次 ★

> **归属** billing · **来源** 🆕 · **本期** ✅

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | |
| `user_id` | BIGINT | |
| `source` | VARCHAR(24) | 积分来源，见 §2.1.1 |
| `amount` | BIGINT (mc) | **发放总量**，发放后不变 |
| `remaining` | BIGINT (mc) | **剩余总量**（含冻结） |
| `frozen` | BIGINT (mc) | **冻结中**的量 |
| `expires_at` | DATETIME NULL | **NULL = 永久** |
| `biz_type` | VARCHAR(32) | 来源业务类型：`order` / `grant` / `migrate` |
| `biz_id` | VARCHAR(128) | 来源业务 id（订单号 / 活动号） |
| `grant_key` | VARCHAR(190) | **发放幂等键**（见 §2.1.2） |
| `gmt_create` / `gmt_modified` / `version` | | |

**不变量（任何时刻）**：`0 ≤ frozen ≤ remaining ≤ amount`

**可用余额**（不落表，实时聚合）：

```sql
SELECT COALESCE(SUM(remaining - frozen), 0)
  FROM billing_credit_lots
 WHERE user_id = ?
   AND (expires_at IS NULL OR expires_at > NOW());
```

**索引**
- `uk_lots__grant_key (grant_key)` —— 发放幂等
- `idx_lots__user_expiry (user_id, expires_at)` —— 余额聚合 + 临期查询
- `idx_lots__user_id (user_id, id)` —— 扣减顺序（`id ASC` 的第三级 tie-break）

#### 2.1.1 `source` 枚举

| 值 | 来源 | 默认有效期 | 财报口径 |
|---|---|---|---|
| `register` | 注册赠送 | 30 天 | 成本 |
| `daily` | 每日登录 | **当日 23:59:59** | 成本 |
| `invite` | 邀请奖励 | 30 天 | 成本 |
| `redeem` | 兑换码 | 按码配置 | 成本 |
| `purchased` | **充值本金** | **永久** | **收入** |
| `bonus` | **充值赠送** | 按套餐 | 成本 |
| `subscription` | 会员周期赠送 | 当期 | 成本 |
| `gift` | 运营赠送 | 按配置 | 成本 |
| `compensation` | 事故补偿 | 按工单 | 成本 |

**`purchased` 与 `bonus` 必须拆两个批次**——有效期不同、财报口径不同、
**退款只退本金**。

#### 2.1.2 `grant_key` 格式

| 场景 | 值 |
|---|---|
| 注册赠送 | `grant:register:{userId}` |
| 每日赠送 | `grant:daily:{userId}:{date}` |
| 邀请奖励 | `grant:invite:{inviteeId}` |
| 兑换码 | `grant:redeem:{code}` |
| 会员周期 | `grant:sub:{subId}:{period}` |
| 充值本金 | `recharge:{orderNo}` |
| 充值赠送 | `recharge:{orderNo}:bonus` |
| 运营补偿 | `grant:{ticketNo}` |

**全部落在唯一索引上**——重复请求靠数据库报冲突，不靠应用层判重。

### 2.2 `billing_ledger_entries` 复式账本 ★

> **归属** billing · **来源** 🆕 · **本期** ✅

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | |
| `user_id` | BIGINT | |
| `account` | VARCHAR(24) | 会计科目，见 §2.2.1 |
| `direction` | VARCHAR(8) | `debit`（借）/ `credit`（贷） |
| `amount` | BIGINT (mc) | **恒正**。方向由 `direction` 表达 |
| `biz_type` | VARCHAR(32) | `hold` / `settle` / `refund` / `recharge` / `grant` / `expire` / `adjust` |
| `biz_id` | VARCHAR(128) | 关联业务 id（jobId / orderNo） |

| `remark` | VARCHAR(255) | 备注 |
| `gmt_create` | DATETIME | |

**append-only**：不 UPDATE、不 DELETE。冲正靠**反向分录**，不靠改历史。

**复式平衡**：每笔业务动作产生的分录**借贷合计相等**（分录总表见《计费逻辑详细设计》§3）。

#### 2.2.1 `account` 科目

| 值 | 含义 | 正常方向 |
|---|---|---|
| `wallet` | 用户积分钱包 | 贷方余额 |
| `frozen` | 用户冻结 | 借方余额 |
| `revenue` | 平台收入（**付费**积分被消耗） | 贷方 |
| `cost` | 平台成本（**赠送**积分被消耗 / 上游成本） | 借方 |
| `receivable` | 应收（超扣、欠费） | 借方 |

**索引**：`uk_ledger__idem (idempotency_key)`、`idx_ledger__user_time`、`idx_ledger__biz (biz_type, biz_id)`

| `amount` | BIGINT (mc) | **最终值**。消费时 = 实际消耗 |
| `reserved_amount` | BIGINT (mc) NULL | **仅 consume**：预扣值。**内部字段，用户 API 不返回** |

`type`：`consume` · `recharge` · `bonus` · `daily` · `invite` · `redeem` ·
`subscription` · `gift` · `compensation` · `refund` · `expire`

**约束**
- `uk_utx__biz (user_id, type, biz_id)` —— **一个 job 只可能有一行**
- `idx_utx__user_time (user_id, gmt_create)` —— 列表分页

**硬规则（用户可见性）**
- 任何用户可见界面**永远只出现一个金额**
- **禁止**「预扣 X，实扣 Y」并列；**禁止**「预扣」这个词出现在用户端
- **用户端 API 不返回 `reserved_amount`**

**投影性质**：本表**可从账本重建**——按 `biz_id` 聚合 `billing_ledger_entries` 即可。
所以它的「可变」（`pending → done`）不构成一致性问题。
