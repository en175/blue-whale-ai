## 1. 单位与口径

| 项 | 值 |
|---|---|
| 币种 | 人民币，**单一币种，无汇率** |
| 积分定义 | **1 元 = 15 积分** |
| 账本单位 | **整数积分** |
| 最低粒度 | 1 积分 ≈ 0.0667 元 ≈ 6.67 分 |
| 与「分」的关系 | 只在支付边界出现，**不进账本、不进定价** |

**为什么账本不用「分」**：`1 积分 = 100 ÷ 15 ≈ 6.6667 分`，不是整数。
用「分」会让定价被迫按 300 分（3 元）的倍数走，**无法表达「1 张图 = 2 积分」**。

**充值档位约束**：套餐金额必须使积分为整数——5 元 = 75 ✓；10 元 = 150 ✓；0.5 元 = 7.5 ✗。
`billing_products` 保存时校验。

### 1.1 舍入规则：出口只**四舍五入**一次

计算管线内部用 `long` 微积分（mc，1 积分 = 1000 mc）保精度，
**出口一次性四舍五入（HALF_UP）到整数积分，此后不再有任何舍入**：

```java
/** HALF_UP：mc + 500 后整数除法截断。credits 恒正，无负数边界。 */
private static long roundHalfUp(long mc) {
    return (mc + 500L) / 1000L;
}
```

**这一条保证「用户看到的 = 实际扣的」** —— 舍入发生在**写账本之前**，
而不是展示层再做一次。

> **为什么不用向上取整（ceil）**：ceil 永远偏向平台，且让折扣更难生效。
> 四舍五入是中性的——有时多得、有时少得，用户更容易接受。

### 1.2 整数积分的必然约束：让利必须 > 0.5 积分

```
定价 5 积分，9 折   → 4.5  → 四舍五入 → 5     折扣失效（让利恰好 0.5，卡边界）
定价 5 积分，85 折  → 4.25 → 四舍五入 → 4    ✓ 生效（让利 0.75）
定价 6 积分，9 折   → 5.4  → 四舍五入 → 5    ✓ 生效（让利 0.6）
定价 50 积分，99 折 → 49.5 → 四舍五入 → 50    折扣失效（让利 0.5）
```

**生效条件**：`B × (1 − f) > 0.5`，即**让利必须超过半个积分**。

| 定价 | 生效的最低折扣 | 说明 |
|---|---|---|
| 5 积分 | ≤ **85 折** | 让利 0.75 |
| 6 积分 | ≤ **9 折** | 让利 0.6 |
| 10 积分 | ≤ **95 折** | 让利 0.5 —— **刚好不生效**，实际要 ≤ 94 折 |
| 50 积分 | ≤ **99 折** | 让利 0.5 —— 同上，实际要 ≤ 98 折 |
| 100 积分 | ≤ **995 折**（99.5%） | 让利 0.5 —— 同上 |

**这不是 bug，是整数积分 + 四舍五入的数学必然。**

> **比向上取整宽松一倍**：ceil 要求让利 ≥ 1 积分，四舍五入只要 > 0.5 积分。
> 5 积分 × 9 折在 ceil 下彻底失效，在四舍五入下也失效（卡在 0.5 边界），
> 但 **85 折在四舍五入下能生效，在 ceil 下不能**。

**对策：把它变成配置期校验**（§4.5.6）——而不是上线后收到「会员怎么没便宜」的投诉。

## 2. 数据模型

### 2.1 billing_credit_lots（积分批次）

```sql
CREATE TABLE billing_credit_lots (
  id           BIGINT       NOT NULL AUTO_INCREMENT,
  user_id      BIGINT       NOT NULL,
  source       VARCHAR(24)  NOT NULL,   -- §2.1.1
  amount       BIGINT       NOT NULL,   -- 发放总量（发放后不变）
  remaining    BIGINT       NOT NULL,   -- 剩余总量（含冻结）
  frozen       BIGINT       NOT NULL DEFAULT 0,
  expires_at   DATETIME     NULL,       -- NULL = 永久
  biz_type     VARCHAR(32)  NOT NULL,
  biz_id       VARCHAR(128) NOT NULL,
  grant_key    VARCHAR(190) NOT NULL,   -- 发放幂等键
  gmt_create   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  gmt_modified DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  version      INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_lots__grant_key (grant_key),
  KEY idx_lots__user_expiry (user_id, expires_at),
  KEY idx_lots__user_id (user_id, id)
) ENGINE=InnoDB;
```

**不变量（任何时刻）**：`0 ≤ frozen ≤ remaining ≤ amount`

**可用余额**——不落表，实时聚合（10 个批次内微秒级）：

```sql
SELECT COALESCE(SUM(remaining - frozen), 0)
  FROM billing_credit_lots
 WHERE user_id = ?
   AND (expires_at IS NULL OR expires_at > NOW());
```

> **为什么不设物化余额表**：两处状态必然有不一致风险，而对账时无法判断谁对。
> 批次是唯一权威。展示层用 Redis 缓存 + 写时失效即可。

#### 2.1.1 source 枚举与默认有效期

| source | 来源 | 默认有效期 | 财报口径 |
|---|---|---|---|
| `register` | 注册赠送 | 30 天 | 成本 |
| `daily` | 每日登录 | **当日 23:59:59** | 成本 |
| `invite` | 邀请奖励 | 30 天 | 成本 |
| `redeem` | 兑换码 | 按码配置 | 成本 |
| `purchased` | **充值本金** | **永久** | **收入** |
| `bonus` | **充值赠送** | 按套餐 `credits_expire_days` | 成本 |
| `subscription` | 会员周期 | 当期 | 成本 |
| `gift` | 运营赠送 | 按配置 | 成本 |
| `compensation` | 事故补偿 | 按工单 | 成本 |

**`purchased` 与 `bonus` 必须拆成两个批次**——有效期不同、财报口径不同、
**退款只退本金**。`bonus`（充值赠送）也区别于 `gift`（运营赠送）。

#### 2.1.2 冻结语义

| 阶段 | 操作 |
|---|---|
| 提交预扣 | `frozen += x`（按 §3.1 顺序分配到多个批次） |
| 完成结算 | `frozen -= x`；`remaining -= actual` |
| 失败返还 | `frozen -= x`（**`remaining` 不动**） |

**`frozen` 不是「已花掉的钱」，是「暂时占用的钱」。**

> **为什么返还不动 `remaining`**：若「先扣掉、返还时新建批次」，返还的积分会带上
> **新的有效期**——用户凭空获得一次有效期重置，与应得权益不符。

### 2.2 billing_ledger_entries（复式账本）

```sql
CREATE TABLE billing_ledger_entries (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  user_id         BIGINT       NOT NULL,
  account         VARCHAR(24)  NOT NULL,  -- §2.2.1
  direction       VARCHAR(8)   NOT NULL,  -- debit(借) | credit(贷)
  amount          BIGINT       NOT NULL,  -- 恒正
  biz_type        VARCHAR(32)  NOT NULL,  -- hold|settle|refund|recharge|grant|expire|adjust
  biz_id          VARCHAR(128) NOT NULL,
  idempotency_key VARCHAR(190) NOT NULL,
  balance_after   BIGINT       NOT NULL,  -- 该科目变动后余额快照
  remark          VARCHAR(255) NOT NULL DEFAULT '',
  gmt_create      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (id),
  UNIQUE KEY uk_ledger__idem (idempotency_key),
  KEY idx_ledger__user_time (user_id, gmt_create),
  KEY idx_ledger__biz (biz_type, biz_id)
) ENGINE=InnoDB;
```

- **append-only**：不 UPDATE、不 DELETE。冲正靠**反向分录**，不靠改历史。
- **复式平衡**：每笔业务动作产生的分录**借贷合计相等**（见 §3 分录总表）。

#### 2.2.1 科目

| account | 含义 | 正常方向 |
|---|---|---|
| `wallet` | 用户积分钱包 | 贷方余额 |
| `frozen` | 用户冻结 | 借方余额 |
| `revenue` | 平台收入（付费积分被消耗） | 贷方 |
| `cost` | 平台成本（赠送积分被消耗 / 上游成本） | 借方 |
| `receivable` | 应收（超扣、欠费） | 借方 |

#### 2.2.2 balance_after 的作用

每个 `(user_id, account)` 的**变动后余额快照**。

**作用**：对账时**逐笔可验证**——`prev.balance_after ± amount == cur.balance_after`。
不成立即**定位到具体的那一笔分录**，而不是只知道总数不平。

### 2.3 billing_user_transactions（用户可见流水）

```sql
CREATE TABLE billing_user_transactions (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  user_id         BIGINT       NOT NULL,
  direction       VARCHAR(8)   NOT NULL,  -- in | out
  type            VARCHAR(24)  NOT NULL,  -- 见下
  biz_type        VARCHAR(32)  NOT NULL,
  biz_id          VARCHAR(128) NOT NULL,
  title           VARCHAR(255) NOT NULL,  -- 展示文案快照（免关联查询）
  amount          BIGINT       NOT NULL,  -- **最终值**，恒正
  reserved_amount BIGINT       NULL,      -- 仅 consume：预扣值，**内部字段**
  status          VARCHAR(16)  NOT NULL,  -- pending | done
  catalog_version INT          NULL,      -- 仅 consume
  gmt_create      DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  gmt_settled     DATETIME     NULL,
  version         INT          NOT NULL DEFAULT 0,
  PRIMARY KEY (id),
  UNIQUE KEY uk_utx__biz (user_id, type, biz_id),
  KEY idx_utx__user_time (user_id, gmt_create)
) ENGINE=InnoDB;
```

`type`：`consume` · `recharge` · `bonus` · `daily` · `invite` · `redeem` ·
`subscription` · `gift` · `compensation` · `refund` · `expire`

#### 2.3.1 硬规则：用户可见性

| | |
|---|---|
| ✅ 允许 | 「处理中 · 预计消耗 40 积分」→「已完成 · 消耗 30 积分」 |
| ❌ 禁止 | 「预扣 40，实扣 30，退回 10」 |
| ❌ 禁止 | 「扣费 40」+「退款 10」两条 |
| ❌ 禁止 | **「预扣」这个词出现在任何用户端** |
| ❌ 禁止 | 用户端 API 返回 `reserved_amount`（仅客服/运营后台可见） |

**任何用户可见界面，永远只出现一个金额。**

#### 2.3.2 投影性质

本表**可从账本重建**——按 `biz_id` 聚合 `billing_ledger_entries` 即可。

所以它「可变」（`pending → done`）**不构成一致性问题**：
不是「一个事实存两处」，而是「**权威 + 缓存**」的关系。

### 2.4 billing_cost_reservations（内部预留）

由原 `cost_reservations` 改造。**不暴露给用户端任何接口**，仅 Admin 与对账使用。

关键新增字段：`allocations JSON` —— 记录预扣时**分配到哪些批次的哪些数量**（见 §4.2）。

### 2.5 billing_pricing_catalogs（定价目录 — 版本化 JSON 文档）

**定价不是行表，是一份版本化的 JSON 文档。** 理由：

- 定价规则要**整体发布 / 整体回滚**，行表做不到原子
- 一份 catalog ≈ 50 模型 × 5 任务 ≈ 250 条规则 < 300 KB，**可整体加载进内存**
- 运营改价 = 改 JSON + 发布，**不发版、不改表、不重启**

```sql
CREATE TABLE billing_pricing_catalogs (
  id              BIGINT       NOT NULL AUTO_INCREMENT,
  catalog_version INT          NOT NULL,
  status          VARCHAR(16)  NOT NULL,   -- draft | active | retired
  document        JSON         NOT NULL,   -- ★ 完整规则
  schema_version  INT          NOT NULL,
  document_hash   CHAR(64)     NOT NULL,   -- 内容哈希
  effective_from  DATETIME     NULL,
  effective_to    DATETIME     NULL,
  published_by    VARCHAR(64)  NOT NULL,
  published_at    DATETIME     NOT NULL,
  note            VARCHAR(255) NOT NULL DEFAULT '',
  PRIMARY KEY (id),
  UNIQUE KEY uk_catalog__version (catalog_version),
  UNIQUE KEY uk_catalog__hash (document_hash)
) ENGINE=InnoDB;
```

- **同一时刻只有一条 `active`**
- 发布 = 插新行 + 旧行置 `retired`（**永不删**，历史 job 结算要用）
- **回滚 = 把旧版本重新置 `active`**，一条 UPDATE，不改文档
- job 上冻结 `catalog_version` + `document_hash`

#### 2.5.1 JSON 文档结构

**catalog 只管「基础单价」——不含任何折扣。** 折扣见 §2.6 / §2.7 的独立表。

```json
{
  "schemaVersion": 1,
  "currency": "CNY",
  "creditsPerYuan": 15,

  "models": {
    "doubao-1.5-pro": {

      }

    "seedance-2.5": {
      "text2video": {

                       "table": { "1024x1024": 2000, "1792x1024": 3332 } },
```

**为什么折扣不在这份文档里**（详见 §2.6 开头的对比表）：
基础计价的变更频率是**月/季度**，营销活动是**每天**。
混在一份文档里，运营每建一个活动就要发布一个新 catalog 版本——
**版本号爆炸、停一条活动要发整版、权限分不开**。

#### 2.5.2 编码约定（写进 JSON Schema）

| 约定 | 原因 |
|---|---|
| **金额 = 微积分整数**（`2000` = 2.000 积分） | 零浮点 |
| **倍率 = 万分比整数**（`4000` = 4.0 倍 · `1000` = 0.1 倍） | 零浮点 |
| **`basePrice.by` 显式声明定价轴** | 完整性校验的依据 |
| **`baseUnit` / `dims` / `multipliers` 的 key 是封闭枚举** | 拼错在**加载期**拒绝（§4.5.8） |

#### 2.5.3 计费模型：等效数量 × 基准单价

**对齐 new-api 的倍率制**（`service/text_quota.go:257-308`）——
**只有一个基准价，其他维度全是「相对基准的倍率」**：

```
effectiveUnits = quantity(baseUnit) + Σ over dims ( quantity(dim) × 相对倍率 )
credits_mc     = effectiveUnits × basePrice / unitDenominator
                              × Π over multipliers ( 整单倍率 )
```

**三个概念**：

| 概念 | 含义 |
|---|---|
| `baseUnit` + `basePrice` | **基准维度与基准单价**。单价为常数，或按轴查表 |
| `dims` | **按数量加权**的其他维度，值是**相对基准的万分比** |
| `multipliers` | **整单连乘**的倍率（无独立数量，如参考图加价） |

**为什么用相对倍率而不是绝对单价**：

| | 绝对单价 | **相对倍率（本设计）** |
|---|---|---|
| 配置量 | 每维一个价（4–6 个） | **1 个基准 + 几个倍率** |
| **调价** | 每个维度都要改 | **只改 `basePrice` 一处** |
| 语义 | 「输入 2、输出 8」 | **「输出是输入的 4 倍」** |

**同一套结构覆盖全部模态**：

| 模态 | `baseUnit` | `basePrice` | `dims` | `multipliers` | 本期 |
|---|---|---|---|---|---|
| **图片** | `usage.succeededSlots` | 查尺寸档表 | — | 参考图数 | ✅ |
| **视频** | `usage.seconds` | 查分辨率表 | — | 参考图数 | ✅ |
| **音频** | `usage.seconds` / `usage.characters` | 常数 | — | — | ✅ |
| **按次**（mediakit） | `constant:1` | 常数 | — | — | ✅ |
| **文本 / LLM** | `usage.p` | 常数 | `c` / `cr` / `cc` | — | ❌ **本期不做** |

> **文本模型本期不纳入计费。** 结构（`dims` / `usageSemantic`）**保留在 Schema 里但不启用**，
> 将来要计费时只需配 catalog + 启用归一化，**不用改契约、不用改引擎骨架**。
>
> 连带影响：`dims` / `usageSemantic` / `TextPricingCalculator` 的**实现与测试均推迟**，
> 但 **JSON Schema 字段保留**（加字段成本极低，删了以后再加要改契约）。

**没有任何模态特殊分支。**

#### 2.5.4 usage 归一化：`usageSemantic`（**本期不启用，为文本模型预留**）

> **本期文本模型不纳入计费**，所以这一节**只需 Schema 保留字段，不需实现**。
> 保留它是因为「重复计费」是文本计费最难发现的坑，将来一定会遇到——
> 现在写清楚，将来只加实现不加契约。

**上游 usage 的分类是重叠的**——这是文本计费「准确」最大的坑：

```
OpenAI 格式：prompt_tokens  **已包含** cached_tokens / image_tokens
Claude 格式：input_tokens   **不含** cache read / cache creation
```

若配置同时写了 `usage.p` 和 `usage.cr`，而上游是 OpenAI 格式：

```
❌ 错：p × 2 + cr × 0.1            ← cached 被收了两次
✅ 对：(p − cr) × 2 + cr × 0.1
```

**一个字段声明语义**（对齐 new-api 的 `IsClaudeUsageSemantic` 布尔）：

| 值 | 含义 | 归一化 |
|---|---|---|
| `"openai"`（默认） | 父类**含**子类 | `p_text = p − Σ(在 dims 里配了倍率的子类)` |
| `"claude"` | 父类是**纯文本**，子类独立 | 不减 |

**只减「在 `dims` 里配了倍率的子类」**——没配的留在父类里按父类价收，**不漏不重**。
这正是 new-api `usedVars` 那段逻辑在做的事。

**只有文本 / 多模态需要这个字段**；图片、视频、音频的计量维度本来互斥。

#### 2.5.5 折扣不在 catalog 里

折扣拆成两张**独立的 live 表**：

| | 表 | 章节 |
|---|---|---|
| 会员等级折扣（长期契约） | `billing_member_discounts` | §2.7 |
| 营销活动折扣（临时活动） | `billing_promotions` | §2.6 |

**叠加策略**留在 catalog 的 `discountPolicy`：

```
最终系数 = 会员折扣（同等级命中多条取最优）
         × 营销折扣（多活动命中取最优，活动之间不叠加）
         × 底线：max(最终系数, floorFactorBp)
```

| 规则 | 说明 |
|---|---|
| **会员内部取最优** | `pro 全局 95 折` 与 `pro 视频 8 折` 不叠加，取 8 折 |
| **营销内部取最优** | 同时命中 3 个活动，取折扣最大的那个（**不叠加**，否则会叠出离谱折扣） |
| **会员 × 营销** | 由 `stackMode` 控制：`multiply`（默认，会员再享活动）· `best`（两者取优） |
| **有底线** | `floorFactorBp: 3000` → 最低不低过 3 折，防配错亏本 |

**可解释**：命中结果写进定价快照的 `appliedDiscounts`，
用户问「为什么这个价」能逐条列出（见 §2.5.5）。

#### 2.5.6 判定时机与冻结

```
用户 21:58 提交（活动 22:00 开始）→ 原价
用户 22:01 提交（活动已开始）    → 7 折
两个任务都可能 22:05 才结算。
```

**以 `Hold` 时刻为准**，命中结果**冻结进 job 的定价快照**：

```json
{
  "catalogVersion": 42,
  "unitPriceMc": 3332,
  "appliedDiscounts": [
    { "source": "member",    "id": 17,  "discountBp": 8000 },
    { "source": "promotion", "id": 203, "code": "NIGHT_OCT", "discountBp": 7000 }
  ],
  "finalFactorBp": 5600,
  "finalCredits": 19
}
```

结算时**只按快照复现，不重查 live 表**。

> 否则：提交时看到 7 折、结算时活动结束变原价——**用户看到的价格变了**，
> 这是最不可接受的体验。
>
> **快照冻结的是「结果」而不是「规则」**——这也是 §2.6/§2.7 的 live 表
> **不需要版本化**的原因：活动改了折扣、停了活动，都不影响已提交任务。

### 2.6 billing_promotions（营销活动 — 独立表）

**营销活动不进 catalog。** 变更频率、生命周期、回滚粒度三者都不同：

| | 基础计价（catalog） | 营销活动 |
|---|---|---|
| 变更频率 | 月 / 季度 | **每天** |
| 变更者 | 定价负责人 | **运营** |
| 回滚粒度 | 整体（整份 catalog） | **单条活动** |
| 生命周期 | 版本化（有历史） | 起止时间 + 启停开关 |

**混在一起的直接后果**：运营每建一个活动就要发布一个新 catalog 版本 →
**版本号爆炸、停一条活动要发整版、权限分不开**。

```sql
CREATE TABLE billing_promotions (
  id               BIGINT       NOT NULL AUTO_INCREMENT,
  code             VARCHAR(64)  NOT NULL,      -- 活动标识（审计/排查用）
  name             VARCHAR(128) NOT NULL,      -- 活动名称（前端展示）
  discount_bp      INT          NOT NULL,      -- ★ 折扣，万分比：7000 = 7 折

  model_ids        JSON         NOT NULL,      -- ★ 营销的模型集合 ["seedance-*","seedream-4.0"]
  task_types       JSON         NULL,          -- 可选，NULL = 全部任务类型

  tier_scope       JSON         NULL,          -- ★ 适用用户等级 ["pro","max"]，NULL = 不限

  start_at         DATETIME     NOT NULL,      -- ★ 起始时间
  end_at           DATETIME     NOT NULL,      -- ★ 结束时间

  daily_time_start TIME         NULL,          -- 每日时段（可空 = 全天，支持「夜间折扣」）
  daily_time_end   TIME         NULL,
  days_of_week     JSON         NULL,          -- [1..7]，NULL = 每天
  tz               VARCHAR(64)  NOT NULL DEFAULT 'Asia/Shanghai',

  status           VARCHAR(16)  NOT NULL,      -- ★ draft | enabled | disabled | expired

  priority         INT          NOT NULL DEFAULT 0,
  created_by       VARCHAR(64)  NOT NULL,
  gmt_create       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  gmt_modified     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  version          INT          NOT NULL DEFAULT 0,

  PRIMARY KEY (id),
  UNIQUE KEY uk_promo__code (code),
  KEY idx_promo__active (status, start_at, end_at)
) ENGINE=InnoDB;
```

**字段与需求的对应**：

| 需求 | 字段 |
|---|---|
| 营销的模型集合 | `model_ids`（支持 `*` 与 `seedance-*` 通配） |
| 折扣 | `discount_bp`（万分比整数，零浮点） |
| 起始时间 | `start_at` / `end_at` |
| 启用状态 | `status`（四态） |
| 适用用户等级 | `tier_scope`（NULL = 不限） |

**`status` 四态**：

| 值 | 含义 | 谁改 |
|---|---|---|
| `draft` | 草稿（运营还没启用） | 运营 |
| `enabled` | 进行中 | 运营 |
| `disabled` | 运营手动停 | 运营 |
| `expired` | 已过 `end_at` | 定时任务刷；查询时也会按时间兜底判定 |

**命中条件（全部满足）**：`status = enabled` **且** `now ∈ [start_at, end_at)`
**且** `now` 落在 `days_of_week` / `daily_time_*` 内（为空则不限）
**且** `model_id` 命中 `model_ids` **且** `task_type` 命中 `task_types`
**且** 用户等级命中 `tier_scope`（为空则不限）。

**多个活动同时命中 → 取折扣最大的一个，不叠加。**
叠加会出离谱折扣（3 个 7 折 = 34 折），且用户算不清。

> **`tz` 必填**，默认 `Asia/Shanghai`——对齐 [ADR-0111](../adr/0111-datetime-caliber-beijing-wall-clock.md)
> 的北京时间口径。**不写时区，跨零点时段必然算错。**

> **本表是 live 表，不版本化。** 因为 job 提交时把命中的折扣**冻结进定价快照**（§2.5.5），
> 结算只按快照走。活动改折扣、停活动，都不影响已提交任务。

### 2.7 billing_member_discounts（会员等级折扣 — 独立表）

## 3. 账本分录总表 ★

**每个业务动作产生的逐笔分录。实现时逐行对照。**

| # | 业务动作 | 幂等键 | 分录 |
|---|---|---|---|
| 1 | 充值到账（本金） | `recharge:{orderNo}` | 借 `cost` 1500 / 贷 `wallet` 1500 |
| 2 | 充值赠送 | `recharge:{orderNo}:bonus` | 借 `cost` 200 / 贷 `wallet` 200 |
| 3 | 注册 / 每日 / 邀请 / 兑换 / 会员赠送 | `grant:{key}` | 借 `cost` N / 贷 `wallet` N |
| 4 | 运营补偿 | `grant:{ticketNo}` | 借 `cost` N / 贷 `wallet` N |
| 5 | **提交预扣** | `hold:{commandId}` | 借 `wallet` N / 贷 `frozen` N |
| 6 | **结算**（实际 < 预扣） | `settle:{jobId}` | 借 `frozen` N / 贷 `wallet` (N−A) ＋ 贷 `revenue`\|`cost` A |
| 7 | **结算**（实际 = 预扣） | `settle:{jobId}` | 借 `frozen` N / 贷 `revenue`\|`cost` N |
| 8 | **结算**（实际 > 预扣） | `settle:{jobId}` | 借 `frozen` N ＋ 借 `receivable` (A−N) / 贷 `revenue` A |
| 9 | **全额返还**（失败） | `refund:{jobId}` | 借 `frozen` N / 贷 `wallet` N |
| 10 | 批次过期 | `expire:{lotId}` | 借 `wallet` R / 贷 `cost` R |
| 11 | 充值退款 | `refund:{orderNo}` | 借 `wallet` R / 贷 `cost` R |

> **第 6/7 条的 `revenue` vs `cost` 选择**：消耗的批次是 `purchased` → `revenue`（收入确认）；
> 是赠送类批次 → `cost`（成本确认）。**按批次来源逐笔判定**，不能整单一个科目。

> ⚠️ **第 2 条（充值赠送）的键已改口径**（2026-09-28）：不再是 `recharge:{orderNo}:bonus`，
> 而是 **`bonus:tier:{userId}:{tierId}`**（批次与账本同用这一把）。
> 原因：首购加赠的经营口径定为「**每档首次**」——判据是「这个用户在这个档位上有没有发过赠送」，
> **不是**「这一笔订单发过没有」。而幂等键恰好是这条判据唯一可靠的落点：
> 下单那一刻可能同时存在两笔同档位未支付单，两笔都会自认首单；
> 交给 `uk_lots__grant_key` 唯一索引原子裁决「谁先到谁赢」最省事，也绕不过去。
> 副作用要说清楚：**同一档位的第二笔不再发赠送**（这正是想要的）；
> 而「重放第一笔」会撞回同一个键（409）——调用方必须靠 billing 回带的 `existingBizId`
> 区分「是我自己发的」与「别人先占了」，**不能只按「撞没撞键」下结论**。

> **第 10 条的 R**：过期时该批次的 `remaining − frozen`（冻结中的部分不能算过期）。

**自检查询**（§10 层次①）：

```
对每个 user_id：
  Σ debit(wallet) − Σ credit(wallet)   应等于   Σ lots.remaining
不等 → 按 balance_after 断裂点定位到具体分录
```

## 4. 核心算法

### 4.1 扣减顺序（三级 tie-break）

```
ORDER BY
  (expires_at IS NULL),      -- ① 永久排最后
  expires_at ASC,            -- ① 先过期先扣
  source_priority ASC,       -- ② 同到期时间按来源
  id ASC                     -- ③ 先获得的先扣
```

**source 优先级**（数值小者优先）：

```
compensation(10) > bonus(20) > gift(30) > daily(40)
  > invite(50) = register(50) > redeem(60) > subscription(70) > purchased(80)
```

**先消耗平台赠送的，后消耗用户付费的。**

> 第 ① 条在「赠送有期、购买永久」的场景下**自动实现「先花送的」**（赠送的先过期）。
> 第 ② 条只处理有效期相同（尤其都是永久）时的退化情况——**必须显式定，不能靠默认顺序**。

### 4.2 预扣分配算法

`billing-svc` 是 Java（ADR-0116），以下为**可直接实现的 Java 形态**。

```java
@Service
public class HoldService {

    private final CreditLotRepository lotRepo;
    private final LedgerRepository ledgerRepo;
    private final ReservationRepository reservationRepo;
    private final UserTransactionRepository userTxRepo;

    /**
     * 预扣。幂等键 {@code hold:{commandId}}。
     * 余额不足抛 {@link InsufficientCreditsException}（映射 HTTP 402），不创建 job。
     */
    @Transactional
    public HoldResult hold(long userId, String commandId, long jobId,
                           long amount, int catalogVersion, String title) {

        // ── 幂等：唯一索引 uk_ledger__idem 兜底，重复请求返回首次结果
        Optional<LedgerEntry> dup = ledgerRepo.findByIdempotencyKey("hold:" + commandId);
        if (dup.isPresent()) {
            return reservationRepo.loadByJobId(jobId).toHoldResult();
        }

        // ── 锁该用户全部有效批次（§4.1 的顺序即 SQL 的 ORDER BY）
        List<CreditLot> lots = lotRepo.lockActiveLots(userId);
        // SELECT id, remaining, frozen, expires_at
        //   FROM billing_credit_lots
        //  WHERE user_id = ? AND (expires_at IS NULL OR expires_at > NOW())
        //  ORDER BY (expires_at IS NULL), expires_at, source_priority, id
        //    FOR UPDATE

        long available = lots.stream()
                .mapToLong(l -> l.remaining() - l.frozen())
                .sum();
        if (available < amount) {
            throw new InsufficientCreditsException(available, amount);
        }

        long rest = amount;
        List<Allocation> allocations = new ArrayList<>();
        for (CreditLot lot : lots) {
            if (rest == 0) break;
            long take = Math.min(lot.remaining() - lot.frozen(), rest);
            if (take <= 0) continue;
            lotRepo.addFrozen(lot.id(), take);          // UPDATE ... SET frozen = frozen + ?
            allocations.add(new Allocation(lot.id(), take));
            rest -= take;
        }

        reservationRepo.insert(new CostReservation(
                jobId, userId, amount, catalogVersion,
                ReservationStatus.HELD, allocations));

        // 复式分录：借 wallet / 贷 frozen（§3 分录 5）
        ledgerRepo.insertBalanced(
                LedgerEntry.debit (userId, Account.WALLET, amount, BizType.HOLD,
                                   String.valueOf(jobId), "hold:" + commandId),
                LedgerEntry.credit(userId, Account.FROZEN, amount, BizType.HOLD,
                                   String.valueOf(jobId), "hold:" + commandId));

        userTxRepo.insert(new UserTransaction(
                userId, Direction.OUT, TxType.CONSUME, jobId, title,
                amount,      // amount（预扣时先等于 reserved）
                amount,      // reservedAmount
                TxStatus.PENDING, catalogVersion));

        return new HoldResult(amount, catalogVersion);
    }
}

public record Allocation(long lotId, long take) {}

public record HoldResult(long reservedCredits, int catalogVersion) {}
```

> **`allocations` 必须落库。** 结算与返还时按**同一份分配明细**解冻与扣减，
> 否则会扣错批次（尤其当期间有新批次插入或旧批次过期时）。

### 4.3 结算算法

```java
@Service
public class SettleService {

    /** 结算。幂等键 {@code settle:{jobId}}。 */
    @Transactional
    public void settle(long jobId, long actualCredits) {

        if (ledgerRepo.existsByIdempotencyKey("settle:" + jobId)) return;

        CostReservation r = reservationRepo.lockByJobId(jobId);   // SELECT ... FOR UPDATE
        if (r == null || r.status() != ReservationStatus.HELD) return;  // 已结算 / 已返还

        GenerationJob job = jobRepo.find(jobId);
        if (r.catalogVersion() != job.catalogVersion()) {                 // 防御
            throw new CatalogVersionMismatchException(r.catalogVersion(), job.catalogVersion());
        }

        // ── 按 hold 时的同一份 allocations 分配实际金额（顺序一致）
        List<Settlement> settled = allocateOver(r.allocations(), actualCredits);
        for (Settlement s : settled) {
            lotRepo.settle(s.lotId(), s.frozenTake(), s.actualTake());
            // UPDATE billing_credit_lots
            //    SET frozen = frozen - ?, remaining = remaining - ?, version = version + 1
            //  WHERE id = ?
        }

        // ── 复式分录（§3 分录 6/7/8）
        long refund = r.reservedCredits() - actualCredits;
        List<Pair<LedgerEntry, LedgerEntry>> entries = new ArrayList<>();
        LedgerEntry frozenDebit = LedgerEntry.debit(job.userId(), Account.FROZEN,
                r.reservedCredits(), BizType.SETTLE, String.valueOf(jobId), "settle:" + jobId);
        LedgerEntry revenueCredit = LedgerEntry.credit(job.userId(),
                accountForSource(settled),        // purchased → REVENUE；赠送类 → COST
                actualCredits, BizType.SETTLE, String.valueOf(jobId), "settle:" + jobId);
        entries.add(Pair.of(frozenDebit, revenueCredit));

        if (refund > 0) {                         // 实际 < 预扣：解冻差额回钱包
            entries.add(Pair.of(
                    LedgerEntry.debit (job.userId(), Account.FROZEN, refund, BizType.SETTLE,
                                       String.valueOf(jobId), "settle:{jobId}:refund"),
                    LedgerEntry.credit(job.userId(), Account.WALLET, refund, BizType.SETTLE,
                                       String.valueOf(jobId), "settle:{jobId}:refund")));
        } else if (refund < 0) {                  // 实际 > 预扣：理论不该发生
            long gap = -refund;
            entries.add(Pair.of(
                    LedgerEntry.debit (job.userId(), Account.RECEIVABLE, gap, BizType.SETTLE,
                                       String.valueOf(jobId), "settle:{jobId}:over"),
                    LedgerEntry.credit(job.userId(), accountForSource(settled), gap, BizType.SETTLE,
                                       String.valueOf(jobId), "settle:{jobId}:over")));
            alerting.warn("hold 算漏维度", Map.of("jobId", jobId, "gap", gap));   // ★ 告警
        }
        ledgerRepo.insertAll(entries);

        reservationRepo.markSettled(jobId, actualCredits);
        userTxRepo.markDone(jobId, actualCredits);   // ★ 同一行，不新建
        // UPDATE billing_user_transactions
        //    SET amount = ?, status = 'done', gmt_settled = NOW(), version = version + 1
        //  WHERE biz_id = ? AND type = 'consume'

        cache.invalidateBalance(job.userId());
    }
}

public record Settlement(long lotId, long frozenTake, long actualTake) {}
```

#### 4.3.1 actualCredits 由「成功的 slot 数」决定

| job.status | actualCredits |
|---|---|
| `succeeded` | N 个 slot 全额 |
| `partially_succeeded` | **M 个成功 slot 之和** |
| `failed` | 0 → 走 refund 而非 settle |
| `cancelled`（`provider_task_id IS NULL`） | 0 |
| `cancelled`（已派发） | 按 catalog 的 `refundPolicy` 配置，**默认按比例退** |

**按 slot 计费而非按 job** —— 这是 `partially_succeeded` 能正确结算的前提，
也是拆镜头（fan-out）公平收费的前提。

### 4.4 返还算法

```java
@Service
public class RefundService {

    /** 全额返还。幂等键 {@code refund:{jobId}}。 */
    @Transactional
    public void refund(long jobId, String reason) {

        if (ledgerRepo.existsByIdempotencyKey("refund:" + jobId)) return;

        CostReservation r = reservationRepo.lockByJobId(jobId);   // SELECT ... FOR UPDATE
        if (r == null || r.status() != ReservationStatus.HELD) return;

        // ── 解冻即可，remaining 不动 —— 批次原封不动（含有效期）
        for (Allocation a : r.allocations()) {
            lotRepo.subFrozen(a.lotId(), a.take());
            // UPDATE billing_credit_lots SET frozen = frozen - ?, version = version + 1 WHERE id = ?
        }

        // ── 复式分录（§3 分录 9）
        ledgerRepo.insertBalanced(
                LedgerEntry.debit (r.userId(), Account.FROZEN, r.reservedCredits(),
                                   BizType.REFUND, String.valueOf(jobId), "refund:" + jobId),
                LedgerEntry.credit(r.userId(), Account.WALLET, r.reservedCredits(),
                                   BizType.REFUND, String.valueOf(jobId), "refund:" + jobId));

        reservationRepo.markReleased(jobId, reason);
        userTxRepo.markDone(jobId, 0L);          // ★ 同一行，amount=0
        cache.invalidateBalance(r.userId());
    }
}
```

**返还只更新原行，不新建流水行**——用户看到「本次未消耗」，看不到「扣了又退」。
**`remaining` 与批次的 `expires_at` 都不变**——不会凭空获得一次有效期重置。

### 4.5 定价计算

#### 4.5.1 spec_key 规范化（强制）

```java
/** 维度名与值统一 trim + lowercase，按键名排序，用 | 连接。 */
public static String normalize(Map<String, String> specs) {
    return specs.entrySet().stream()
            .map(e -> e.getKey().trim().toLowerCase(Locale.ROOT)
                    + "=" + e.getValue().trim().toLowerCase(Locale.ROOT))
            .sorted()
            .collect(Collectors.joining("|"));
}
// {"Size":"2K", "duration":"5"}  →  "duration=5|size=2k"
```

**在 catalog 加载时对 `unitPrice.table` 的键做一次性 normalize**（预计算成
`Map<String, Long>`），运行时**直接查**，不再每次重算字符串——
既省 CPU，也保证「写入与查询用同一份规范化结果」。

**所有写入与查询都必须经过 `normalize`。**
这是「seedream 矩阵大小写不匹配导致空表」bug 的根治手段。

**`unitPrice.table` 的键、以及 `terms[].unitPrice.by` 声明的轴，
在 catalog 加载时统一 normalize**——不给调用方写错的机会。

#### 4.5.2 两个入口

```java
long holdCredits(PricingRequest req);    // 预扣
long actualCredits(UsageReport usage);   // 结算
```

**预扣不是无脑取上界**：

| 请求 | 预扣 |
|---|---|
| 规格全确定（`duration=5` · `size=2k` · `n=1`） | **精确价**（差额通常为 0） |
| 有不确定维度（智能时长 `duration = -1`） | 该维度取**模型允许的最大值** |

> **不照搬 new-api 的「差额常态」**——它估算是被逼的（MediaKit 入参是 URL，
> 提交时拿不到时长，只能用一个默认分钟数硬估）。视频规格在提交时已经确定。

#### 4.5.3 计算管线（全程整数，出口只四舍五入一次）

**骨架由模板方法钉死**（`AbstractPricingCalculator.compute()`，§4.6.2），
调用方只看到一行 `compute`：

```java
@Service
public class PricingEngine {

    private final PricingCatalogHolder catalog;          // volatile 原子替换，读路径无锁
    private final AbstractPricingCalculator calculator;  // 模板方法骨架

    /** @return 整数积分。出口唯一一次舍入。 */
    public long compute(PricingRequest req, UsageLine usage, Instant submitAt) {
        CompiledRule rule = catalog.lookup(req.modelId(), req.taskType());
        if (rule == null) {
            throw new UnpriceableException(req.modelId(), req.taskType());   // 拒绝，不降级为 0
        }
        return calculator.compute(new PricingContext(rule, req, usage, submitAt));
    }
}
```

**骨架内部七步**（完整实现见 §4.6.2）：

```java
public final long compute(PricingContext ctx) {
    UsageLine usage = normalize(ctx);                                     // ① 归一化（文本覆写）
    long units      = aggregateUnits(ctx, usage);                          // ② 等效数量
    long mc         = units * resolveBasePrice(ctx) / ctx.rule().unitDenominator();  // ③ × 基准单价
    mc              = applyMultipliers(ctx, usage, mc);                    // ④ × 整单倍率
    mc              = clamp(ctx, mc);                                      // ⑤ 上下限
    mc              = discountResolver.apply(ctx, mc);                     // ⑥ 折扣
    return rounding.round(ctx, mc);                                        // ⑦ ★ 出口唯一舍入
}
```

- **② 等效数量** = `quantity(baseUnit) + Σ(quantity(dim) × 万分比倍率)`
- **③ `basePrice` 可以是常数或按轴查表**（`BasePriceResolver` 策略）
- **⑥ 命中的折扣明细写进定价快照**（`appliedDiscounts`，可解释、可审计）

**全程 `long` 整数运算，零浮点。⑦ 之后不可能再有不一致。**

#### 4.5.4 折扣解析（查两张独立表）

折扣走**模板方法基类 + 多实现**（`AbstractDiscountProvider`，§4.6.3），
骨架固定为「拉候选 → 过滤 → 取最优」：

```java
@Service
public class DiscountResolver {

    private final List<DiscountProvider> providers;   // Spring 注入全部实现
    private final DiscountStackPolicy stackPolicy;    // 策略：multiply / best
    private final int floorFactorBp;

    public long apply(PricingContext ctx, long mc) {
        List<AppliedDiscount> applied = providers.stream()
                .map(p -> p.resolve(ctx.toDiscountContext()))
                .flatMap(Optional::stream)
                .toList();                                        // 每个来源各取最优（内部不叠加）

        int bp = stackPolicy.combine(applied);                    // 策略：会员 × 营销
        bp = Math.max(bp, floorFactorBp);                         // 底线，防配错亏本
        ctx.recordApplied(applied);                               // 写进定价快照
        return mc * bp / 10_000L;
    }
}
```

**两个 Provider**（各自的模板方法实现见 §4.6.3）：

| Provider | `loadCandidates` | 覆写的 `matchesScope` |
|---|---|---|
| `MemberDiscountProvider` | 查 `billing_member_discounts`（按等级） | — |
| `PromotionDiscountProvider` | 查 `billing_promotions`（按时间窗） | **时段命中**（周几 + 跨天时段 + tz） |

**两张表的查询都走 Caffeine 短 TTL 缓存**（30–60s）——
活动变更频率是"每天几条"，缓存后读路径几乎零成本。
活动保存/启停时**主动失效缓存**。

#### 4.5.5 发布前校验（三层，缺一不可）

| 层 | 校验什么 | 失败 |
|---|---|---|
| **① 结构** | JSON Schema：字段类型 / 必填 / 枚举 / 数值范围 | 拒绝保存 |
| **② 业务** | 轴空间完整性 · `model_id` 存在 · 折扣优先级无歧义 · `tz` 合法 | 拒绝发布 |
| **③ dry-run** | 用样例请求集跑一遍，任何组合算不出价 | 拒绝发布 |

**② 轴空间完整性**（治「配一半」的根）：

```java
/** 发布前校验：每个 (model, taskType) 的定价轴组合必须被 unitPrice.table 全覆盖。 */
void validateAxisCoverage(CatalogDocument doc, CapabilityRepository caps) {
    for (var modelEntry : doc.models().entrySet()) {
        String modelId = modelEntry.getKey();
        for (var taskEntry : modelEntry.getValue().entrySet()) {
            String taskType = taskEntry.getKey();
            PricingRule rule = taskEntry.getValue();

            // 期望键 = 各定价轴的取值集合经 normalize 后的笛卡尔积
            Set<String> expected = Set.of("");
            for (Term t : rule.terms()) {
                Set<String> values = caps.valuesFor(modelId, taskType, t.unitPrice().by());
                expected = cartesian(expected, values, PricingKeys::normalize);
            }

            Set<String> missing = Sets.difference(expected, rule.allTableKeys());
            if (!missing.isEmpty()) {
                throw new CatalogValidationException(
                        "轴空间未全覆盖：%s/%s 缺 %s".formatted(modelId, taskType, missing));
            }
        }
    }
}
```

`by` 声明的轴取值从 `generation_model_capabilities` 取 →
**同一份规格语义只有一个事实来源**。
这是「seedream 矩阵配一半」「sizes 小写 `1k` vs 大写 `1K` 空表」两个 bug 的共同根治点。

**③ dry-run 的样例集**：

每个 `(model, task_type)` 准备一组标准请求（覆盖全部轴组合的下界与上界），
发布时全部跑一遍，与 `expect` 比对：

```json

  { "model": "seedance-2.5", "task": "text2video",
    "specs": {"size":"1792x1024"}, "usage": {"seconds": 5}, "expect": 17 }

```

#### 4.5.6 折扣生效性校验（在**活动 / 会员折扣保存时**执行）

折扣是独立表，所以这条校验**不在 catalog 发布流程里**，而是挂在
`billing_promotions` / `billing_member_discounts` 的**保存与启用**上。

```java
/**
 * 让利不足 1 积分的折扣会静默失效（见 §1.2），必须在配置期发现。
 *
 * @param discountBp      待校验折扣（万分比）
 * @param modelIds        该规则的模型集合（支持通配）
 * @param taskTypes       任务类型集合，null = 全部
 * @param becomingActive  本次操作是否会让规则**立即生效**
 *                        （启用活动 / 保存已启用活动 → true；存草稿 → false）
 */
List<ValidationIssue> validateEffectiveness(int discountBp,
                                            List<String> modelIds,
                                            List<String> taskTypes,
                                            boolean becomingActive) {
    List<Long> prices = pricingEngine.pricesCoveredBy(modelIds, taskTypes);
    if (prices.isEmpty()) {
        return List.of(ValidationIssue.warn("未匹配到任何定价，该规则不会生效"));
    }

    // 折后价经与生产**完全相同**的舍入后，仍等于原价 → 该档位上无效
    List<Long> ineffective = prices.stream()
            .filter(p -> p > 0)
            .filter(p -> roundHalfUp(p * discountBp / 10_000L) == roundHalfUp(p))
            .toList();

    if (ineffective.size() == prices.size()) {
        String msg = "折扣在全部目标上无实际效果（让利不足 0.5 积分），"
                + "折后价四舍五入后仍等于原价：" + ineffective;
        // 会立即生效的 → 拒绝；存草稿 → 允许但红字提示
        return List.of(becomingActive ? ValidationIssue.error(msg) : ValidationIssue.warn(msg));
    }
    if (!ineffective.isEmpty()) {
        return List.of(ValidationIssue.warn(
                "在 %d/%d 个定价档位上无实际效果：%s"
                        .formatted(ineffective.size(), prices.size(), ineffective)));
    }
    return List.of();
}

/** 必须与引擎出口的舍入方式**逐字一致**（§1.1）。 */
private static long roundHalfUp(long mc) { return (mc + 500L) / 1000L; }
```

> **校验里的舍入函数必须与生产引擎逐字一致**——否则会出现
> 「校验说生效、线上算出来没生效」这种最难查的偏差。

**挂在两处**：

| 操作 | 行为 |
|---|---|
| 保存营销活动 / 会员折扣（草稿或未启用） | `becomingActive = false` → **WARN**，管理端红字提示，允许保存 |
| **启用**活动 / 保存**已启用**的活动 | `becomingActive = true` → **ERROR**，拒绝 |

> 这条把 §1.2 的数学必然**变成配置期可发现的问题**，
> 而不是上线后收到「会员怎么没便宜」的投诉。

#### 4.5.7 发布流程（catalog 与折扣分开）

**两条独立的流程**——这是把它们拆表的直接收益：

```
【基础计价 · catalog】低频，走完整发布流程

① 管理端编辑（结构化表单 → 生成 JSON）
     ↓ ② 保存为 draft（JSON Schema 结构校验）
     ↓ ③ 业务校验（轴空间完整性 / model_id 存在）
     ↓ ④ dry-run（样例集跑一遍，算不出价即拒）
     ↓ ⑤ diff 预览：「seedream 2k 图片：5 → 6 积分」+ 影响面（近 7 天受影响调用数）
     ↓ ⑥ 指定 effective_from（可未来生效）
     ↓ ⑦ 发布：新 catalog_version，旧版本 retired，写 billing_cost_publish_logs
     ↓ ⑧ MQ 广播 pricing.catalog.activated { version, hash }
     ↓ ⑨ 各服务拉取 → 编译 → **原子替换内存索引**

     回滚 = 把旧版本置回 active + 广播。**一条 UPDATE。**


【营销活动 · billing_promotions】高频，常规运营操作

① 运营建活动（表单：模型集合 / 折扣 / 起止时间 / 等级范围 / 可选时段）
     ↓ ② 保存 → 结构校验 + **生效性校验**（§4.5.6，草稿只 WARN）
     ↓ ③ 启用（status: draft → enabled）
     │     启用时若生效性校验为 ERROR → 拒绝
     ↓ ④ 缓存失效（无需 MQ 广播——live 表，各实例短 TTL 缓存自然过期）
     ↓ ⑤ 到点自动生效 / 到点自动过期（定时任务刷 expired）

     停活动 = status 改 disabled。**不碰 catalog，不影响任何其他活动。**


【会员折扣 · billing_member_discounts】低频，定价负责人操作

① 改记录（等级 / 模型模式 / 折扣）
     ↓ ② 生效性校验（同 §4.5.6）
     ↓ ③ 保存即生效（live 表）+ 缓存失效
```

> **不再需要"每次建活动发一个 catalog 版本"**——这正是拆表的理由。
> 已提交的 job 靠**定价快照**（§2.5.5）隔离，活动怎么改都不影响它们。

#### 4.5.8 运行时消费

```
billing-svc 启动 / 收到激活广播
   ↓ 拉 active catalog（JSON 文档）
   ↓ normalize 全部 spec_key 与 table 键
   ↓ **校验所有 key 都是封闭枚举**：
        baseUnit / dims / multipliers 的 key 必须在 QuantityRegistry 里
        → 拼错（如 "usage.tokens"）在**加载期直接拒绝**，不进内存
   ↓ 编译成内存索引：Map<modelId, Map<taskType, CompiledRule>>
       CompiledRule = { usageSemantic, baseUnit, basePrice, dims,
                        multipliers, unitDenominator, rounding, min/max }
   ↓ 原子替换（volatile 引用，读路径无锁）
   ↓ 失败 → **拒绝加载，保持旧版本，告警**（fail fast，绝不降级为 0）
```

**折扣走独立的短 TTL 缓存**（Caffeine，30–60s）：
`billing_promotions` / `billing_member_discounts` 的记录量小、变更频率是"每天几条"，
缓存后读路径几乎零成本；活动**保存/启停时主动失效**本地缓存。

- **`business-api` 订阅同一份 catalog**（只读副本）→ 价格预览本地算，0 延迟
- **结算用不到 catalog**——按 job 冻结的定价快照复现即可（§2.5.5）

运营配了活动，用户得知道。billing 提供公开接口：

```
→ [{ "id": "night-owl", "label": "夜间 7 折", "factorBp": 7000,
```

### 4.6 模块设计（设计模式落地）

#### 4.6.1 先讲变化点 —— 不列变化点的设计都是耍流氓

| 变化点 | 频率 | 谁改 | 落点 |
|---|---|---|---|
| 计价公式 | 极低（就一种） | 工程 | 模板方法骨架 |
| **新增 usage 维度** | 中 | 工程 | 策略注册表 |
| **单价形态** | 低 | 工程 | 策略 |
| **新增折扣来源** | **高** | 运营 | 模板方法基类 + 子类 |
| **新增校验规则** | **高** | 工程 | 责任链 |
| 舍入 / 叠加策略 | 低 | 配置 | 策略 |

**设计目标一句话：运营加折扣、工程加校验，都不用改引擎。**

```
pricing/
├─ catalog/          定价目录（加载 / 编译 / 原子替换）
│   CompiledCatalog · CompiledRule · CatalogHolder(volatile) · CatalogLoader
│
├─ engine/           计价引擎
│   AbstractPricingCalculator   ← 模板方法（骨架钉死）
│   ├─ TextPricingCalculator       （覆写 normalize）
│   └─ MediaPricingCalculator      （全用默认）
│   BasePriceResolver           ← 策略（常数 / 按轴查表）
│   QuantityRegistry            ← 策略注册表（usage 维度 → 取值函数）
│   RoundingPolicy              ← 策略（ceil / round / floor）
│
├─ discount/         折扣
│   AbstractDiscountProvider    ← 模板方法（拉候选 → 过滤 → 取最优）
│   ├─ MemberDiscountProvider
│   └─ PromotionDiscountProvider
│   DiscountStackPolicy         ← 策略（multiply / best）
│
└─ validation/       校验
    ValidationHandler           ← 责任链 + 模板方法
    ├─ SchemaHandler · AxisCoverageHandler
    ├─ DryRunHandler · EffectivenessHandler
    └─ ValidationChain（装配）
```

#### 4.6.2 模板方法 · 计价骨架

```java
/**
 * 计价管线骨架。**所有模态共用同一流程，子类不可覆写 compute。**
 *
 * 为什么钉死顺序：计费顺序被某个模态改乱 = 算错钱，且极难发现。
 */
public abstract class AbstractPricingCalculator {

    private final DiscountResolver discountResolver;
    private final RoundingPolicy rounding;

    public final long compute(PricingContext ctx) {
        UsageLine usage = normalize(ctx);                                    // ①
        long units      = aggregateUnits(ctx, usage);                        // ②
        long mc         = units * resolveBasePrice(ctx) / ctx.rule().unitDenominator();  // ③
        mc              = applyMultipliers(ctx, usage, mc);                  // ④
        mc              = clamp(ctx, mc);                                    // ⑤
        mc              = discountResolver.apply(ctx, mc);                   // ⑥
        return rounding.round(ctx, mc);                                      // ⑦
    }

    // ── 钩子：默认实现覆盖 90% 场景，子类只覆写真正需要的
    /** ① 归一化。默认 no-op；文本模型覆写为「减掉被单独定价的子类」。 */
    protected UsageLine normalize(PricingContext ctx) {
        return ctx.usage();
    }

    /** ④ 整单倍率。默认遍历 rule.multipliers()，按维度取倍率连乘。 */
    protected long applyMultipliers(PricingContext ctx, UsageLine u, long mc) {
        for (var e : ctx.rule().multipliers().entrySet()) {
            mc = mc * e.getValue().resolve(ctx, u) / 10_000L;
        }
        return mc;
    }

    /** ⑤ 上下限。默认套 minCredits / maxCredits。 */
    protected long clamp(PricingContext ctx, long mc) {
        var r = ctx.rule();
        if (r.maxCredits() != null) mc = Math.min(mc, r.maxCredits() * 1000L);
        return Math.max(mc, r.minCredits() * 1000L);
    }

    // ── 组合：由策略完成，子类通常不用碰
    private long aggregateUnits(PricingContext ctx, UsageLine u) {
        long units = QuantityRegistry.of(ctx.rule().baseUnit()).applyAsLong(u);
        for (var e : ctx.rule().dims().entrySet()) {
            units += QuantityRegistry.of(e.getKey()).applyAsLong(u) * e.getValue() / 10_000L;
        }
        return units;
    }

    private long resolveBasePrice(PricingContext ctx) {
        return ctx.rule().basePrice().resolve(ctx.specs());   // ← BasePriceResolver 策略
    }
}
```

**只有两个子类**：

```java
/** 文本 / 多模态：上游 usage 有层级包含关系，需归一化。 */
public final class TextPricingCalculator extends AbstractPricingCalculator {
    @Override
    protected UsageLine normalize(PricingContext ctx) {
        return ctx.rule().usageSemantic() == UsageSemantic.OPENAI
                ? UsageNormalizer.subtractPricedSubclasses(ctx.usage(), ctx.rule().dims().keySet())
                : ctx.usage();
    }
}

/** 图片 / 视频 / 音频 / 按次：维度互斥，无需归一化。 */
public final class MediaPricingCalculator extends AbstractPricingCalculator {
    // 全部继承默认实现
}
```

> **`MediaPricingCalculator` 是空类，有意义吗？**
> 有——`compute()` 是 `final`，它**声明了「本模态不做归一化」这个决定**，
> 而不是「忘了做」。将来图片也有层级 usage 时，覆写点就在这里，不用动骨架。

#### 4.6.3 模板方法 + 组合 · 折扣

```java
/**
 * 折扣提供者骨架：**拉候选 → 过滤 → 取最优**。
 * 子类只实现「从哪拉」和「额外的匹配条件」。
 */
public abstract class AbstractDiscountProvider implements DiscountProvider {

    public final Optional<AppliedDiscount> resolve(DiscountContext ctx) {
        return loadCandidates(ctx).stream()
                .filter(DiscountCandidate::isActive)                 // 默认
                .filter(c -> matchesModel(c, ctx.modelId()))         // 默认
                .filter(c -> matchesTask(c, ctx.taskType()))         // 默认
                .filter(c -> matchesScope(c, ctx))                   // ← 子类可覆写
                .min(comparingInt(DiscountCandidate::discountBp));   // 取最优，不叠加
    }

    protected abstract List<DiscountCandidate> loadCandidates(DiscountContext ctx);

    /** 额外的适用范围过滤。默认不限。 */
    protected boolean matchesScope(DiscountCandidate c, DiscountContext ctx) {
        return true;
    }
}
```

```java
/** 会员折扣：等级已在 SQL 过滤，无需额外 scope。 */
@Component
public class MemberDiscountProvider extends AbstractDiscountProvider {
    private final MemberDiscountRepository repo;

    @Override protected List<DiscountCandidate> loadCandidates(DiscountContext ctx) {
        return repo.findEnabledByTier(ctx.tier()).stream()
                .map(MemberDiscountCandidate::from).toList();
    }
}

/** 营销活动：多一层「时段匹配」（周几 + 跨天时段 + tz）。 */
@Component
public class PromotionDiscountProvider extends AbstractDiscountProvider {
    private final PromotionRepository repo;

    @Override protected List<DiscountCandidate> loadCandidates(DiscountContext ctx) {
        return repo.findEnabledInWindow(ctx.submitAt()).stream()
                .map(PromotionCandidate::from).toList();
    }

    @Override protected boolean matchesScope(DiscountCandidate c, DiscountContext ctx) {
        return ((PromotionCandidate) c).hitsTimeWindow(ctx.submitAt());
    }
}
```

> **新增折扣来源（优惠券 / 企业协议价）→ 加一个 `@Component Provider`，
> 引擎、组合器、快照全部不用动。** 这就是「高内聚低耦合」的落点。

#### 4.6.4 策略 · 单价 / 舍入 / 叠加

```java
public sealed interface BasePriceResolver permits ConstantPrice, TablePrice {
    long resolve(Map<String, String> specs);
}

/** 常数单价：文本、按次。 */
public record ConstantPrice(long mc) implements BasePriceResolver {
    @Override public long resolve(Map<String, String> specs) { return mc; }
}

/** 按轴查表：图片按尺寸档、视频按分辨率。表在编译期已 normalize。 */
public record TablePrice(Map<String, Long> table) implements BasePriceResolver {
    @Override public long resolve(Map<String, String> specs) {
        Long v = table.get(PricingKeys.normalizeSubset(specs, table.keySet()));
        if (v == null) throw new UnpriceableSpecException(specs);   // 查不到就拒绝，不降级
        return v;
    }
}

/** 舍入策略。默认 HALF_UP（四舍五入）。 */
public sealed interface RoundingPolicy permits HalfUpRounding, CeilRounding, FloorRounding {
    long round(PricingContext ctx, long mc);
}

/** ★ 默认：四舍五入。中性——有时多得有时少得，用户更容易接受。 */
public record HalfUpRounding() implements RoundingPolicy {
    @Override public long round(PricingContext ctx, long mc) {
        return Math.max(ctx.rule().minCredits(), (mc + 500L) / 1000L);
    }
}

/** 备选：向上取整。偏平台，且让折扣更难生效（§1.2）。 */
public record CeilRounding() implements RoundingPolicy {
    @Override public long round(PricingContext ctx, long mc) {
        return Math.max(ctx.rule().minCredits(), Math.floorDiv(mc + 999L, 1000L));
    }
}
```

#### 4.6.5 责任链 · 校验

```java
/** 校验链节点。模板方法钉死「本级 → 致命则中断 → 交给下一级」。 */
public abstract class ValidationHandler {

    private ValidationHandler next;

    public ValidationHandler linkWith(ValidationHandler next) {
        this.next = next;
        return next;
    }

    public final ValidationReport handle(ValidationContext ctx) {
        List<Issue> issues = validate(ctx);

        if (issues.stream().anyMatch(Issue::isFatal)) {
            return ValidationReport.of(issues);                       // 致命 → 中断，不往下走
        }
        ValidationReport downstream = (next == null)
                ? ValidationReport.empty()
                : next.handle(ctx);
        return downstream.merge(issues);
    }

    protected abstract List<Issue> validate(ValidationContext ctx);
}
```

**四个节点，各自独立**：

```java
@Component class SchemaHandler        extends ValidationHandler { /* JSON Schema 结构 */ }
@Component class AxisCoverageHandler  extends ValidationHandler { /* 轴空间全覆盖 */ }
@Component class DryRunHandler        extends ValidationHandler { /* 样例集试算 */ }
@Component class EffectivenessHandler extends ValidationHandler { /* 折扣让利 ≥ 1 积分 */ }
```

**装配（Spring 收集全部实现，按 `@Order` 串链）**：

```java
@Configuration
public class ValidationChainConfig {

    /** catalog 发布链：全四道。 */
    @Bean("catalogValidationChain")
    public ValidationChain catalogChain(List<ValidationHandler> handlers) {
        return ValidationChain.of(handlers);   // 按 @Order 排序后依次 linkWith
    }

    /** 活动保存链：只要结构与生效性两道。 */
    @Bean("promotionValidationChain")
    public ValidationChain promotionChain(SchemaHandler schema, EffectivenessHandler eff) {
        schema.linkWith(eff);
        return new ValidationChain(schema);
    }
}
```

> **新增校验规则 → 加一个 `@Component`，链自动串上。**
> **不同场景用不同链**：catalog 发布走全四道，活动保存走两道。

#### 4.6.6 扩展点与边界（三档改动）

**「引擎核心」= `AbstractPricingCalculator.compute()` 的那七行。**
它是唯一「所有模态共用、改了影响全部收入」的东西。

```
🟢 改配置                → 运营自己做，不发版
🔵 加新类（不改已有代码）  → 工程加文件，**开闭原则**
🔴 改那七行骨架          → 影响全部模态，要走 ADR + 全量回归
```

| 要加什么 | 改什么 | 档位 |
|---|---|---|
| 新模型 / 新价格 | catalog JSON | 🟢 配置 |
| 新的 usage 维度（`usage.videoIn`） | `QuantityRegistry` 加一行 | 🔵 加代码 |
| 新的单价形态 | 加一个 `BasePriceResolver` 实现 | 🔵 加代码 |
| **新的折扣来源**（优惠券 / 企业协议价） | 加一个 `Provider` 子类 | 🔵 加代码 |
| **新的校验规则** | 加一个 `ValidationHandler` 子类 | 🔵 加代码 |
| 新的叠加策略 | 加一个 `DiscountStackPolicy` 实现 | 🔵 加代码 |
| **新增一个模态**（如 3D） | 加一个 `PricingCalculator` 子类 | 🔵 加代码 |
| **改计费步骤顺序**（先打折再封顶） | 改 `compute()` 那七行 | 🔴 **改骨架** |
| **改计费公式**（如加开方） | 改 `compute()` | 🔴 **改骨架** |

**开闭原则下，新增子类 / 新增实现不算「动引擎」** —— 已有代码一行不改。

**边界**：

```
engine/AbstractPricingCalculator.compute()   ★ 🔴 唯一需要 ADR 的地方
engine/*PricingCalculator（子类）              🔵 新增
engine/BasePriceResolver · QuantityRegistry · RoundingPolicy   🔵 扩展点
discount/AbstractDiscountProvider（子类）      🔵 新增
validation/ValidationHandler（子类）           🔵 新增
catalog/CompiledCatalog                       🔵 极少数情况才动（如新增 dims 字段）
```

#### 4.6.7 明确拒绝的模式（避免过度设计）

| ❌ 不做 | 为什么 |
|---|---|
| **责任链做计价管线** | 步骤固定有序、无分支、不可插拔。责任链的价值是「可动态增减的拦截」，这里不需要。**模板方法才对** |
| **解释器 / DSL**（表达式引擎） | 售价自定，不需要复刻上游公式。真要动态逻辑，`dims` / `multipliers` 已够 |
| **每个 usage 字段一个类** | 一个注册表 Map 就够。写 13 个 `PromptTokenQuantitySource` 类是自嗨 |
| **工厂 + 反射 + 注解做插件系统** | 编译期能确定的东西，别拖到运行期 |
| **每张表一个 Repository 接口 + 实现 + DTO + Mapper** | 按需抽象，不是按「三层架构」教条 |

## 7. 各场景计费细则

| 场景 | 预扣 | 结算 | 用户流水 |
|---|---|---|---|
| 视频 | `holdCredits`（规格确定 → 精确） | **按成功 slot 数** | 一行，`pending → done` |
| 视频 fan-out（拆镜头） | **父 job 统一 Hold** | **父 job 统一 Settle** | 一行（父 job） |
| 图片 | 同视频 | 按成功张数 | 一行 |
| 音频 / MediaKit | 提交时**先异步探测时长**再 Hold | 按实际时长 | 一行 |
| **Agent / LLM** | **不 Hold**，只查余额 ≥ 阈值 | **每次调用实时扣 + 累加** | 一行（AgentRun） |

> ⚠️ **Agent / LLM 本期不纳入计费**（文本模型不计费）。
> §7.1 保留为**后续启用时的设计**——届时只需加 catalog 配置 + 启用 `dims` 归一化，
> **不用改契约、不用改引擎骨架**。
| 充值 | — | 回调幂等入账 | 一行（`in`） |
| 会员周期 | — | 定时发放（幂等） | 一行（`in`） |

### 7.1 Agent / LLM 的特殊处理（**本期不启用，为后续预留**）

```
会话开始（AgentRun 创建）
  ├─ 检查 可用余额 >= 阈值（如 10 积分）—— 不通过则拒绝发起
  └─ INSERT billing_user_transactions
       (type='consume', biz_id=agentRunId, amount=0, status='pending')

每次 LLM 调用完成（流式结束时上游回 usage）
  ├─ 幂等键 llm:{agentRunId}:{callId}
  ├─ credits = input×单价 + output×单价 + cached×折扣单价
  ├─ INSERT ledger（借 wallet / 贷 revenue）
  ├─ UPDATE billing_user_transactions
  │    SET amount = amount + credits WHERE biz_id = agentRunId   ← 累加
  └─ 若可用余额 < 阈值 → 中断会话，提示积分不足

会话结束 → UPDATE billing_user_transactions SET status='done'

嵌套工具调用（agent 生成图片 / 视频）
  ├─ 那个 job 有自己的 hold/settle（内部账本照常）
  └─ **用户可见流水归到同一个 agentRunId**（累加到同一行）
```

**为什么不预扣**：会话级 Hold 上限 = `max_context × 最大输出`，
通常是实际消耗的 **5–10 倍**。用户开一个会话就被冻结几百积分，体验极差。

**累加天然幂等**：`callId` + `ledger` 唯一索引保证 MQ 重投不会重复累加。

## 8. 并发与事务

| 约束 | 做法 |
|---|---|
| **争用范围** | **单用户**——锁该用户的有效批次。同一用户并发提交是个位数，业务语义上本就该串行 |
| **事务长度** | 扣费事务 **< 5ms**：若干 UPDATE + 若干 INSERT。**禁止任何慢查询进入这条路径** |
| **加锁顺序** | 恒按 `(expires_at IS NULL), expires_at, source_priority, id` 加锁，**避免死锁** |
| **分片键** | `user_id`——**现在只预留不实现**，到阈值再上中间件 |
| **读路径** | 余额走 Redis 缓存 + **写时失效**；流水走只读副本 |
| **分布式事务** | **禁用**（Seata / 2PC）。跨服务一致性靠 **MQ + 幂等 + 对账** |

## 9. 对账

| 层次 | 频率 | 查什么 | 不平怎么办 |
|---|---|---|---|
| **① 账本自检** | 每日 | `Σ ledger(wallet)` vs `Σ lots.remaining` | 按 `balance_after` 断裂点定位到具体分录 |
| **② 预留兜底** | 每 10 分钟 | `status=held` 且超 2h 未终态的预留 | 查 job 实际状态 → 补 settle / refund |
| **③ 上游对账** | 每日 | new-api 账单 vs `billing_provider_usage` 汇总 | 差异列表，人工核查 |

**② 是必需的不是可选的**：MQ 重投有次数上限（现有 18 次进 DLQ 的配置），
超限后必须有人兜底。billing 扫自己的表，不依赖外部。

**③ 的局限**：若 new-api 只给日/总额（不给按调用明细），只能对**总额**，
按用户归因只能靠自己上报的 usage —— 这是必须接受的。
也正因如此，`billing_provider_usage` 必须记 `upstream_request_id`，否则连抽样核查都做不到。

## 10. 边界与异常清单 ★

| # | 情况 | 处理 |
|---|---|---|
| 1 | 余额不足 | `hold` 返回 402，**不创建 job、不产生任何记录** |
| 2 | `actual > reserved` | 允许扣到 0，差额记 `receivable`，**同时告警**（说明 `holdCredits` 算漏维度） |
| 3 | 结算时 job 尚未终态 | 幂等重投，等下次事件 |
| 4 | 重复结算 / 重复返还 | 幂等键拒绝，返回已存在结果 |
| 5 | 结算与返还同时到达 | `billing_cost_reservations` 的 `FOR UPDATE` 保证只有一个赢 |
| 6 | 跨批次扣减 | 单事务内多行 UPDATE，按固定顺序加锁 |
| 7 | **批次在预扣与结算之间过期** | 预扣时锁定的 `frozen` **不受过期影响**——过期只影响 `remaining − frozen` 的口径。结算仍按 `allocations` 走 |
| 8 | 用户删除 / 封禁 | 不删批次；封禁只拒新请求，**进行中任务照常结算** |
| 9 | 定价版本在提交后被下架 | job 冻结了 `catalog_version`，**按冻结版本结算**，不受下架影响 |
| 10 | 上游调用失败但已产生成本 | 用户侧走 refund（失败不收费）；成本侧记 `billing_provider_usage`，进毛利分析 |
| 11 | 定时任务漏跑（每日赠送） | `grant_key` 幂等 + 登录事件双触发，兜底任务可补 |
| 12 | 充值回调乱序（先退款后到账） | 订单状态机保护，非法状态转移直接拒绝并记录 |
| 13 | 退款时本金已部分消费 | 只退 `purchased` 批次的**剩余部分**，已消费不退 |
| 14 | 积分溢出 | `BIGINT` 上限 9.2×10¹⁸，按 15:1 约合 6×10¹⁷ 元，无实际风险 |
| 15 | 同一 `commandId` 重复提交 | 幂等命中，返回首次的 `holdId`，不重复冻结 |
| 16 | **结算时对应批次被人工调整** | 由 **「禁止直接改批次余量」**（ADR-0115 决策 9）在制度上排除——人工调整只能新建 `compensation` 批次 |
| 17 | 上游产出时长 ≠ 请求时长 | `actual` 按实际上报算，可能小于或大于 `reserved`，走 §3 分录 6/8 |
| 18 | 缓存命中（火山缓存计费） | 缓存读取走**独立计量项**（`quantityFrom: usage.cr`）的单价，反映在 `actual` |
| 19 | **折扣让利不足 1 积分** | §4.5.6 生效性校验挂在**活动保存 / 启用**上（草稿 WARN、启用 ERROR） |
| 20 | **活动在提交与结算之间结束** | 判定以 **`Hold` 时刻**为准（§2.5.5），命中结果**冻结进 job**，结算只复现不重判 |
| 21 | **每日时段跨天**（22:00 → 06:00） | `inWindow` 支持跨天；**`tz` 必填**，默认 `Asia/Shanghai` |
| 22 | **活动改折扣 / 停用** | live 表，已提交 job 按冻结快照走，不受影响 |
| 23 | **catalog 加载失败**（JSON 编译不过） | **拒绝加载，保持旧版本 + 告警**（fail fast），绝不降级为 0 |
| 24 | **多个营销活动同时命中** | 取折扣最大的一个，**不叠加**（否则三个 7 折 = 34 折） |
| 25 | **`end_at` 已过但 `status` 仍是 `enabled`** | 查询时按时间兜底判定；定时任务刷 `expired` 只为让运营界面准确 |
| 26 | **会员折扣与营销折扣同时命中** | 由 `stackMode` 决定：`multiply`（默认）相乘 / `best` 取优；再套 `floorFactorBp` 底线 |
| 27 | **活动 `model_ids` 写了不存在的模型** | 保存时校验模型存在性；不存在的条目忽略并 WARN |
| 28 | **usage 维度拼错**（如 `usage.tokens`） | **加载期拒绝**（§4.5.8）——不进内存、不降级 |
| 29 | **OpenAI 语义下 cached 被重复计费** | `usageSemantic` 归一化（§2.5.4）：只减「在 `dims` 里配了倍率的子类」 |
| 30 | **配了某维度但 worker 不上报** | 该维度恒为 0 → 静默少收。发布校验需比对 worker 契约的上报字段清单 |
| 31 | **`basePrice` 改价与进行中任务** | 按 job 冻结的定价快照结算（§2.5.6），新提交用新价 |

| **活动** | **生效性校验**：构造「5 积分 × 9 折」，草稿 WARN、启用 ERROR |
| **活动** | **启停**：`enabled → disabled` 后新提交不再命中；已提交 job 不受影响 |
| **活动** | **多活动命中取最优**（不叠加）；`tier_scope` 过滤生效 |
| **活动** | **自动过期**：`end_at` 之后新提交不再命中 |
| 对账 | 构造账本与批次不一致的夹具，验证自检能**定位到具体分录** |
| 边界 | §10 清单逐条 |

## 附：与 new-api 机制的差异（易混淆）

| | new-api | 本设计 |
|---|---|---|
| 预扣语义 | **直接扣** `DecreaseUserQuota`（`service/task_billing.go:94-102`） | **冻结** `frozen += x` |
| 结算 | `delta = actual − pre`，正补负退 | `frozen -= x; remaining -= actual` |
| 用户账面 | **总余额**当场变少，事后补回 | **可用余额**变少，**总余额不变** |
| 用户可见 | **2 条**（预扣 + 差额） | **1 条**（同一行 `pending → done`） |
| 预扣精度 | 估算 → 差额常态 | 规格精确 → 差额例外 |
| 谁算价 | 网关自己 | billing-svc（worker 只报用量） |
