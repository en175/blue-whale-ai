## 0. 通用标记

| 符号 | 含义 |
|---|---|
| `█` | **同步阻塞**（在用户等待路径上） |
| `░` | 异步（MQ / 定时任务） |
| `[DB]` | 落库点 |
| `⚡` | 幂等键产生处 |

**两条贯穿全局的规则**：

1. **只有「提交预扣」是同步的** —— 其余全是异步或本地计算
2. **每次落账本都带幂等键** —— 重复执行不会重复扣

## 1. 流程一：登录与会话建立

```
浏览器 ──①手机号+验证码──▶ business-api
                              │
                              ├─② 校验验证码 ─▶ identity-svc
                              │                   └─[DB] bw_verification_codes
                              │◀─ {ok} ───────────┘
                              │
                              ├─③ 建立会话 ───▶ identity-svc
                              │                   └─[Redis] session:{sha256(token)}
                              │◀─ {sessionToken} ─┘
                              │
                              ├─④ 写登录日志 ─▶ identity-svc
                              │                   └─[DB] bw_login_logs
                              │
                              └─⑤ Set-Cookie: bw_session=<不透明令牌>
浏览器 ◀── 200 {user: {id, username, tier}} ─────┘
```

| # | 节点 | 输入 | 做什么 | 输出 | 失败 |
|---|---|---|---|---|---|
| ① | 浏览器 | 手机号 + 验证码 | 组装请求 | `{phone, code, scene:"login"}` | — |
| ② | identity 校验码 | 上面的请求 | 查 `bw_verification_codes`，比对 + 判过期 + 标记已用 | `ok` / `code_invalid` | 返回 401 |
| ③ | identity 建会话 | `user_id` + `tier` | 生成随机令牌，`session:{sha256(token)}` 写 Redis，**7 天滑动 TTL** | `sessionToken` | 503 |
| ④ | identity 记日志 | `user_id` + `ip` + `ua` | 写 `bw_login_logs`（**含失败也在这一步记**） | — | **失败不影响登录**（best-effort） |
| ⑤ | business-api | `sessionToken` | 写 HttpOnly Cookie，返回用户信息 | `Set-Cookie` + `{user}` | — |

**关键设计**

- **令牌是「不透明的」**，不是 JWT —— 校验靠 Redis 查，**但认证在应用层做，不在网关**（架构设计 §5）
- **`tier` 随会话返回** —— billing 算折扣要用，避免每次 Hold 多一跳 RPC（架构设计 §11）
- **登录日志失败不阻断登录** —— 审计是 best-effort，不能因为它挂了用户登不进来
- **没有 `sk-`** —— 旧版会存 new-api 的 `sk-` 进会话，**改造后整个概念消失**

## 2. 流程二：价格预览

```
浏览器 ──①改参数──▶ business-api
                      │
                      └─② 本地算 ─▶ 内存里的 catalog 只读副本
                                      │
                                      ├─ 归一化规格
                                      ├─ 查 basePrice（按轴）
                                      ├─ 套 dims / multipliers
                                      ├─ 查折扣（会员 + 营销，走本地短缓存）
                                      └─ 四舍五入
浏览器 ◀── ③ {credits: 19} ───────────┘
```

| # | 节点 | 输入 | 做什么 | 输出 | 失败 |
|---|---|---|---|---|---|
| ① | 浏览器 | 用户拖动参数（模型/分辨率/时长） | **防抖**后发请求 | `{modelId, taskType, specs}` | — |
| ② | business-api | 上面的请求 | **纯本地计算，零 RPC** | `credits` | 算不出价 → 显示「—」，**不阻断** |
| ③ | 浏览器 | `credits` | 显示「预计消耗 19 积分」 | — | — |

**关键设计**

- **预览不走 RPC** —— 否则用户每拖一次滑杆就打一次 billing。catalog 在 business-api 有**只读副本**（MQ 广播失效）
- **折扣走本地短缓存**（Caffeine 30–60s）—— 活动变更是「每天几条」
- **预览是乐观的** —— 允许与最终不一致（缓存没刷新）。**扣费才是悲观的**（以 billing 为准）
- **算不出价不阻断预览** —— 显示「—」即可；**但提交时会被拒**（P1 告警）

## 3. 流程三：提交生成任务（**核心**）

```
浏览器 ──①提交(commandId)──▶ business-api
                              │
                              ├─② 本地校验 ░
                              │     ├─ 能力矩阵（支持这个规格吗）
                              │     ├─ 素材合规（参考素材过审了吗）
                              │     └─ 并发配额（按会员等级）
                              │
                              ├─③ Hold ⚡hold:{commandId} █──▶ billing-svc
                              │                                 │
                              │                                 ├─ 归一化规格 → normalize
                              │                                 ├─ 查 catalog 编译后的内存索引
                              │                                 ├─ 算等效数量 × 基准单价
                              │                                 ├─ 套 multipliers
                              │                                 ├─ 查折扣（会员 + 营销）
                              │                                 ├─ 上下限 → 四舍五入
                              │                                 ├─[DB] billing_credit_lots（frozen += x）
                              │                                 ├─[DB] billing_ledger_entries（借 wallet / 贷 frozen）
                              │                                 ├─[DB] billing_cost_reservations（allocations）
                              │                                 └─[DB] billing_user_transactions（pending）
                              │◀── {holdId, reservedCredits, catalogVersion} ─┘
                              │
                              ├─④ 写 job + slots ░[DB] generation_jobs / generation_output_slots
                              ├─⑤ 发 MQ ░ generation.submit
                              └─⑥ 返回 jobId
浏览器 ◀── 200 {jobId, 预计消耗 19 积分} ─────┘
```

### 节点详解

| # | 节点 | 输入 | 做什么 | 输出 | 失败 |
|---|---|---|---|---|---|
| ① | 浏览器 | 用户点「生成」 | **生成 `commandId`**（客户端一次性 UUID） | `{commandId, modelId, taskType, specs, refs}` | — |
| ② | business-api 校验 | 上面的请求 | 查 `generation_model_capabilities` + 素材合规 + 并发配额 | 通过 / 拒绝 | 400，**不创建任何东西** |
| ③ | **billing Hold** | `+userId` | 见下方「Hold 内部六步」 | `{holdId, reservedCredits, catalogVersion}` | **402 余额不足** / 400 算不出价 / 503 billing 挂 |
| ④ | business-api 写 job | `catalogVersion` | 本地事务：写 job(queued) + N 个 slot(pending)，**冻结 `catalogVersion`** | `jobId` | 回滚；③的 hold 由幂等键兜底（重试安全） |
| ⑤ | 发 MQ | `jobId` + 会员等级 | 发 `generation.submit`，**带优先级**（付费用户插队） | — | MQ 挂了 → job 卡 queued，由 recovery 兜底 |
| ⑥ | 返回 | — | 返回 `jobId` + 预计消耗 | — | — |

### Hold 内部六步（billing-svc）

| 步 | 动作 | 落库 |
|---|---|---|
| 1 | **幂等检查** `hold:{commandId}` | 命中 → 直接返回首次结果 |
| 2 | **锁该用户全部有效批次**（`FOR UPDATE`，按 §扣减顺序排序） | — |
| 3 | 校验可用余额 `Σ(remaining − frozen)` | 不够 → 402 |
| 4 | **按顺序跨批次 `frozen += take`**，记录 `allocations` | `billing_credit_lots` · `billing_cost_reservations.allocations` |
| 5 | 写**复式分录**（借 wallet / 贷 frozen） | `billing_ledger_entries` ×2 |
| 6 | 写**用户可见流水**（`pending`） | `billing_user_transactions` |

### 关键设计

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **幂等键用 `commandId` 而非 `jobId`** | 让 Hold 能发生在写 job **之前**。Hold 成功但 ④ 失败 → 重试时命中幂等，**不需要跨服务补偿、不产生垃圾 job** |
| 2 | **`allocations` 必须落库** | 结算时按**同一份分配明细**解冻与扣减，否则会扣错批次（期间可能插入新批次或旧批次过期） |
| 3 | **`catalogVersion` 冻结进 `cost_reservations`** | 结算按它，**不按当前版本** —— 改价不影响已提交任务 |
| 4 | **只有 ③ 是同步的** | 200ms 预算全花在这 50ms 上；其余本地或异步 |
| 5 | **402 不创建任何东西** | 余额不足时 job 表、MQ 都干净——**没有「先建后删」** |

### 折扣在这一步怎么算

```
会员折扣：查 billing_member_discounts（按 tier + 模型/任务模式）→ 命中最优一条
营销折扣：查 billing_promotions（status=enabled + 时间窗命中 + 模型/等级命中）→ 命中最优一条
最终系数：会员 × 营销（stackMode=multiply）→ 套 floorFactorBp 底线
写入快照：appliedDiscounts: [{source:"member",id:17,bp:8000}, {source:"promotion",...}]
```

**判定用 Hold 时刻，不是结算时刻** —— 否则用户会看到「提交时 7 折、结算时原价」。

## 4. 流程四：任务执行（worker-java）

```
MQ ░ generation.submit
      │
      ▼
worker-java ──① claim ░[DB] generation_jobs
                 UPDATE ... SET status='processing', lease_owner=?, fencing_token=fencing_token+1
                 WHERE id=? AND status='queued'          ← 0 行 = 被别人抢走，放弃
      │
      ├─② 调上游（统一 key）──▶ new-api ──▶ 火山
      │◀── {provider_task_id} ──┘
      │
      ├─③ 轮询 / 回调 ░（直到终态）
      │     ├─ 每完成一个 slot：[DB] generation_output_slots.status + asset_id
      │     └─ 写 [DB] generation_job_logs
      │
      ├─④ 采集用量 ░[DB] generation_job_usage
      │     {quantities:{"usage.seconds":5,"usage.referenceCount":2},
      │      succeededSlots:1, usageSource:"upstream"}
      │
      ├─⑤ 置终态 ░[DB] generation_jobs.status
      │     succeeded | partially_succeeded | failed | cancelled
      │
      └─⑥ 发 MQ ░ generation.job.completed / generation.job.failed
```

| # | 节点 | 输入 | 做什么 | 输出 | 失败 |
|---|---|---|---|---|---|
| ① | claim | MQ 消息 `jobId` | **CAS 抢任务**（`status='queued'` + fencing token） | 拿到租约 | 0 行 → 放弃（别人在跑） |
| ② | 调上游 | job input | 用**统一 key** 调 new-api（**不再是用户 sk-**） | `provider_task_id` | 重试；超次数 → 走失败路径 |
| ③ | 轮询 | `provider_task_id` | 轮询直到终态，逐 slot 落库 | slot 状态 + asset | 超 `execution_deadline_at` → recovery 判失败 |
| ④ | **采集用量** | 上游响应 | **只采集原始量**：秒数/张数/token/缓存命中 | `generation_job_usage` | — |
| ⑤ | 置终态 | — | 写终态 + `succeeded_slots` | — | — |
| ⑥ | 发 MQ | — | 事件带 `catalog_version` + `usage` + `succeeded_slots` | — | MQ 挂了 → billing 兜底扫描补 |

### 关键设计

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **worker 只上报原始量，不报积分** | **worker 不该知道价格**。价格是 billing 的事 |
| 2 | **`quantities` 的 key 与 catalog 枚举同一套** | 配置与上报天然对齐 —— **结构上不可能「配了但没人报」** |
| 3 | **`catalog_version` 不由 worker 回显** | 存在 `cost_reservations` 上，worker 不参与版本管理 |
| 4 | **`usage_source` 标记权威性** | `upstream`（权威）vs `estimated`（估算，结算时告警） |
| 5 | **`fencing_token` 保护** | 旧 worker 租约过期后写不进（双写保护） |

## 5. 流程五：结算（多退少补）

```
MQ ░ generation.job.completed
      │
      ▼
billing-svc ──① 幂等检查 ⚡settle:{jobId}
      │
      ├─② 锁预留 [DB] billing_cost_reservations FOR UPDATE
      │      status != held → 直接返回（已结算/已返还）
      │
      ├─③ 读冻结的 catalogVersion → 复现定价
      │      actualCredits = f(usage, 成功的 slot 数, catalogVersion)
      │
      ├─④ 按 allocations 同序分配 actual
      │      [DB] billing_credit_lots: frozen -= frozenTake, remaining -= actualTake
      │
      ├─⑤ 写复式分录 [DB] billing_ledger_entries
      │      借 frozen(reserved)
      │      贷 wallet(reserved − actual)     ← 差额返还
      │      贷 revenue|cost(actual)          ← 按批次来源判定
      │
      ├─⑥ **UPDATE 同一行** [DB] billing_user_transactions
      │      SET amount = actual, status = 'done'      ← 不新建行
      │
      └─⑦ Redis 余额缓存失效
```

| # | 节点 | 输入 | 做什么 | 输出 | 失败 |
|---|---|---|---|---|---|
| ① | 幂等 | `jobId` | 查 `settle:{jobId}` | 命中 → 返回 | — |
| ② | 锁预留 | `jobId` | `SELECT ... FOR UPDATE` 锁预留行 | 预留状态 | 已终态 → 返回 |
| ③ | 算实际 | usage + `catalogVersion` | **按冻结版本复现定价**，按成功 slot 数算 | `actualCredits` | 版本不存在 → 告警 |
| ④ | 扣批次 | `allocations` | 同序解冻 + 实扣 | 批次更新 | — |
| ⑤ | 写账本 | — | 复式分录（§分录 6/7/8） | 分录 | — |
| ⑥ | **更新流水原行** | `actualCredits` | **UPDATE 不是 INSERT** | 用户看到的那一行 | — |
| ⑦ | 缓存失效 | `userId` | 删 Redis 余额缓存 | — | 失败不影响正确性（TTL 兜底） |

### 三种情况

| 情况 | 实际 vs 预扣 | 分录 | 用户看到 |
|---|---|---|---|
| 全部成功、规格精确 | `actual = reserved` | 借 frozen / 贷 revenue | 「消耗 19 积分」 |
| **部分成功** | `actual < reserved` | 借 frozen / 贷 wallet(差额) + 贷 revenue | 「消耗 12 积分」 |
| 实际超出（**理论不该发生**） | `actual > reserved` | 借 frozen + 借 receivable / 贷 revenue | 「消耗 25 积分」+ **P1 告警** |

### 关键设计

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **按「成功的 slot 数」计费** | 这是 `partially_succeeded` 能正确结算的前提 |
| 2 | **按冻结的 `catalogVersion` 复现** | 改价不影响已提交任务 |
| 3 | **`revenue` vs `cost` 按批次来源逐笔判定** | 消耗付费批次记收入，消耗赠送批次记成本 |
| 4 | **用户流水 UPDATE 同一行** | 用户**永远只看到一条**，且只有一个金额 |
| 5 | **`actual > reserved` 直接告警** | 说明 `holdCredits` 算漏维度，是配置/代码 bug |

## 6. 流程六：失败返还

```
MQ ░ generation.job.failed
      │
      ▼
billing-svc ──① 幂等检查 ⚡refund:{jobId}
      │
      ├─② 锁预留，确认还是 held
      │
      ├─③ 按 allocations 全额解冻
      │      [DB] billing_credit_lots: frozen -= take
      │      ★ remaining 不动 —— 批次原封不动（含有效期）
      │
      ├─④ 写复式分录 [DB] billing_ledger_entries
      │      借 frozen(reserved) / 贷 wallet(reserved)
      │
      └─⑤ **UPDATE 同一行** [DB] billing_cost_reservations（投影成那行流水）
             SET type = 'refund', direction = 'in', status = 'done'  -- 金额取当初的预扣额
```

| # | 节点 | 输入 | 做什么 | 输出 | 失败 |
|---|---|---|---|---|---|
| ① | 幂等 | `jobId` | 查 `refund:{jobId}` | — | — |
| ② | 锁预留 | `jobId` | 确认 `status = held` | — | 已结算 → 返回（**不会重复退**） |
| ③ | 解冻 | `allocations` | `frozen -= take`，**`remaining` 不动** | 批次回到预扣前 | — |
| ④ | 写账本 | — | 借 frozen / 贷 wallet | 分录 | — |
| ⑤ | 更新流水 | — | **同一行**转 `status=done`，金额取终态实际值 = **0**（退回是「结算到 0」） | 用户看到「消耗 0」，预扣额走运营面注解 | — |

> ⚠️ **as-built 勘误（2026-09-29，IKJ132，同日再修）**：第 ⑤ 步**不出成 `type=refund / direction=in`**。
> 退回与「多退少补」是同一条口径 —— 行里永远取终态实际值（失败单 = `markReleased` 写的 0），
> 类型恒为 `consume`、方向恒为 `out`，预扣额另走运营面的 `reserved_credits` 注解。
> 出成「已退回 +N」那样的进账，会让流水自己加不出余额（多出这 N）；退回的真实净变化是 0。
> 另：那行**不能消失**（用户此前已看到过 pending 行、余额真的降过）。
> 本文多处 `billing_user_transactions` 是设计期形态，**该表不存在**：流水由
> `TransactionMapper.selectPage` 投影得出，详见《计费逻辑详细设计》§2.3 / §4.4 勘误。

### 关键设计

**为什么 `remaining` 不动**：

若「先扣掉、返还时新建批次」，返还的积分会带上**新的有效期**——
用户凭空获得一次有效期重置，与应得权益不符。

**为什么用户看不到「扣了又退」**：

只更新原行，**不新建流水行**。用户看到的是「本次未消耗」，不是两条记录。

## 7. 流程七：充值到账

```
浏览器 ──①下单──▶ business-api ──▶ billing-svc
                                      └─[DB] billing_orders (status=pending, orderNo ⚡)
                                      └─ 调 blue_whale_pay → 返回支付页/二维码
浏览器 ◀── 支付页 ─────────────────────┘

  ⏳ 超时未支付（600s）→ 定时任务关单，**不产生任何积分**

用户支付 ──▶ blue_whale_pay ──②服务端回调──▶ billing-svc
                                              │
                                              ├─③ 验签（失败 → 拒绝）
                                              ├─④ 幂等 ⚡recharge:{orderNo}
                                              │
                                              └─⑤ 事务内：
                                                   ├─[DB] billing_orders.status = paid
                                                   ├─[DB] billing_credit_lots ×2
                                                   │      source=purchased（本金，永久）
                                                   │      source=bonus（赠送，按套餐有效期）
                                                   ├─[DB] billing_ledger_entries ×4（两组借贷）
                                                   └─[DB] billing_user_transactions 一行
浏览器 ◀── 轮询/推送 ── 「充值 · 100 元套餐 · +1500 积分」
```

| # | 节点 | 输入 | 做什么 | 输出 | 失败 |
|---|---|---|---|---|---|
| ① | 下单 | `{productId, payChannel}` | 建订单（`orderNo` 唯一），调支付网关 | 支付页 / 二维码 | 网关不可用 → 提示重试 |
| ② | **服务端回调** | `{orderNo, tradeNo, status, sign}` | **只信回调，不信前端跳转** | — | 验签失败 → 拒绝 |
| ③ | 验签 | 回调报文 | 校验签名 | ok / reject | 401 |
| ④ | 幂等 | `orderNo` | 查 `recharge:{orderNo}` | 命中 → 返回成功（**重复回调安全**） | — |
| ⑤ | 入账 | 套餐信息 | 发**两个批次** + 写账本 + 写流水 | 积分到账 | 事务回滚 |

### 关键设计

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **幂等键是 `orderNo`，不是支付网关流水号** | 网关会**重发多次**，且可能换流水号 |
| 2 | **只信服务端回调** | 用户从支付页跳回成功页 **≠** 支付成功 |
| 3 | **本金与赠送拆两个批次** | 有效期不同、财报口径不同（收入 vs 成本）、**退款只退本金** |
| 4 | **超时关单不产生积分** | 避免「挂起的订单」长期占位 |

## 8. 流程八：每日赠送

```
两条触发路径（互为兜底）：

路径 A（主）：登录成功事件 ░
  identity-svc ──登录成功──▶ MQ: identity.user.logged_in
                                │
                                ▼
                            billing-svc
                                ├─ 幂等 ⚡grant:daily:{userId}:{date}
                                ├─ 判连续登录天数（streak_day）
                                ├─[DB] billing_credit_lots（source=daily, 当日 23:59:59 过期）
                                ├─[DB] billing_daily_grants（uk: user_id + date）
                                └─[DB] billing_user_transactions 一行

路径 B（兜底）：每日定时任务 ░
  扫「今天登录过但没发积分」的用户 → 走同一段逻辑（trigger=cron_fallback）
```

| # | 节点 | 输入 | 做什么 | 输出 | 失败 |
|---|---|---|---|---|---|
| A | 登录事件 | `userId` + `loginAt` | 发 MQ（**不阻塞登录**） | — | MQ 挂了 → 路径 B 兜底 |
| B | 发放 | `userId` + `date` | 幂等检查 → 发批次 → 写流水 | 积分到账 | 重复触发 → 幂等拒绝 |
| C | 兜底定时 | — | 扫漏发的 | 同上 | — |

### 关键设计

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **双路径互为兜底** | 事件丢了有定时任务；定时任务漏了有事件 |
| 2 | **`uk_daily__user_date` 保证一天只发一次** | 用户登录十次不重复发 |
| 3 | **有效期 = 当日 23:59:59** | 即梦式「当日有效，不结余」 |
| 4 | **`streak_day` 记连续天数** | 供阶梯奖励（第 7 天 ×2）与运营分析 |
| 5 | **发的是普通批次** | 与其他 source 同构，**不做特例** |
| 6 | **登录不被阻塞** | 发积分是 best-effort，挂了不能让用户登不进来 |

## 9. 流程九：对账（三层）

```
┌─ ① 账本自检（每日）────────────────────────────────────┐
│ 对每个 user_id：                                        │
│   Σ ledger(wallet) 借记 − 贷记  ==  Σ lots.remaining   │
│ 不等 → 按 balance_after 断裂点定位到**具体分录**          │
│ 输出：「userId=42, delta=5000, suspectEntryId=991234」   │
└─────────────────────────────────────────────────────────┘

┌─ ② 预留兜底（每 10 分钟）──────────────────────────────┐
│ 扫 billing_cost_reservations WHERE status='held'        │
│    AND gmt_create < NOW() - INTERVAL 2 HOUR             │
│ → 查 generation_jobs 实际状态                            │
│     已终态 → 补 Settle / Refund                          │
│     未终态但超时 → 告警                                   │
└─────────────────────────────────────────────────────────┘

┌─ ③ 上游对账（每日）────────────────────────────────────┐
│ new-api 给的人民币账单  vs  Σ billing_provider_usage     │
│ 差异 → 列表                                              │
│ （若无按调用明细，只能对总额；按用户归因靠自己上报）        │
└─────────────────────────────────────────────────────────┘

┌─ ④ 报表 ───────────────────────────────────────────────┐
│ 毛利 = Σ 用户消费(account=revenue) − Σ 上游成本          │
│ 按模型 / 能力 / 时段聚合 → 「哪些模型在亏钱」              │
└─────────────────────────────────────────────────────────┘
```

| 层 | 频率 | 发现什么 | 不平怎么办 |
|---|---|---|---|
| ① 账本自检 | 每日 | 账本与批次分叉 | **按 `balance_after` 断裂点定位到具体分录** |
| ② 预留兜底 | 10 分钟 | 卡住的预留 | 查 job 状态 → 补结算/返还 |
| ③ 上游对账 | 每日 | 上游账单差异 | 人工核查 |
| ④ 报表 | 每日 | 毛利 | 定价决策依据 |

### 关键设计

| # | 设计 | 为什么 |
|---|---|---|
| 1 | **② 是必需的，不是可选** | MQ 重投有次数上限（现有 18 次进 DLQ），超限后必须有人兜底 |
| 2 | **billing 扫自己的表** | 不依赖外部系统，自己兜自己 |
| 3 | **`balance_after` 让对账能「定位」而非「发现」** | 只知道总数不平没用，要知道是哪一笔 |
| 4 | **③ 的局限必须接受** | 上游若只给总额，按用户归因只能靠自己上报的 usage |

## 10. 全流程串起来：一次视频生成的完整数据流

```
① 浏览器          {modelId:"seedance-2.5", specs:{size:"1080p"}, duration:5}
       │
② business-api    本地校验通过 → 生成 commandId
       │
③ billing Hold    ⚡hold:{commandId}
                   规格归一化 → catalog 查价 → ×折扣 → 四舍五入 = 19 积分
                   落库：credit_lots(frozen) + ledger×2 + reservation + transaction(pending)
       │          → {reservedCredits:19, catalogVersion:42}
④ business-api    [DB] generation_jobs(queued) + output_slots(pending)
       │          [MQ] generation.submit
⑤ worker-java     claim → 调 new-api(统一key) → 轮询 → slot 完成
       │          [DB] generation_job_usage {usage.seconds:5, usageSource:"upstream"}
       │          [MQ] generation.job.completed {status:"succeeded", succeededSlots:1}
⑥ billing Settle  ⚡settle:{jobId}
                   按冻结的 catalogVersion 复现 → 15 积分（实际）
                   [DB] credit_lots(frozen-=19, remaining-=15)
                   [DB] ledger: 借 frozen 19 / 贷 wallet 4 / 贷 revenue 15
                   [DB] transaction: UPDATE amount=15, status=done     ← 同一行
       │
⑦ 浏览器          「已完成 · 消耗 15 积分」     ← 全程只有这一个金额
```

**用户视角全程只有两个数字**：「预计消耗 19 积分」（处理中）→「消耗 15 积分」（已完成）。
**「预扣」这个词从不出现。**

## 11. 一图速查：谁在什么时候写哪张表

| 流程 | 写 `credit_lots` | 写 `ledger` | 写 `user_transactions` | 写 `cost_reservations` |
|---|---|---|---|---|
| 提交预扣 | `frozen +=` | 借 wallet / 贷 frozen | INSERT (pending) | INSERT (held) |
| 结算 | `frozen -=`, `remaining -=` | 借 frozen / 贷 wallet + revenue | **UPDATE** | UPDATE (settled) |
| 失败返还 | `frozen -=`（remaining 不动） | 借 frozen / 贷 wallet | **UPDATE**（同一行转 `refund`，金额 = 预扣额） | UPDATE (released) |
| 充值 | INSERT ×2 批次 | 借 cost / 贷 wallet ×2 | INSERT | — |
| 每日赠送 | INSERT 批次 | 借 cost / 贷 wallet | INSERT | — |
| 批次过期 | — | 借 wallet / 贷 cost | INSERT (expire) | — |
| 人工补偿 | INSERT 批次 | 借 cost / 贷 wallet | INSERT | — |

> ⚠️ **本表的 `user_transactions` 一列是设计期形态**：**该表不存在**，流水由
> `TransactionMapper.selectPage` 从 `credit_lots` / `cost_reservations` / `ledger_entries`
> **投影**得出（既无 INSERT 也无 UPDATE）。「失败返还」那格的 `amount=0` 见上方勘误
> （IKJ132 起改为取预扣额）。

**两条读法**：

1. **预扣是唯一 `INSERT` 流水 + `INSERT` 预留的动作**；结算与返还都是 **UPDATE**
2. **`remaining` 只在结算时减少** —— 预扣只动 `frozen`，返还原封不动
