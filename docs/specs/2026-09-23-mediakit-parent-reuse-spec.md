# MediaKit 家族重试收割（parent-reuse）推广规格

来源：IKI7PK 评估票的 grill-with-docs 讨论（2026-09-23），决策已逐项拍板。实施拆票见本规格父工单下挂的 8 张切片子工单。相关 ADR：0114。IKICD0（2026-09-24）修订失租边界：收割发布期间失租与守卫未命中从回退提交改为停止执行，见 Solution 与 Implementation Decisions。

## Problem Statement

用户使用工具家族（音频截取、人声背景分离、音频提取、视频 HD 高清、场景切分、视频去字幕、智能抠像、视频插帧）跑任务时，worker 侧统一有 720 次乘 5 秒约 60 分钟的轮询上限。任务超窗被判失败后，上游任务并没有取消，它还在跑。如果它在超时之后跑完，结果放在上游那里无人领取，24 小时后失效。

这时候用户看到失败卡片，手动点重试。当前系统的处理是全新提交一次上游任务，从头再跑一遍，用户再等一整轮，公司再付一份上游费用。哪怕旧任务其实已经跑完、结果就放在那里，也不会有人去捡。如果某类任务真实耗时超过 60 分钟，用户会陷入「超时、重试、再超时」的死循环，每转一圈多烧一份上游费用，永远拿不到结果。

视频生成家族没有这个问题：重试时系统会先查旧的上游任务，跑完了就直接把旧结果取回来发布。其余 8 个家族都没有这套机制。

## Solution

把视频生成家族已有的重试收割机制推广到 8 个家族。机制行为：用户点重试，worker 领取到这个重试 GenerationJob 时，先查它父任务的上游任务跑到哪了。如果旧任务已经成功且结果齐全，就直接把旧结果取回来，走本家族既有的发布流程交付给用户，不重新提交、不产生新的上游费用。收割结果分两类走向（IKICD0）：旧任务失败了、不存在、查询出错，或者取回发布失败但当前 Worker 仍持有执行权，就回退到现在的行为，正常重新提交；收割发布期间当前 Worker 失去 GenerationJob 的租约（续租未命中或续租状态无法确认），或 Finalize 守卫未命中，就停止本次执行，不向上游提交、不写终态、不安排后续轮询，任务由新 Worker 重新领取后重新检查父任务继续收割。

对用户而言，超时后的重试从「从头再等一整轮」变成「旧任务已跑完就立刻拿到结果」。对公司而言，重试不再重复消耗上游费用，死循环的经济伤害被消除。60 分钟窗口的语义不变，它只决定用户多久看到失败提示。

## User Stories

1. 作为使用音频截取的用户，当我的任务超时判失败后点重试，而旧上游任务已经跑完，我希望直接拿到旧任务的结果，这样我不用再等一整轮。
2. 作为使用人声背景分离的用户，当旧上游任务已经跑完，我希望重试直接拿到分轨结果，不用再等一整轮。
3. 作为使用音频提取的用户，当旧上游任务已经跑完，我希望重试直接拿到提取的音频，不用再等一整轮。
4. 作为使用视频 HD 高清的用户，当旧上游任务已经跑完，我希望重试直接拿到增强后的视频，不用再等一整轮。
5. 作为使用场景切分的用户，当旧上游任务已经跑完，我希望重试直接拿到切片结果，不用再等一整轮。
6. 作为使用视频去字幕的用户，当旧上游任务已经跑完，我希望重试直接拿到处理后的视频，不用再等一整轮。
7. 作为使用智能抠像的用户，当旧上游任务已经跑完，我希望重试直接拿到抠像结果，不用再等一整轮。抠像官方耗时为片长 1 到 3 倍，长片超窗比重最高。
8. 作为使用视频插帧的用户，当旧上游任务已经跑完，我希望重试直接拿到插帧后的视频，不用再等一整轮。
9. 作为用户，当旧上游任务也失败了，我希望重试正常重新提交，这样我还有机会拿到结果。
10. 作为用户，当系统查不到旧上游任务（父任务从未提交成功、或上游侧已无记录），我希望重试正常重新提交。
11. 作为用户，当查询旧上游任务出错（网络抖动、上游限流），我希望系统按「重新提交」处理，而不是把我的重试也判失败。
12. 作为用户，当旧任务显示成功但结果取回或发布失败（例如结果 URL 已超过 24 小时有效期）且当前 Worker 仍持有执行权时，我希望系统回退重新提交，最终拿到有效结果。
12a. 作为平台运营方，当收割发布期间当前 Worker 已失去任务租约或终态守卫未命中（被新 Worker 接管、任务已终态），我希望旧 Worker 停止本次执行并且不再向上游提交新任务，这样不会为一份无人轮询的孤儿上游任务白付费用（IKICD0）。
13. 作为使用人声背景分离的用户，只有旧任务的人声轨和伴奏轨都齐全时，我才希望系统直接复用旧结果；缺轨时我希望重新提交。
14. 作为使用场景切分的用户，只有旧任务返回了非空切片数组时，我才希望系统直接复用；空结果我希望重新提交。
15. 作为首次提交任务（非重试）的用户，我希望执行路径与现在完全一致，不受任何影响。
16. 作为用户，我希望收割得到的结果在卡片上的呈现与正常完成完全一致，资产入库、槽位回填、项目事件都与正常路径同型。
17. 作为用户，我希望重试收割不产生第二次计费，与视频家族的防双扣先例一致。
18. 作为平台运营方，我希望超时后的重试默认零上游成本，只有旧结果真的拿不到时才付费重新提交。
19. 作为用户，我希望任务日志能看出这次重试是复用了旧结果还是重新提交，便于排查问题。
20. 作为平台运营方，我希望 60 分钟窗口的口径不被这次改动影响，各家族的轮询上限与租约参数保持现状。

## Implementation Decisions

- 改动只落在 worker-java。backend 重试入口已对全部任务类型通用写入 retry_of_job_id，零改动；前端零改动。
- 机制形态逐家族照抄视频生成家族的三段先例（IKEA26）：
  - DTO：各家族 ClaimedXxxJobDto 新增 parentProviderTaskId 字段。
  - claim：JobClaimService 中各家族的 claim 方法在 retryOfJobId 非空时，调用视频先例已在用的同一个 mapper 查询方法，二次查询父任务的 provider_task_id 投影进 DTO。不新增 SQL。
  - submit 相：各家族处理器在提交入口先检查 parentProviderTaskId 非空则查旧上游任务。旧任务成功且结果齐全，直接把查到的 observation 喂给本家族既有 publishResult(claim, observation) 发布，不重新提交。发布守卫未命中（stale worker 或已终态）属于停止执行，不回退提交（IKICD0）。
- 回退分支固定为四种：旧任务失败、旧任务不存在、查询出错、仍持有执行权时的收割发布失败（下载转存异常，如结果 URL 超 24h 失效）。回退就是走现在的正常提交逻辑。收割发布期间失租与守卫未命中（场景切分逐段转存续租未命中或续租状态无法确认、智能抠像心跳失租、Finalize 守卫未命中）属于停止执行：不提交上游、不写 Finalize、不安排后续轮询，任务保持 processing 由新 Worker 重新领取后重新检查父任务继续收割，失败的旧 Worker 不妨碍接手（IKICD0，不再归入「收割发布失败一律回退提交」）。
- 结果齐全判定逐家族对齐该家族轮询相的既有成功口径，不新立标准：人声背景分离要求轨数组齐全（2 到 3 条轨），场景切分要求切片数组非空，其余单输出家族要求结果 URL 非空。
- 不为结果 URL 的 24 小时有效期加探测层。URL 失效会在取回或转存阶段表现为发布失败，由回退分支兜底。
- 各家族 DTO 现有注释「无 parentProviderTaskId：手动重试是沿用冻结 input 的新 job（免费工具无二次扣费面）」随机制落地逐家族改写。该立场只算了用户计费面，没算上游成本面，本规格将其推翻（见 ADR-0114）。
- 发布动作复用各家族既有 publishResult，不改其签名，不为收割新建发布路径。资产入库、槽位回填、Finalize 终态收口与正常路径同型。
- 日志：收割命中与回退原因各打一条家族既有格式的 info/warn 日志，对齐视频先例的留痕方式；停止执行（失租/守卫未命中）与回退重新提交在日志措辞上可区分（IKICD0：骨架 warn 分别为「停止本次执行（不回退提交）」与「回退重新提交」）。
- 计费：收割路径不新建 cost 记录，与视频家族先例的防双扣口径一致（重试 job 的记账快照在 backend 重试入口已复用原 job）。
- 批次划分：批一为 6 个纯轮询家族（音频截取、人声背景分离、音频提取、视频 HD、场景切分、视频去字幕），批二为智能抠像与视频插帧。批二开工前必须先核验心跳续租机制（60 秒租约心跳）与收割路径的交互，确认收割期间租约行为正确。
- 模式定型票为音频提取（media_extract），它是其余 MediaKit 处理器编排骨架的模板家族。批二两票阻塞在它之后。
- 60 分钟轮询窗口、各家族租约秒数、MQ 契约一律不动。
- IKIDEK 有界接手：默认恢复扫描只看创建后 120 分钟内的任务。八个收割家族中，只有 `processing`、有 `retry_of_job_id`、父任务有上游任务号且自身尚未提交上游任务的 job，才保留额外 10 分钟扫描资格，默认须在创建后未满 130 分钟时由恢复扫描重新投递。这些持久条件覆盖收割发布失租或续租状态不明后停止的任务，也覆盖相同状态下意外退出的 Worker；库中没有单独记录停止原因。420 秒租约到期后，正常 60 秒扫描节奏仍有至少下一轮接手机会及约 2 分钟余量。新 Worker 按原有租约和 fencing 条件重新领取，再查父任务并走原发布路径。超过接手期限不自动重投；其他家族、已提交自身上游任务、父任务无上游任务号、非重试、queued 和已有终态任务不享受额外窗口。`RECOVERY_MAX_AGE_MINUTES=0` 的既有 audio_mix 扫描语义不变。
- 不做监控：不加埋点、不配看板、不配告警（决策记录见 ADR-0114）。

## Testing Decisions

- 好测试只测外部行为：给定一个 claim 构造，断言处理器是「不提交直接发布」还是「正常提交」，以及发布内容。不断言内部调用顺序与私有方法。
- 测试接缝为各家族处理器的既有 Mockito harness，不新开接缝。视频 HD、场景切分、视频去字幕、人声背景分离、智能抠像、视频插帧 6 家有独立测试类；音频截取与音频提取挂各自 ErrorMappingTest 文件（本身就是 mock 掉上游 client、mapper、转存、MQ 的完整处理器编排测试）。
- 每个家族的用例矩阵固定六条：父任务成功且结果齐全则复用发布；父任务失败则重新提交；父任务查询异常则重新提交；非重试 job 不查父任务；结果不齐全（多输出家族缺轨或空切片）则重新提交；收割发布失租或守卫未命中则停止执行（上游 submit 零调用、不落失败终态、不续排，IKICD0）。
- 先例：VideoJobProcessorTest 的 parent-reuse 用例（构造带 parentProviderTaskId 的 claim，断言不提交直接发布及各回退分支），逐家族平移。
- 验收口径：worker-java 全量测试零失败。

## Out of Scope

- 视频生成家族既有 parent-reuse 机制不动。
- backend 重试写入链路、前端重试入口不动。
- 60 分钟轮询窗口与各家族租约参数不调（ADR-0114 决策 2）。
- 监控埋点、看板、告警全部不做（ADR-0114 决策 3）。
- 视频家族以外的其他家族形态（图片家族、音频生成家族）不纳入，它们没有 60 分钟轮询窗口语义。
- 自动重试不做：收割只发生在用户手动重试产生的新 job 上，不新增系统自动重试。
