# MQ 选型与「解耦」决策记录

> 2026-07-31 架构讨论。结论：**保持 BullMQ + Redis 升级哨兵**，不为「解耦」上专业 MQ。
> 适用场景：视频生成长耗时任务队列（低频、高可靠、需延迟/重试）。

---

## 一、决策结论

### 主决策：保持 BullMQ，Redis 单机 → 哨兵/集群

**理由**：场景匹配 + 已落地 + 零迁移成本。BullMQ 的可靠性机制（lease/fencing/重试/延迟）已完整实现，换 MQ 等于重写。

### 次选（若坚持独立 MQ）：RabbitMQ（不是 Kafka）

**理由**：功能匹配 + 运维比 Kafka 轻 + Node 生态好。但**不推荐为了「专业」而迁移**。

### Kafka 的正确位置（未来）：日志收集 / 事件流管道

现在缺集中日志（这是真问题）。未来上 Kafka 做日志汇聚 → ELK/Loki，那才是它的主场，**不是视频任务队列**。

## 二、横向对比（针对我们的负载特征）

**负载特征**：视频生成，长耗时（几十秒~几分钟），低频，并发 8，可靠性要求高，需延迟/定时/重试。

| 维度 | BullMQ (Redis) | Kafka | RocketMQ | RabbitMQ | NATS JetStream |
|---|---|---|---|---|---|
| 设计定位 | 任务队列 | 高吞吐日志/事件流 | 金融级事务消息 | 通用消息路由 | 云原生轻量 |
| 持久化可靠性 | 中（依赖 Redis） | 强（磁盘副本） | 强（CommitLog） | 强（镜像队列） | 强（副本） |
| 延迟/定时任务 | ✅ 原生 | ❌ 需自造 | ✅ 原生 | ✅ 插件 | ⚠️ 有限 |
| 重试/backoff | ✅ 原生 | ❌ 自造 | ✅ | ✅ | ⚠️ |
| 死信队列 | ✅ 原生 | 自造 | ✅ | ✅ | ✅ |
| 运维复杂度 | 低 | 高（Broker+KRaft） | 中高（NameServer+Broker） | 中 | 低 |
| 资源占用 | 极低 | 重（单 broker 2G+） | 重 | 中 | 极低 |
| 8C16G 单机能跑 | ✅ 轻松 | ⚠️ 勉强 | ⚠️ 勉强 | ✅ | ✅ |
| Node 生态 | ✅ 一等公民 | ✅ kafkajs | ⚠️ 弱 | ✅ | ✅ |
| 我们已有 | ✅ 生产在用 | ❌ | ✅ 支付域 | ❌ | ❌ |
| 适合视频任务 | ✅ 完美 | ❌ 杀鸡用牛刀 | ⚠️ 大材小用 | ✅ 可以 | ✅ |

### Kafka ❌
- 场景错配：高吞吐日志流的设计，视频任务低频用不上吞吐优势
- 功能缺口：无延迟任务/重试/优先级，视频生成刚需要自造
- 运维重：Broker + KRaft/ZK，8C16G 吃力
- 适合的位置：未来日志收集、用户行为流、实时数仓

### RocketMQ ⚠️
- 场景仍错配：强在事务消息/顺序消息/金融一致性，视频生成用不上
- 和支付域隔离：复用不了，等于新搭一套
- Node 生态弱
- 适合的位置：未来金融级扣费（扣费+生成原子性），支付域已在用

### RabbitMQ ✅（备选）
- 功能全，Node 生态好，运维比 Kafka 轻
- 但 BullMQ 已覆盖需求，新增 RabbitMQ 无明显增益
- 适合的位置：若未来要独立于 Redis 的专业 MQ，比 Kafka 更合适

## 三、「解耦」认知纠偏

### 误区：「专业企业都用 MQ 解耦」
**MQ 解耦的是特定类型的耦合，不是所有耦合都该用 MQ。** 

我们的视频链路**已经解耦**了：
```
前端 → POST 创建任务 → BullMQ 队列 → Worker 消费 → 调 new-api → 轮询 → 落库
```
创建任务（API 进程）与执行任务（Worker 进程）通过 BullMQ 隔离，用户提交后立刻返回不阻塞。**这就是 MQ 解耦的本质，BullMQ 已实现。**

「解耦」不是「非要用某品牌 MQ」，而是「异步 + 进程隔离 + 消息驱动」这个模式。

### 成熟企业的分层架构（不是全用 Kafka）

| 层 | 工具 | 场景 |
|---|---|---|
| 任务队列（低频、可靠、延迟/重试） | BullMQ / RabbitMQ | 视频生成、邮件、报表 |
| 事件流（高吞吐、多消费者、日志） | Kafka | 行为埋点、审计、数据同步 |
| 通知/广播（瞬态、轻量） | Redis Pub/Sub | SSE 唤醒（已在用） |
| 事务消息（金融级一致性） | RocketMQ | 扣费+下单原子（支付域在用） |

**专业 = 每个场景用对的工具，不是所有场景都用最重的工具。**

## 四、什么时候该上专业 MQ（三个信号）

不是看「是不是初创」，而是看信号：

1. **单机 Redis 成为可靠性瓶颈**
   - 解法：Redis 升级哨兵（一主两从 + 故障转移），**不是换 Kafka**
   - 换 Kafka 的信号：Redis 集群也扛不住（任务积压百万级 / 跨机房）——离我们很远

2. **出现「一份数据多个独立消费者」需求**
   - Kafka 核心优势：发布-订阅 + 持久日志，一个事件多个消费者各自消费
   - 例：生成完视频，下游同时（通知用户 + 记账 + 数据分析 + 转码）
   - 现在只有「更新库 + 推 SSE」，BullMQ fanout 够用
   - 真有多个独立消费者了，再上 Kafka

3. **跨服务异步通信频繁**
   - 现在服务少（web/api/gateway/worker），HTTP 同步调用够用
   - 服务拆到 10+ 个、调用链成网状，才值得事件总线

## 五、迁移成本视角

**BullMQ → 专业 MQ 的迁移成本比想象中高：**

1. **重写可靠性机制**：lease（120s）+ fencing token + cancellation + Redis 恢复是手写业务逻辑，换 MQ 重写一遍（Kafka/RabbitMQ 不自带，只提供投递保证）
2. **延迟/重试任务重建**：BullMQ 原生的 delayed job + exponential backoff，换 Kafka 要自造轮子
3. **双写过渡期风险**：迁移期间新老队列并存，任务可能分流/重复/状态不一致
4. **运维新栈**：broker/ZK/监控，要人学、要人值班
5. **Node 生态降级**：BullMQ 是 Node 一等公民，其他客户端不如它贴合

**反过来说：BullMQ 现在留着，未来要换也能换**——业务逻辑在 `runVideoJobStep` 里（接收 repo/mediaRelay/provider 注入，不绑死 BullMQ）。**只要保持「业务逻辑与队列实现解耦」，换队列是「换管道不换水」。**

---

## 六、初创期该做的「解耦」（ROI 高、成本低）

比纠结 MQ 品牌更值得治理：

1. **业务逻辑与队列实现解耦**（已做 ✅）：`runVideoJobStep` 依赖注入，不绑 BullMQ
2. **服务间契约解耦**（部分做了）：前端走 HTTP 契约调后端，不直接碰队列
3. **数据存储解耦**（要做）：Prisma + GORM + JPA 三个 ORM 连同一个 MySQL，schema 变更要三方协调——**这个耦合比 MQ 品牌更值得治理**

---

## 七、演进路线

```
现在：BullMQ + 单机 Redis
  ↓
第一步（立刻）：Redis 升级哨兵（解决单点）  ← 性价比最高
  ↓
第二步（任务量涨10倍）：BullMQ 不动，观察积压
  ↓
第三步（出现多消费者/跨服务事件需求）：
        → 日志/埋点/审计上 Kafka（Kafka 的主场）
        → 视频任务继续 BullMQ
  ↓
第四步（金融级扣费）：RocketMQ 事务消息（支付域已在用）
```

**原则：不要用「未来可能要用」指导现在选型。架构是演进的，不是一次定终身。**

---

## 八、开会一句话结论

> 「我们不是不上专业 MQ，是现在还没到上的时候。视频任务队列 BullMQ 已满足，单点是 Redis 没做哨兵。Kafka 真正的价值在日志收集和事件流——那块我们现在缺（无集中日志），未来上 Kafka 的位置在那里，不是视频队列。初创期的『专业』是『每个场景用对的轻量工具 + 保持业务解耦』，不是『一上来全用最重的组件』。」
