# ADR-0134：视频样片报价指纹不含提示词字数

- 状态：已采纳
- 日期：2026-10-29
- 决策者：lixq（经 `/grilling-with-docs` 会话共同得出）
- **关联**：[ADR-0088](0088-prompt-assembly-ownership-and-reference-marker.md)（提示词全文由提交方给出）
- **工单**：IKRH5I（V1.3.0 样片提交「价格已更新」1056 误报）

## 背景

样片提交用 `quote_revision` 做价格确认：客户端先取报价，提交时带回 `expected_credits` 与 `quote_revision`，服务端按提交体重新投影报价入参并比对（`handle-create-generation-job.ts` 的样片分支）。

`quote_revision` 是整份报价入参的指纹，其中含 `prompt_characters`。而报价与提交的提示词文本由两条路径产生：报价曾用编辑器拍平值（引用渲染为 `图片1`、`首帧`），提交用发送形态（引用渲染为 `&<身份>&`，文本附件展开为 `文本1：正文`）。两组字符数必然不同，**带图片引用或文本附件的样片提交每次都被判为价格已变**，与操作快慢无关；纯文本提交则受 600ms 报价防抖窗口影响偶发。

## 决策

1. **视频的报价指纹只覆盖价格维度。** `quoteRevisionOf` 的入参在视频场景下剔除 `prompt_characters`；报价端点、样片创建校验、成片与重新生成样片两条链路的报价与校验共用同一投影。成片链路的存储输入本就不含 `prompt_characters`，该处为防御性对齐，防止将来派生输入补上该键后重新失配。
2. **视频报价请求不再携带提示词。** 客户端报价入参只含模型、分辨率、比例、时长、音频、模式与参考素材；提示词内容既不进指纹，也不触发报价重算。
3. **提交被 1056 拒绝时作废已缓存的报价**，用户重新打开面板时按新价格重新报价；不自动补价重提。
4. **参考素材保持全量参与指纹**：顺序、条数、类型、时长仍在，前端报价与提交的参考数组必须逐项一致（报价按拖拽序 / `stripOrder` 生成）。
5. **1056 语义不变**：目录版本、能力行版本、用户等级、参数与参考素材任一变化，仍拦截并要求用户重新确认报价。

## 依据

视频计价规则只用 `usage.succeededSlots` / `usage.seconds` / 参考条数与参考秒数等维度；按字符计费的 `usage.characters`（`UsageDim.CHARACTERS`）当前只被音频使用。产品确认：**视频不按提示词计费**。

## 被否决的备选

- **前端把报价入参改成完整发送体**：同样能消除误报，但需要把终稿 prompt 的生成收敛到一处，改动横跨弹窗、dock 与任务提交三层，且对价格确认没有额外收益。
- **提交侧剔除提示词**：提示词是生成输入，无法剔除；只改报价侧会让任意非空提示词恒定失配。
- **放宽 1056 判定本身**：等于放弃价格确认，本单明确排除。

## 后果

- 提示词编辑不再使已取到的报价失效，提交前不再因文本差异被拒；报价请求也不再随输入逐字变化。
- **反向约束**：若将来视频引入按字计费，必须同时恢复指纹中的 `prompt_characters` 与报价请求里的提示词；否则报价会按 0 字计价且确认环节无法察觉。
- 提示词在报价请求与提交请求中仍可能不同（附件展开、引用标记形态），这是接受的偏差：它不影响价格，也不影响模型输入（模型只收到提交侧文本）。
