# ADR-0088：生成提示词由提交方给出全文，服务端只做引用标记转移

- **状态**：Accepted
- **日期**：2026-09-17
- **决策者**：lixq（经 `/grilling` 会话共同得出）

- **工单**：IKG6EK（父缺陷）；执行子单 IKGJT2（后端）、IKGJT5（前端）

## 背景

方案附件正文在提交给供应商的 `prompt` 中重复两份（IKG6EK）。两份来自两个各自成立的实现：

- 前端 `composeImageSendPrompt` 把连线附件正文原样拼进 `parameters.prompt`（`21856177`，2026-09-13 生图；`e618d17e`，09-14 扩到音视频）。
- 后端接纳侧 `freezePromptPlans` 又把编译后的附件正文与 `input.prompt` 组合（`composeTextAttachmentPrompt`），冻结进 `prompt_plan_snapshot.providerPrompt`。

根因不是谁算错，是**同一个字段被当成了两个东西**：`parameters.prompt` 名义上是「用户主提示词」（后端在它前面接附件正文），实际上前端把它填成了「附件 + 主提示词」的拍平结果。后端无从分辨那 275 字是从附件抄来的，照约定当前缀拼接。

后端 `21856177` 之前的行为（附件与提示词分别表达）由 IKDLQF/IKDLQG 定死；前端拼接是后来加的，且**没有任何规格文档授权**——`docs/specs`、`docs/adr`、`docs/projects` 中查不到「拼进 prompt」「拍平」的任何记载，且与 IKDLQF 明文冲突（它还反手加了一个契约明确禁止的前端 1000 字闸）。两个 PR 都经正常评审合入，冲突是两处各自看都对、放一起才暴露。

## 决策

1. **提交方给出全文。** 前端提交的 `prompt` 即最终正文，附件正文与主提示词的拼装在前端完成。
2. **前端只标身份，不标编号。** 正文中每一处素材引用写为 `&asset_id&`（本地 asset 纯数字 id）。编号不写进正文。
3. **服务端只做标记转移。** `&asset_id&` → `@标签`，**找不到 id 就不转、标记原样保留**。标签按端派生，与 `prompt_doc` 编译同一套规则（`backend/libs/contracts/prompt-doc.ts` 的 `videoRefLabel`）：

   | 端 | 本次素材数组 | 出站标签 |
   | --- | --- | --- |
   | 图片 | `input_asset_ids`（直接参考 + 文本带入的合并序） | `@图片N`，N = 下标 + 1 |
   | 视频 | 单数组 `references`（帧在前） | 首尾帧 → `@首帧` / `@尾帧`；普通参考 → `@图片N` / `@视频N` / `@音频N`（同类型内连续编号） |
   | 音频 | 单数组 `references` | `@图片N` / `@音频N`（同类型内连续编号） |

   编号一律由服务端按本次请求的素材顺序现算——客户端只给身份。**这张表是前端实现 `&asset_id&` 时唯一的编号依据**；前端展示编号也必须由同一有序数组派生（IKFA1M §2）。
4. **服务端对提示词不再有任何其他动作**：不拼装、不追加、不做兜底组合。执行侧（`worker-java`）三端统一只读 `input.prompt`。
5. **请求契约三端统一用 `references` 承载素材数组**；`material` 仍**仅视频**可用（图片/音频上游不支持，`validateRejectMaterialReferences` 保留）。
6. **删除**：`providerPrompt` 的生成与消费、`input.composed_prompt`、执行侧三端优先级链中的兜底组合。`prompt_plan_snapshot` 保留（方案绑定校验、审计、重试复用仍需要），但不再携带 `providerPrompt`。

## 被否决的备选

- **回退前端拼接，维持后端组合**：即整个撤回 `21856177` 的前端半。被否——会议已定方向，且前端拼接另有展示用途。
- **前端连编号一起编译**：前端确实拿得到最终参考顺序与角色（`collectImageInputAssetIds` / `buildVideoJobReferences`），但要复刻整套编号规则与角色标签（参考图/参考视频/参考音频/首帧/尾帧），一旦与后端漂移就会出现「用户看到图片2、模型收到 @图片1」。IKFA1M §2 已确立「稳定身份 ≠ 展示编号」，由服务端算编号是该原则的自然延伸。
- **服务端对 `references` 去重**：同一张图既当首帧又当普通参考时会被静默合成一条，帧角色丢失。维持现状「重复即 400」（`freezePromptPlans` 现有校验）——**不做静默去重**。
- **本次一并退役 `prompt_doc`**：见「后果」第一条。

## 后果

- **服务端短期存在两种引用标记输入，且这是有意的**：`&asset_id&`（文本形态）与 `prompt_doc`（结构化形态，IKFA1M/IKFA1O/IKFA1P）。`prompt_doc` 已上验收、有独立契约与三套回归，一并退役会让一个 P2 缺陷变成跨三份契约的迁移。**两者并存不是冗余，不要合并掉**；收敛另开一票，等 `&asset_id&` 在线上跑过一轮、有实测数据再谈。

  ⚠️ **但「`prompt_doc` 线不动」只对它的输入形态成立，不对它的输出成立。** 删 `providerPrompt` 改变了这条线的最终正文：带 `prompt_doc` 时 `handle-create-generation-job.ts` 会用 `compilePromptDoc` **整体覆盖** `parameters.prompt`，而附件正文原先只由服务端的组合送进供应商。因此**前端侧必须把附件正文作为 `prompt_doc` 的 `text` 段带进来**——塞进 `parameters.prompt` 是无效的，会被覆盖掉。这条要求写进了 IKGJT5；不满足就是「模型收到 `文本1` 却从不知道文本内容」的静默降级。
- **标记语法无转义**：正文中原本形如 `&数字&` 的文本会被当作引用（用户手打「价格 &21212& 元」）。找不到 id 时原样保留，因此用户侧零提示、模型可能收到看不懂的标记——等于把「静默丢弃素材」换成了「静默降级」。**这是已知代价**，登记在此，将来观测到这类脏正文能对上号；若要收紧（禁裸 `&` 或加转义口子），另开一票。
- **`input` 内部字段不随请求契约改名**：请求体统一 `references`，但图片 worker 读的仍是 `input.input_asset_ids`，由接纳侧做一次映射。改请求字段不等于改冻结字段。
- **历史任务不做特殊处理**：重试整份复制原 `input`（`generation-command-repo.ts` 现状），不重算、不回填。**但这不等于行为不变**——`input` 里冻结的正文来源本身变了：经 `21856177` 之后提交的任务，前端已把附件正文拼进 `parameters.prompt`，重试照旧完整；而 `prompt_doc` 分支（IKFA1P）提交的任务，附件正文原先只存在于 `providerPrompt`，而 worker 现在不读它——**这批任务重试会发出更短的正文**。接受这个结果（快照即历史事实），但不当作「无变化」。
- **发布窗口**：同批发布，未升级的前端发来的请求不含 `&asset_id&`——标记不会被转移（原样保留），且**带 `prompt_doc` 的请求会丢失附件正文**（见上「两种引用标记输入」一节），带方案附件的请求不再有服务端编译的 `参考图N`。**窗口内行为与改造前不一致**，这是本决策已知且接受的代价；不设兼容层，靠前端同批上线闭合。
- 本决策的收益是「同一信息只有一处表达」；代价是把编号规则留在服务端的同时，把**拼装顺序**的责任交给了前端，因此前端卡片/chip 上显示的编号必须与服务端编译同序（IKFA1M §2 已有该要求），否则会出现展示与出站不一致。
