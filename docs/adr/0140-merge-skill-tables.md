# ADR-0140：技能域四表收敛为两张

- **状态**：已采纳
- **日期**：2026-10-29
- **决策者**：lixq
- **关联**：IKRJO3（实施）、IKRJP7（下架失效缺陷）、IKQWV1（父需求）、[ADR-0135](0135-catalog-material-content-prefixes.md)

## 背景

技能域此前有四张表：`catalog_skills`（官方目录）、`catalog_creative_skills`（官方与个人共用的技能身份）、`catalog_creative_skill_versions`（正文版本）、`user_skills`（用户引用）。它们分四批叠加而成，每批都没有退役上一批。

核对生产代码后确认三个事实：

1. **身份表没有维护入口**。管理端七个接口全部只操作 `catalog_skills`；`catalog_creative_skills` 只有回填创建官方行（已存在即跳过）与用户创建/删除个人行，没有任何更新通路。
2. **版本表从未被使用**。写入只有 `display_version='1.0.0'` 的插入和删除，没有发布新版本的通路；其服务的运行 pin 依赖的 `agent_runs` 已由 IKRJ9P 退役。
3. **由此产生三个可观察缺陷**：运营修改目录的名称、简介、正文不会同步到身份表，解析结果停留在回填当天；官方技能下架后解析端点未判断上下架，仍返回正文（IKRJP7）；目录行删除或改名后身份行成为无主孤儿。

资产契约（2026-08-03）把「目录」「身份」「版本」拆成三层，前提是运行时要按不可变版本固定执行。该前提已随运行 pin 退役而不复存在，个人技能在线编辑本来也属非目标。

## 决策

1. **保留 `catalog_skills` 作为唯一的技能本体表**，官方与个人共用：`owner_user_id=0` 表示官方，`asset_domain` 区分领域，`creative_skill_id` 为对外稳定身份。
2. **删除 `catalog_creative_skills` 与 `catalog_creative_skill_versions`**。正文落到技能行的 `body`，摘要落到 `content_digest`，不再保留多版本历史。
3. **`user_skills` 保持引用语义不变**：只指向官方技能，个人技能凭 ownership 出现在「我的技能」。
4. **名称唯一性改为按 owner**：删除全局 `uk_name`，改由 `(owner_user_id, name_key)` 索引与应用层校验承担；个人技能允许不同用户同名。
5. **管理端补齐官方技能维护入口**：列表、详情、更新（名称、简介、正文、分类），全部限定 `owner_user_id=0`。
6. **解析端点按上下架判断**：官方技能仅在 `is_delete=0` 时可解析；个人技能仍按 owner 判断。
7. **迁移以数据合并为主**：官方行按原 `source_skill_id` 1:1 合并；身份表中没有对应目录行的官方行、以及全部个人行，插入为新行；正文优先取 active version，其次取目录 `content`。

## 后果

- **破坏性发布**：迁移执行后旧镜像读不到两张旧表。数据库与后端镜像必须同一维护窗口内上线，先镜像后 DDL 或同窗口完成，不得让新镜像长时间空跑。
- **不可回滚的数据变更**：两张旧表被删除，正文与摘要已并入 `catalog_skills`。迁移前必须备份；回滚只能靠备份恢复，不接受「逆序删表重建」。
- **名称唯一性从库级降为应用级**：官方目录名重复不再被数据库拦截，管理端改名时按 `(owner_user_id=0, name_key)` 查重并返回冲突；绕过管理端直接写库仍可产生同名行。
- **迁移只执行一次**：删除 `content` 列后重复执行会在 `ADD COLUMN ... AFTER content` 处失败；不提供幂等重放，恢复走备份。
- **无正文条数在迁移中输出**：删除列与表之前执行 `SELECT COUNT(*) AS skills_without_body FROM catalog_skills WHERE body IS NULL`，执行者需核对该计数并记录。
- **版本历史不再存在**：需要按历史版本复现时，只能依赖当时的执行记录；若将来产品要求多版本发布，另立工单重新引入。
- **worker-java 测试 schema** 同步为两表结构；`001_baseline.sql` 与 `002_seed.sql` 保持时间点快照，不回改。
- ADR-0135 中 `skill / user_skill / creative_skill / creative_skill_version` 四张表的存在性描述由本 ADR 取代；目录前缀命名规则继续有效。
- 资产契约 §1 的三层存储布局与 §13.2 基于版本表的运行引用保护不再成立，接口字段（`creative_skill_id`、解析响应）保持不变。

## 被否方案

- **保留三张表（目录并入身份，版本表留存）**：版本机制没有写入方，留着只会继续漂移，且会让人误以为存在发布流程。
- **保留四张表并补同步/发布入口**：等于为一个没有被使用的版本机制再造一套运营流程，成本高于收益。
- **只修下架判断不合并表**：三个数据源之间的漂移与孤儿行仍然存在，问题会以别的形式回来。
