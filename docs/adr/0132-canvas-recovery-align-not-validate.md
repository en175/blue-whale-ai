# 画布生成恢复保存：以对齐取代校验

**状态**：accepted（2026-10-21，IKPD88 / IKPD8E / IKPD8H）

规则一句话：**保存时服务端以自己的账本为准补齐缺失事实；客户端只声明意图，不复述服务端已知的明细。只有归属真正冲突时才拒绝。**

ADR-0125 已经把「谁算受保护项」改锚到 `generation_canvas_node_owners`。本篇处理它没覆盖的另一半：**服务端已知、却要求客户端复述的知识**。

## 动因

三张现成画布在两周内造成用户可见的保存失败：

| 画布 | 报错 | 根因 |
| --- | --- | --- |
| 1330（10-09） | 422 未声明的受保护项被改动 | 判据读文档 marker，marker 落后于持有者表（已由 ADR-0125 修复） |
| 432（10-09） | 422 占位转换必须与全部结果同笔保存 | 客户端只声明 `$target`，没有逐条声明该提交的输出 |
| 1541（10-21） | 同上 | 同上 |

432 与 1541 的共同点是：**「这条提交有哪些结果」服务端用 `projectionOf` 自己就能算出来**，却要求客户端逐条复述。客户端漏一条，整笔保存失败。

另一条不一致：1541 同一笔保存里，节点 3、5 带 `assetId` 但恢复表没有输出行，服务端放行；节点 4 走 `replaceTarget` 被拒。同一个不变量在两条路径上口径不同。

## Decisions

1. **`replaceTarget` 由服务端补齐全部输出。** 该提交在 `projectionOf` 里所有未落盘的输出，一律落成 `present`，资产取任务可信产物，不再要求客户端声明。客户端显式声明的 `apply` / `remove` 优先。
2. **普通写节点同样对齐。** 来件文档里带合法 marker、带 `assetId` 的节点，若其提交在 `generation_canvas_outputs` 里缺输出，按同一套投影补齐。资产与可信产物不一致时拒绝，错误体带 `nodeId` / `submissionId` / `outputKey`。
3. **只在「确有输出缺失」时校验资产。** 已经一致的画布不因本次改动新增拒绝面——这是 ADR-0125「只放宽不收紧」的延续。
4. **归属冲突改 409。** 「结果节点已被其他提交占用」三处从 422 改为 409，带节点定位信息。文档与请求不一致、伪造标记、未声明缺席、资产不可信仍是 422：它们不是并发冲突，客户端拿去「刷新重试」不会变好。
5. **客户端只表达意图。** `recoveryChanges` 保留，但一条意图一条：`$target` 的 `replaceTarget`、用户显式删除的 `remove`、撤销的 `restore`。不再逐输出声明。
6. **失败必须可恢复。** 前端在任何 409/422 之后拉一次恢复账本、重组声明；随后解除保存阻塞，让下一次保存自然可用。不做永久 block，也不静默覆盖用户本地编辑。

## Considered Options

- **保留客户端逐条声明（否决）。** 服务端知识转嫁客户端，漏一条整笔失败，已在上表复现两次。
- **删除 `recoveryChanges`，服务端从文档 diff 反推（否决）。** 「用户主动删卡」与「客户端版本旧、没同步到卡」在 diff 里不可区分；分不清就只能关掉守护。
- **只放宽、不补齐（否决）。** 1541 的节点 3、5 会长期停在「画布有产物、恢复表无输出」，也就是 IKNB98 修的同一类不一致。
- **所有错误统一改 409（否决）。** 伪造标记、畸形文档不是并发冲突；统一 409 会诱导客户端刷新重试，掩盖真正的契约错误。

## Consequences

- **补齐写入不进 `recoveryReceipt`。** 回执只回显客户端声明的项；补齐结果由客户端下一次读取账本时收敛。
- **可能产生孤儿 `present` 行。** 节点不在来件文档但输出被补齐时，恢复表会多一条 present；下次加载时恢复逻辑会按账本把卡片补回来。相比「结果永久不可用」，这是更小的一害。
- **每次保存多一次按提交的输出键查询。** 有进程内缓存，按 `submission_id` 去重。
- **`unchangedPrimaryApply` 快路径在存在补齐写入时禁用**，保证对齐不会被版本号快速路径跳过。
- **门控测试**用 1330 / 432 / 1541 三种形状做夹具；真实画布在改动前已被成功保存过，不能作为重放证据。
