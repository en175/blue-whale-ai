## 1. 问题陈述

### 1.1 现象

火山方舟豆包模型的上下文缓存（Context Cache）采用**时间维度计费**：

- **存储费**：¥0.017 / 百万 tokens / 小时
- 只要缓存条目存活，就持续按小时计费
- 即使没有请求命中缓存，存储费仍然累积
- TTL 过期后缓存条目自动删除，存储费停止

new-api 的计费引擎是**请求驱动的**，只能在每次请求时根据 `cached_tokens` 和倍率算钱，完全没有「按时间累计」的能力。

### 1.2 代码证据（穷举验证）

new-api 的 `PriceData` 结构体（`blue_whale_api/types/price_data.go:21-24`）仅有请求维度的缓存字段：

```go
CacheRatio           float64  // 缓存读取倍率（每请求）
CacheCreationRatio   float64  // 缓存写入倍率（每请求）
CacheCreation5mRatio float64  // Claude 5min 档（每请求）
CacheCreation1hRatio float64  // Claude 1h 档（每请求）
```

全仓搜索以下关键词，**零匹配**：

- `cache.*hour`
- `storage.*ratio`
- `cache.*ttl`
- `cache.*duration`
- `cache.*expire`
- `0.017`

new-api 的核心计费逻辑（`blue_whale_api/service/text_quota.go:181-335`）：

```go
// 缓存读取：命中 token × cache_ratio × base_price
cachedTokensWithRatio = dCacheTokens.Mul(dCacheRatio)

// 缓存写入：写入 token × create_cache_ratio × base_price
cachedCreationTokensWithRatio = dCachedCreationTokens.Mul(dCacheCreationRatio)
```

**整个计算在请求返回时一次性完成，没有时间维度。**

### 1.3 两种模型对比

| 维度 | Claude（new-api 兼容） | 火山豆包（new-api 不兼容） |
|---|---|---|
| 计费方式 | 请求触发（0.1x/1.25x/2x） | 存存活期（¥0.017/百万/小时） |
| 没人请求时 | 不收费 | **仍然收费** |
| TTL 机制 | 5min / 1h（请求触发续期） | 有过期时间（按存储时长收费） |
| 谁决定命中 | 厂商（Claude API） | 厂商（火山方舟） |
| new-api 记录 | ✅ 每请求的 cached_tokens | ❌ 无法记录存储时长 |

## 2. 火山缓存计费模型（详细）

### 2.1 官方定价（context7 查证）

| 模型 | 输入价（¥/百万） | 输出价（¥/百万） | 上下文缓存（¥/百万/小时） |
|---|---|---|---|
| Doubao-Seed-2.0-pro | 3.2 | 16 | 0.017 |
| Doubao-Seed-2.0-lite | 0.6 | 3.6 | 0.017 |
| Doubao-Seed-2.0-mini | 0.2 | 2.0 | 0.017 |
| Doubao-1.5-pro-32k | 0.8 | 2.0 | 0.017 |

**关键特征**：
- 所有豆包模型统一存储费率 ¥0.017/百万/小时
- 存储费独立于请求费，是**时间维度**的持续计费
- 缓存命中时，请求的 token 价格可能折扣或免费（但具体折扣率需确认火山最新文档）

### 2.2 TTL 与计费周期

- 缓存条目创建后开始计费
- 每小时扣一次存储费（¥0.017 × 缓存 token 量 / 百万）
- TTL 到期后缓存条目被删除，存储费停止
- 请求命中缓存时 TTL 可能续期（需确认火山行为）

### 2.3 费用估算示例

假设 Doubao-Seed-2.0-pro 缓存了 10000 tokens：

```
存储费 = 10000 / 1,000,000 × ¥0.017 × 存活小时数
       = ¥0.00017 × 存活小时数
       = ¥0.00408/天（约）
```

单次看起来很小，但高并发场景下大量缓存条目持续存活，费用会累积。

## 3. 短期方案（已确认执行）

### 3.1 决策

**火山和 new-api 双方关闭缓存，走纯直连。**

### 3.2 执行清单

| 操作 | 位置 | 效果 |
|---|---|---|
| 关闭上下文缓存功能 | 火山方舟控制台 → 模型推理 → 上下文缓存 | 火山不创建缓存，不收存储费 |
| 不配 `cache_ratio` | new-api 后台 → 模型管理 → 缓存倍率 | 前端缓存列显示 `—`，不给用户折扣 |
| 调用时不传 cache 参数 | new-api 默认中转行为 | 火山不建缓存条目 |

### 3.3 验证

- 火山后台确认上下文缓存开关为关闭
- new-api `cache_ratio` 字段为空或 1
- 前端 DIRECTORY 视图缓存列为 `—`
- 火山月度账单中无「上下文缓存存储费」条目

## 4. 长期方案设计（三选一）

### 方案 A：上游账单对账（推荐）

**思路**：new-api 不改计费引擎，另建独立对账模块，从火山 `ListBillDetail` API 拉取月度存储费账单，按模型和时间段分摊到成本核算。

**架构**：

```
火山 ListBillDetail API
    ↓ （月度/日度拉取）
独立对账模块（system_task）
    ↓ （按模型分摊存储费）
成本报表 / 利润分析
```

**优点**：
- 不改 new-api 核心计费引擎，风险低
- 存储费精确对账，不遗漏
- 可扩展到其他有类似计费模式的厂商

**缺点**：
- 存储费是事后对账，不能实时反映在用户账单上
- 需要火山企业账号 API 权限
- 对账模块需要单独开发和维护

**适用场景**：内部成本核算、利润分析、月度财务报表

### 方案 B：计费引擎扩展（不推荐）

**思路**：扩展 `PriceData` 结构体，增加时间维度的缓存字段，在计费引擎中支持按时间累计。

**新增字段**：

```go
CacheStorageRate  float64 // 缓存存储费率（¥/百万/小时）
CacheStorageTTL   int     // 缓存存活时间（秒）
```

**优点**：
- 理论上可以在请求级别精确计费
- 模型统一

**缺点**：
- new-api 不跟踪缓存条目的创建和过期时间
- 计费引擎需要大幅重构（从请求驱动 → 混合驱动）
- 改动面太大，影响所有计费路径
- 火山的 TTL 续期行为不确定，难以精确模拟

**不推荐原因**：改动成本远大于收益，且精度无法保证。

### 方案 C：混合模式（备选）

**思路**：请求维度走 new-api 现有 `cache_ratio`（给用户缓存命中折扣），存储费走独立对账模块（方案 A 的子集），两者在利润分析层合并。

**架构**：

```
请求计费：cache_ratio × base_price → new-api 现有逻辑
存储费对账：ListBillDetail → 独立模块 → 成本层
利润 = 用户支付（new-api） - 上游成本（请求费 + 存储费）
```

**优点**：
- 用户能看到缓存折扣（体验好）
- 存储费不遗漏（成本准）
- 两层解耦，各自演进

**缺点**：
- 需要先开火山缓存功能
- 用户折扣和上游存储费之间的利润差需要监控
- 比方案 A 多一层复杂度

**适用场景**：决定开火山缓存并给用户折扣后的长期运营

## 5. 推荐路径

```
当前 → 方案 A（对账模块）
         ↓
     决定开缓存？
         ↓
    是 → 方案 C（混合模式）
    否 → 维持方案 A
```

1. **第一步（本 issue 范围）**：确认方案 A 设计，不写代码
2. **第二步（后续 issue）**：实现方案 A 对账模块（独立 system_task，拉火山账单，分摊到模型）
3. **第三步（条件触发）**：如果决定开火山缓存给用户折扣，升级到方案 C

## 6. 兼容策略

### 6.1 与现有 `cache_ratio` 体系的关系

- 短期：火山模型不配 `cache_ratio`，与现有体系不冲突
- 长期（方案 A）：`cache_ratio` 仍不配，存储费走对账模块，两套独立
- 长期（方案 C）：`cache_ratio` 配缓存命中折扣，存储费走对账模块，两套协同但解耦

### 6.2 与 Claude 缓存的共存

- Claude 继续用 `cache_ratio` / `create_cache_ratio` / `CacheCreation5mRatio` / `CacheCreation1hRatio`
- 火山走独立的对账路径
- 两者在模型广场前端不区分（用户看到的都是缓存价格），但后端计费路径不同

### 6.3 前端展示

- 短期：火山模型缓存列为 `—`（不配 `cache_ratio`）
- 长期（方案 C）：火山模型缓存列可显示命中折扣价，但不含存储费
- 存储费属于上游成本，不对用户展示
