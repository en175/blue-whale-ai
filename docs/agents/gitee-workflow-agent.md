# Gitee 工作流（给 Agent 读）

给通过 Gitee MCP 或 OpenAPI 改工单的 Agent（Claude、Codex 等）。人看
[gitee-workflow.md](./gitee-workflow.md)，两份是同一套流程（2026-10-10 生效）。
适用于玄浮企业下所有项目：需求、任务、缺陷三种类型是企业级配置，各项目共用。

## 常量

旧流程里的「开发完成态」（任务=已完成、需求=待发布、缺陷=已修复）在新流程里**不存在**。不要拿「待发布」顶替它：
待发布的意思是「测试站已经测过了」，要由测试来点。

拿不准时用 `list_issue_type_states { enterprise_id: 16660949, issue_type_id: <类型> }` 实时读，以返回为准。

## 每个开发节点 Agent 做什么

| 节点 | 状态 | 同时要做 |
| --- | --- | --- |
| 开工（建 worktree 或开始改代码，且绑定了工单） | 起点 → 开发中 4336298 / 修复中 4336305 | 按仓库约定认领负责人 |
| 本地提交 | **不改** | — |
| 开 PR | **不改** | 评论进度和 PR 链接；仓库约定的标签照打 |
| PR 合并 | **不改** | 评论已合并、等测试站部署 |
| 改动已经部署到测试站，并且确认过 | → 测试-待测试 4514469 | 评论里 @测试（蓝鲸项目是 `@ouweich`），写清测什么、怎么测 |
| 测试打回后修好，重新部署到测试站 | 测试-测试打回 → 测试-待测试 4514469 | 评论修了什么，@测试 |
| 子任务跟着父需求一起测（跳步 A） | 合并且部署后，开发中 → 待发布 4336304 | 评论说明随父需求测 |
| 父需求下的子任务都到待发布或已上线 | 父需求 → 测试-待测试 4514469 | @测试；父需求是产品建的，只有人让你提测时才改 |
| 不用测的文档、配置、调研、答疑（跳步 C） | 合并后，或结论发出后 → 已上线 4336299 | 评论结论或 PR 链接 |

「测试站上有没有这次改动」以测试站实际在跑的版本为准，不以「合了 PR」为准。各仓测试站跟哪个分支、怎么核部署，
看各仓自己的 git-workflow 文档。核不了就不改，只评论，并告诉人。

### 开工前先看当前状态

| 当前状态 | 怎么做 |
| --- | --- |
| 待评审、待排期、待确认 | 正常开工 |
| 测试-测试打回、生产-验证打回 | 返工：改回开发中或修复中，然后继续 |
| 开发中、修复中 | 停下，报告给人：可能别人或另一个会话在做 |
| 测试-待测试、待发布、生产-待验证 | 停下，报告给人：已经在测或在等发版 |
| 已上线、已关闭 | 停下，报告给人 |

## Agent 不能点的格

这些归人点，Agent 不替人改：

- **测试-测试打回**，以及**从测试-待测试改到待发布**：测试来点。
- **生产-待验证、生产-验证打回、从生产-待验证改到已上线**：发版的人、测试或产品来点。
- **跳步 B（待发布 → 已上线）**：发版的人来点。只有人明确让 Agent 代为发版时，Agent 才能点。
- **已关闭**：负责人来点。它表示作废，**做完了绝不点它**，做完是已上线。

## 硬规矩

- 读状态只看细状态 `issue_state.title`，不看粗状态 `state`。粗状态只有 open / progressing / closed / rejected，
  测试-待测试和开发中都是 progressing。按细状态筛选用 `list_enterprise_issues` 带 `issue_state_ids=<id>`。
- 改状态时**绝不带 `description`**：`update_enterprise_issue` 会用它整体覆盖正文。补标签时 `label_ids` 也是整体覆盖，
  先读现有标签，合并后再写回。
- 只走画布上的线。往前只能走主线和跳步 A、B、C（需求另有待评审 → 开发中这一条），往回可以退到任意一格。
  接口拒绝了就停下问人，不换一条路绕过去。
- 状态改失败：先读工单，确认到底改没改成，不盲目重试；仍然失败就在汇报里置顶写「⚠️ 工单状态未同步」，
  附上工单号、目标状态名和 id。
- 缺陷不能当子工作项（Gitee 返回 400），只能是顶层单。需求和任务可以挂父单。
- 「已修复-待验证」标签（344168629）是旧流程里缺陷合并后打的。新流程用「测试-待测试」状态表达这件事，不再打这个标签。
