## 0. 一句话结论

后端 5 个接口全部就绪，字段足以填满 v1.3 原型的每一格。前端要动的有两类：

- **4 处破坏性收缩**（接口不再回某些字段，照旧代码写会拿到 `undefined`）：`orders` 不再回 `trade_no`、`credit-lots` 不再回 `biz_type`/`biz_id`、`consumptions` 不再回 `job_id`、订单 `status` 收敛成**三态**。
- **3 类新增能力**：三个页签的**日期区间筛选**、已消耗的**任务类型 / 模型筛选**、`credit-lots` 新增 `product_name`。

逐项改动清单见 §5。

## 1. 全局约定

| 项 | 值 |
| --- | --- |
| 全局前缀 | `api`（**不是** `/api/v1`） |
| 鉴权 | HttpOnly cookie `bw_session`，浏览器自动携带；前端**不附加任何令牌头** |
| 成功信封 | `{ "code": 200, "data": …, "msg": … }` |
| **例外** | `GET /api/account/export` 是**裸二进制流**，不套信封（见 §3.5） |
| 分页 | 全部 **offset 分页**：`page` 从 1 起，`page_size` 默认 20、**上限 100**，响应带 `total` |
| 时间 | RFC3339、**北京时间墙钟字面量**（`+08:00`）。前端直接按字面量格式化，**不要再做时区换算** |
| 时间入参 | `created_from` / `created_to` 必须**带时区**：`YYYY-MM-DDTHH:MM:SS` + 秒后可带小数 + `Z` 或 `±HH:MM`。传 `2026-09-01` 这种裸日期 → **400** |
| 积分单位 | 一律**整数积分**；人民币金额字段名带 `_fen`，单位是**分**，展示前 `/100` |
| 越权 | 所有用户侧接口的 `user_id` **只来自会话**，query 里传什么都不认 |

## 3. 接口契约

### 3.1 `GET /api/usage/token`

**响应**

```jsonc
{
  "code": 200,
  "data": {
    "credits": 12345,
    "by_source": [{ "source": "purchased", "credits": 11145 }],
    "expiring": [
      { "credits": 1200, "expires_at": "2026-12-01T00:00:00+08:00", "source": "purchased" }
    ]
  }
}
```

**本期前端只取 `credits`。** 原型 v1.3 的汇总区只有「当前积分余额」一张卡、**不展示任何到期信息**（口径⑥），所以 `expiring` 与 `by_source` 本期没有消费方 —— 后端保留它们是因为别处（余额卡片、充值弹窗）还在用，**不是给这一页用的**。

⚠️ `expiring` 的取数口径已于 10-08 变更（31 天窗口 → 全部临期、上限 200 条），本轮**未再改动**；10-08 那篇的 §1 仍然有效。

### 3.2 `GET /api/account/orders` — 订单记录 【破坏性】

**请求**

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `page` | number | 否 | `1` | |
| `page_size` | number | 否 | `20` | 上限 100 |
| `status` | string | 否 | 空 = 全部 | **用户侧三态**：`pending` / `paid` / `expired`。**传内部态（`paid_pending` / `grant_failed` / `failed`）→ 400** |
| `created_from` | string | 否 | — | RFC3339，下单时间下界（闭区间） |
| `created_to` | string | 否 | — | RFC3339，下单时间上界（闭区间） |

**响应**

```jsonc
{
  "code": 200,
  "data": {
    "items": [
      {
        "product_name": "自定义充值 · 600 积分",
        "product_type": "custom",
        "amount_fen": 4000,
        "credits": 600,
        "bonus_credits": 0,
        "status": "paid",
        "created_at": "2026-09-29T14:32:00+08:00",
        "paid_at": "2026-09-29T14:32:41+08:00",
        "credits_valid_months": 24
      }
    ],
    "total": 7
  }
}
```

**⚠️ 不再有 `trade_no`。** 订单号是系统内部排查锚点，用户侧**全链路不展示**（订单列表、积分明细、导出都不含）—— 原型的「订单编号」列与「复制订单号」操作列都要删。

**状态三态**（后端已收敛，前端**不要再做映射**）

| 后端 `status` | 文案 | pill |
| --- | --- | --- |
| `pending` | 待支付 | gray |
| `paid` | 已到账 | 绿（默认） |
| `expired` | **已取消** | gray |

后端侧的收敛规则（供理解，前端不用实现）：`paid_pending` / `grant_failed` / `paid` → `paid`；`failed` / `expired` → `expired`。
⚠️ `expired` 的中文是「**已取消**」不是「已过期」——这是历史命名，**不要照字面译**。

**「到账积分」列**：`status === "paid"` 时展示 `credits + bonus_credits`；其余状态一律展示「**—**」，**不展示 0**（查不到 ≠ 0）。注意按三态收敛后，「支付成功待到账」与「到账异常」都归入 `paid`，所以它们**也展示积分**。

### 3.3 `GET /api/account/credit-lots` — 积分明细 · 已获取 【破坏性】

**请求**：`page` / `page_size` / `created_from` / `created_to`（日期按**批次获取时间**过滤）

**响应**

```jsonc
{
  "code": 200,
  "data": {
    "items": [
      {
        "lot_id": "18401",
        "source": "purchased",
        "amount": 3000,
        "remaining": 1200,
        "created_at": "2024-12-01T09:12:00+08:00",
        "expires_at": "2026-12-01T00:00:00+08:00",
        "product_name": "自定义充值 · 3,000 积分"
      }
    ],
    "total": 3
  }
}
```

**⚠️ 不再有 `biz_type` / `biz_id`。** 原来的 `biz_id` 是订单号，前端此前直接渲染在「获取详情」列 —— 正是口径③明令不许出现的东西。替代品是新增的 `product_name`。

**口径**

| 原型列 | 取值 |
| --- | --- |
| 获取时间 | `created_at` |
| 获取来源 | `source` → §4.1 文案表 |
| **获取详情** | `product_name`；当 `remaining < amount` 时拼 ` · 剩余 {remaining}`。`product_name` 为 `null` 时（非充值批次）回落成 `{来源文案} {amount} 积分` |
| 积分生效时间 | **与「获取时间」同为 `created_at`** —— 本项目批次一写入即生效，没有延时生效，两列渲染同一个值 |
| 积分到期时间 | `expires_at`；**空串 = 永久有效**，渲染成「永久有效」，**不要**渲染成 `1970` 或空白 |
| 积分值 | `amount` |

- 临期标黄的阈值后端不提供，**由前端定**（建议 ≤ 30 天）。
- 本列表是**全页唯一的到期信息入口**（汇总区不展示到期）。

### 3.4 `GET /api/account/consumptions` — 积分明细 · 已消耗 【破坏性】

**请求**

| 参数 | 类型 | 必填 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `type` | string | 否 | 空 = 全部 | **逗号分隔多值**，如 `consume,expire`。**未知取值会一路抛到账单侧并返回 502**，前端只传这两个已知值即可 |
| `page` / `page_size` | number | 否 | `1` / `20` | 上限 100 |
| `created_from` / `created_to` | string | 否 | — | RFC3339，按消耗时间过滤 |
| `task_type` | string | 否 | — | `generation_jobs.type`，**原始 key**（如 `text2video`），不是中文 |
| `model` | string | 否 | — | `model_id`（如 `doubao-seedance-2.5`），**不是** `model_label` |

**响应**

```jsonc
{
  "code": 200,
  "data": {
    "items": [
      {
        "id": "res:7",
        "type": "consume",
        "direction": "out",
        "title": "视频生成 · seedance-2.5 1080p 5s",
        "credits": 476,
        "status": "done",
        "created_at": "2026-09-29T15:02:00+08:00",
        "settled_at": "2026-09-29T15:06:00+08:00",
        "task_type": "text2video",
        "model_id": "doubao-seedance-2.5",
        "model_label": "Seedance 2.5",
        "prompt": "一只长毛蓬松的布偶猫安静地坐在窗边…",
        "specs": { "resolution": "1080p", "duration": "5" },
        "lot_source": null,
        "lot_created_at": null
      }
    ],
    "total": 4
  }
}
```

**⚠️ 不再有 `job_id`。** 任务 ID 同为内部锚点，用户侧全链路不展示（含导出）—— 原型的「任务 ID」列要删。

**口径**

- **「任务详情」列 = 提示词。** `prompt` 超长截断（截断长度前端定）；任务没有提示词时展示「**—**」，不要造占位文案。⚠️ **不要**再用 `specs` 渲染这一列 —— 口径②明确「规格信息（时长 / 分辨率）本期不展示」。`specs` 字段仍在响应里，本期不渲染。
- **过期核销行**（`type === "expire"`）：`task_type` / `model_id` / `model_label` / `prompt` **全为 `null`**，此时「任务详情」列改渲染批次上下文：

  ```
  {lot_created_at 的日期} {lot_source 文案}批次        // 例：2024-12-01 充值到账批次
  ```

  `lot_source` 走 §4.1 的批次口径文案表；`lot_created_at` 是 RFC3339，按原型只展示**日期部分**。两者任一为 `null` 时展示「—」（老数据可能取不到，属正常）。
  「任务类型」列对 `expire` 行展示「**过期核销**」（红色标签，与 `consume` 同表不同色）。
- **`credits` 是最终值、唯一金额。** 任务失败全额退回时，这一行的 `credits` 就是 **0**，`type` 恒为 `consume`、`direction` 恒为 `out` —— **不会**另起一行 `+476`。所以展示时：`credits === 0` 直接渲染 `0`（**不要渲染成 `-0`**）。
- 「已过期」并入本页签的方式就是 `type: "consume,expire"` 一次取两条，前端按 `type` 上标签色区分。

**⚠️ 筛选的实现代价与上限**

`task_type` / `model` 这两个字段在 backend 自己的任务表里，billing 账本查不到，所以后端是「先按条件查出一批 `job_id`，再把这批 id 下推给账本过滤」——**分页与 `total` 因此仍然准确**。代价是命中集合有上限：

> 命中超过 **10000** 条 → 返回 **400**，`msg` 为「按任务类型/模型命中的任务超过 10000 条，请先缩小日期范围」。

前端应在有这两个筛选时**引导用户先选日期范围**，并把这条 400 的 `msg` 原样提示出来。

⚠️ **这两个筛选同时会滤掉「过期核销」行** —— `expire` 行没有 `generation_job_id`，下推的 `IN (...)` 天然把它排除在外。所以「已消耗」页签一旦启用了任务类型 / 模型筛选，过期核销行就不在结果里了。这是可接受的行为，但**界面上要能看出来**（例如筛选生效时给个提示），否则用户会以为那笔核销丢了。

**⚠️ 下拉选项后端不提供。** 后端没有「该用户用过哪些任务类型 / 模型」的枚举接口。本期两个办法：① 前端从已加载的行里累积去重（会随翻页增长，不完整）；② 先不做这两个筛选器，只做日期。**建议先按 ② 上，选项接口另开单。**

### 3.5 `GET /api/account/export` — 导出明细 【裸二进制】

**请求**

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `scope` | string | **是** | `orders` \| `gain` \| `consume`，非法值 → 400 |
| `fields` | string | **是** | 逗号分隔的**字段 key**（见下表）。未知 key → 400。传**空串 = 全字段**；**省略该参数与传空串等价** |
| `status` | string | 否 | 仅 `scope=orders` 有效，语义同 §3.2（三态） |
| `type` | string | 否 | 仅 `scope=consume` 有效，语义同 §3.4 |
| `created_from` / `created_to` | string | 否 | 三个 scope 都有效 |
| `task_type` / `model` | string | 否 | 仅 `scope=consume` 有效，语义同 §3.4（同样受 10000 上限约束） |

**响应**：**裸 xlsx 二进制流，不套 `{code, data, msg}` 信封。**

```
HTTP/1.1 200 OK
Content-Type: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet
Content-Disposition: attachment; filename="export.xlsx"; filename*=UTF-8''<URL 编码后的中文名>
```

⚠️ **前端必须绕开统一请求封装的信封解析**（`doRequest` 会把响应体当 JSON 解）。用原生 `fetch` 取 blob 并自行触发下载。

**字段 key ↔ 列头**（`fields` 传 key，列头由后端按同一份定义写，前端弹层文案请用**同一份中文**）

`scope=orders`

| key | 列头 |
| --- | --- |
| `created_at` | 下单时间 |
| `product_name` | 商品名称 |
| `amount_yuan` | 支付金额 |
| `credits` | 到账积分 |
| `status` | 状态 |

`scope=gain`

| key | 列头 |
| --- | --- |
| `created_at` | 获取时间 |
| `source` | 获取来源 |
| `detail` | 获取详情 |
| `activated_at` | 积分生效时间 |
| `expires_at` | 积分到期时间 |
| `amount` | 积分值 |

`scope=consume`

| key | 列头 |
| --- | --- |
| `created_at` | 消耗时间 |
| `task_type` | 任务类型 |
| `model_label` | 模型 |
| `detail` | 任务详情 |
| `credits` | 消耗积分 |

**列集合与原型逐项对齐**：orders **无**「订单编号」、consume **无**「任务 ID」、gain **无**独立「剩余」列（剩余并入「获取详情」）。

**口径**

- 导出**不受分页限制**，是当前筛选条件下的**全部记录**，后端翻页取到上限为止。
- 单次上限 **10000 行**；被截断时末行会写一行「⚠️ 仅导出前 N 条，共 M 条」——前端无需额外处理，但**不要**因此提示「导出成功」而不提截断。
- 字段勾选是前端弹层的事，后端只按 `fields` 裁列；**表头中文由后端写**，弹层勾选项文案与表头用同一份。

## 4. 文案映射

### 4.1 批次口径 `source`

用于 `credit-lots.source`、`usage/token` 的 `by_source` / `expiring`，以及 §3.4 过期核销行的 `lot_source`。

| `source` | 文案 |
| --- | --- |
| `purchased` | 充值到账 |
| `bonus` | 充值赠送 |
| `gift` | 赠送 |
| `compensation` | 补偿 |
| `daily` | 每日赠送 |
| `invite` | 邀请奖励 |
| `register` | 注册赠送 |
| `redeem` | 兑换 |
| `subscription` | 订阅 |

### 4.2 流水口径 `type`

用于 `consumptions.type`。

| `type` | 文案 | 出现在 |
| --- | --- | --- |
| `consume` | 任务消耗 | 已消耗 |
| `expire` | 过期核销 | 已消耗 |
| `recharge` | 充值到账 | （`direction=in`，**不进本页签**） |
| `bonus` / `gift` / `compensation` / `daily` / `invite` / `redeem` / `subscription` | 同 §4.1 文案 | 同上 |
| `refund` | 退款回收 | **目前没有产生者**，本期不会出现 |

> ⚠️ **同一件事两个词**：批次写 `purchased`，流水写 `recharge`。混用会让某一张表里出现空白。

## 6. 本期不做 / 后端明确不提供

| 项 | 说明 |
| --- | --- |
| 订单号、任务 ID 的用户侧展示 | **全链路不留**：订单列表、积分明细、导出都不含。唯一入口是系统内部排查 |
| 「已退款」订单态 | **不存在**（订单状态机没有这个出口），不要为它写分支 |
| 「已退回」页签 | 不做 —— 退回不是独立流水类型，就是 `consume` 行结算到 0（§3.4 口径） |
| 任务规格（时长 / 分辨率）列 | 本期不展示，`specs` 字段虽在但**不渲染** |
| 汇总区到期信息（统一有效期卡 / 最近到期批次卡） | 都不设；到期只以「已获取」逐行为准 |
| 消耗顺序说明入口 | 服务端固定规则，本期不做用户侧说明 |
| 筛选下拉选项接口 | 后端不提供（§3.4） |
| `usage/token` 的 `expiring` / `by_source` | 接口保留，**本页无消费方**（§3.1） |

## 7. 错误语义

| HTTP | 场景 | 前端表现 |
| --- | --- | --- |
| 400 | 参数非法：`status` 传内部态、`created_*` 不是带时区的 RFC3339、`fields` 含未知 key、`scope` 非法、任务类型/模型命中超上限 | 提示 `msg` 原文 |
| 401 | 会话失效 | 走既有的登录引导 |
| 502 | billing 报错（含 `type` 传了未知取值） | 「加载失败」+ 重试 |
| 503 | billing 未配置/不可达 | 同上，文案可提示「稍后重试」 |

## 8. 后端口径自检（供后端回归，前端可忽略）

- `Σ by_source == credits` 恒等仍成立。
- 失败任务的消费行 `credits === 0`，且**不存在**独立的退回行 / 「已退回」页签。
- 导出三 scope 的列集合与 §3.5 表逐项一致；orders 无 `trade_no`、consume 无 `job_id`。
