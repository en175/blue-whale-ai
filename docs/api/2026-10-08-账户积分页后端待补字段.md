## 需后端处理（3 项）

### 1. `usage/token` 的 `expiring[]` 缺批次标识 —— 最需确认

**现状**：`expiring[]` 只回 `credits` / `expires_at` / `source`（`usage.controller.ts:42-46`）。

**问题**：这是「最近到期批次」，但返回项**没有 lot 标识**。前端要拿它去 `credit-lots` 里定位是哪一批（做「· 剩余 1,200」的回落、或点进去跳批次），只能靠 `expires_at + source + credits` 三元组猜 —— 同一天到期、同 source、同积分的两批会撞。

**需后端给**：
```jsonc
"expiring": [
  { "lot_id": "18401", "credits": 1200, "expires_at": "...", "source": "purchased" }
]
```
即补一个 `lot_id`（与 §3.3 `credit-lots` 的 `lot_id` 同源）。

**同时请说明**：`expiring[]` 的取数口径 —— 是「所有临期批次」还是「按 `expires_at` 升序的前 N 条」？取几条？前端要据此决定是取 `[0]` 还是全渲染。

---

### 2. `consumed` 的「任务详情」列缺字段

**现状**：`consumptions` 只回 `title`（预渲染串，如「视频生成 · seedance-2.5 1080p 5s」）和 `prompt`（`account.controller.ts:147-148`）。

**问题**：页面「任务详情」列要展示的是**画质 / 时长**（原型示例 `1080p 5s`），这**不是独立字段**。它现在埋在 `title` 的拼接串里，前端要么按分隔符猜解析（脆），要么改展示 `prompt`（语义变了）。

**需后端确认**（二选一）：
- (a) 契约就是让前端展示 `prompt`（那「任务详情」列的语义要产品重定义）；或
- (b) 给一个独立的 `detail` 字段（画质·时长），与运营面管理端的同名列对齐。

**请后端与产品拍板后回一句**。

---

### 3. `task_type` 的取值稳定性 + 是否给中文名

**现状**：`task_type` = `generation_jobs.type`，**自由文本**（`job-repo.ts:156` 注释：后端不写死白名单），示例 `text2video`。

**问题**：自由文本意味着前端**无法穷举**「任务类型」列的取值范围，只能回退成**原始 key 原样显示**（前端已有这份兜底：`web/src/admin/taskTypeLabels.ts` 的 `taskTypeLabel()`，未收录类型返回 key 本身）。

**需后端确认**：`task_type` 的取值集合是否**已收敛**（`text2video` / `image` / `video` / `audio` / `video_subtitle_erase` …）？若已收敛，请给一份**权威取值枚举**，前端据此补全中文映射；若仍在演进，前端接受「未收录就显示英文 key」这个兜底，**不需后端改动**。

### 已知矛盾（请后端确认口径）

**「积分有效期」取值来源**：对接文档 §1 映射表（line 23）写的是「`GET /api/recharge/tiers` 的 `credits_valid_months`」。但 `tiers` 是**逐档**返回该字段（`recharge.controller.ts:79` 注释：「逐档回…页面级写死任何一个数都会是假话」），**没有页面级的单一值**。前端汇总卡要展示一个数，需后端明确：

- 取默认档位 / 推荐档位的值？还是
- 有效期本身是**用户级配置**，应有独立字段（那 `tiers` 就不是正确来源）？
