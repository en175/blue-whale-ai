## 1. `GET /api/usage/token` —— `expiring` 口径已改

### 变了什么

原来只回**31 天窗口内、最多 5 条**。后果是：用户最近一批 40 天后到期时，这个数组是**空的**，汇总卡误报「暂无即将到期的批次」。

现在：**所有带到期时间、尚未过期、且未用完**的批次，按 `expires_at` 升序，**上限 200 条**。注意这比「未过期未用完」更窄——SQL 的三个谓词是 `expires_at IS NOT NULL` / `expires_at > NOW()` / `remaining > frozen`。`REGISTER` 来源是**永久**的（`GrantPolicy.expiryFor` 对它返回 `null`，`expires_at` 落库为 `NULL`），不进这个数组，所以只持永久积分的用户这里会是空数组。

### 形状（未变）

```jsonc
"expiring": [
  { "credits": 1200, "expires_at": "2026-12-01T00:00:00+08:00", "source": "purchased" }
]
```

| 字段 | 说明 |
| --- | --- |
| `credits` | 该批的**可用量**（上游已按 `remaining − frozen` 算好） |
| `expires_at` | RFC3339，北京时间墙钟字面量 |
| `source` | **批次口径**（`purchased` / `bonus` / …），不是流水口径的 `recharge` |

### 前端怎么用

- 「最近到期批次」取 **`expiring[0]`**。后端已按到期升序排好，不要再排。
- 数组为空 = 该用户没有被提醒的批次（没有**带到期时间、尚未过期、且未用完**的批次；只持永久积分的用户就是这种）。
- ⚠️ **字段名对齐**：后端叫 `credits`，前端的 `CreditsLotPreview` 叫 `remaining`（`types.ts:4`）。接的时候映射一下。

### 同一响应里另外三条口径

（这三条原本写在控制器的注释里，本轮改动删掉了那条含过期口径的注释块，搬到这里）

- `credits` 是**整数积分**（账本单位），不是 new-api 的 quota——用户看到的数就是 billing 记的数，中间不再有一次 50,000 换算。
- `expiring` **不是第二个金额**——这些批次的钱**已经算在 `credits` 里**了，它是同一笔余额的一个切片。
- 要**完整的批次台账**（含已用完、已过期、永久有效）走 `GET /api/account/credit-lots`；`expiring` 不是它。

### 覆盖 v1 的两条

本文件是 v1（[`2026-09-30-account-points-and-orders-api.md`](./2026-09-30-account-points-and-orders-api.md)）的后续，v1 里关于 `expiring` 的两条已被本轮改动覆盖，**照 v1 读会读反**：

- v1 §3.1「`expiring` 是『**临期批次**』子集，不是全部批次」——**不再成立**。后端现在既不按时间窗筛、也不设任何阈值：`expiring` 就是 §1 那条口径的**全部**批次（带到期时间、未过期、未用完），不是「最近会到期的那几条」。
- v1 §3.3「原型 :318 把临期批次标黄（`.expire-warn`），阈值前端定（建议 ≤ 30 天），后端不提供」——后端现在**连窗口都不给了**，所以那个「即将到期」黄色阈值**完全**是前端的判断，v1 的「建议 ≤ 30 天」是仅存的参考。**这条阈值必须实现**：没有它，`expiring[0]` 上一个 2028 年的到期日也会被涂成「即将到期」。

### 不加 `lot_id`

**明确不加。** 理由：

- 页面现在不用它——`CreditsLotPreview` 只有 `remaining` + `expiresAt`；
- 卡片只取一条，而 `expiring` 是数组；
- 加它要动 **7 处**（proto → 生成 TS → Java view → Java service → gRPC → client → controller）。

等前端真做出「点进批次」那个交互（汇总卡 → 跳「已获取」页签 → 高亮那一批）再提，那时需求也才说得清。

## 2. `GET /api/account/consumptions` —— 新增 `specs` 字段

### 为什么

「任务详情」列要展示画质·时长。原来的 `title` 是**调用方快照**，Node 侧从来没有调用方传过它，所以恒为空串，这一列渲染成 `—`。

### 形状

每行新增一个字段。注意 `size` 只有图片任务有、`duration` 只有视频任务有，**没有哪一行同时带这两个键**，所以下面分成两个例子：

图片任务：

```jsonc
{
  "id": "...",
  "title": "",
  "task_type": "image",
  "model_id": "seedream-4.0",
  "model_label": "Seedream 4.0",
  "prompt": "一只猫在跑",
  "specs": { "size": "1024x1024", "reference_count": "0" }
}
```

视频任务：

```jsonc
{
  "id": "...",
  "title": "",
  "task_type": "video",
  "model_id": "seedance-2.5",
  "model_label": "Seedance 2.5",
  "prompt": "一只猫在跑",
  "specs": { "resolution": "1080p", "duration": "5", "video": "0", "reference_count": "0" }
}
```

| | |
| --- | --- |
| 类型 | `Record<string, string> \| null` |
| 键 | **小写**，取值为标量的入参键 |
| 值 | 一律字符串，且**已整体转小写**（`String(v).toLowerCase()`，不是保留原样） |
| `null` 的含义 | 查不到该任务（跨库历史、已清理）；与 `prompt` 的「有任务但没写提示词」是**两回事** |

### 值的来源

后端把 `generation_jobs.input` 过一遍 **`extractSpecs(input, taskType)`** —— 与**计费同一份归一函数**（`backend/libs/shared/billing/billing-specs.ts`）。

这一点是刻意的：页面显示的规格与当初扣钱用的规格**逐字一致**。如果后端另写一个「展示用拼串函数」，它会和计费口径漂移——页面说 1080p、账单按 720p 扣，这类不一致最难查。

**同时**：`extractSpecs` 会**剥掉** `prompt` / `title` / `provider_credential`。最后一个是上游密钥，绝不能出现在响应里。

**另外**：`duration` 本身也是**派生**键——`extractSpecs` 在 `input` 带 `duration_basis_seconds` 时用它**覆写** `duration`（计费按基准时长折算）。所以编辑类任务显示的秒数是**源视频**的时长，不是用户这次填的目标时长。

### ⚠️ 会多带 3 个派生键

`extractSpecs` 为了计费会补三个折算键，前端会看到：

| 键 | 含义 |
| --- | --- |
| `reference_count` | 参考素材数（数组长度折算成标量） |
| `video` | `0` / `1`，本次输入**含不含**视频 |
| `video_input_seconds` | 输入视频时长（秒）；量不到时**整个键不出现** |

它们不属于「原始规格」。前端排版时按白名单取键即可，别盲铺。

### 前端建议的显示规则

后端**不自带拼串**（那样就回到「两处拼法」的老问题）。前端按下面这条白名单排：

```
键顺序：resolution → size → duration → aspect_ratio
逐个取非空值；duration 的值补 's'（值非正数时整项不显示）；用 ' · ' 连接；全空则显示 '—'
```

`duration` 非正数不显示是必需的：`edit` 任务对自适应时长冻结 `duration: -1`，照补 's' 会渲染出 `-1s`。

例：

| `specs` | 显示 |
| --- | --- |
| `{ resolution: "1080p", duration: "5" }` | `1080p · 5s` |
| `{ size: "1024x1024" }` | `1024x1024` |
| `{ resolution: "1080p", duration: "-1" }` | `1080p` |
| `{}` / `null` | `—` |

### 字段改名

原前端字段叫 `detail`，与后端对不上。**统一叫 `specs`**。

### ⚠️ 顺带一条一致性提醒

导出 xlsx 里的「任务详情」列走的是 `prompt ?? title`（`account-export.ts`），**暂未跟着改成 specs**——所以页面与导出这两个同名列目前显示的东西不一样。要对齐的话得先定「拼法写在哪一侧」，后端不擅自改。

## 4. 「积分有效期」——这是产品口径，后端定不了

事实：

- `GET /api/recharge/tiers` 是**逐档**返回 `credits_valid_months`，**没有页面级单值**。控制器注释自己写着「页面级写死任何一个数都会是假话」。
- **单位还不一致**：前端的 `CreditsSummary.validityYears` 是**年**，后端回的是**月**。

要产品拍板：

- 取哪个档的值（默认档 / 推荐档）？还是
- 「有效期」本质是**用户级配置**，应该独立给一个字段，而不是从档位推？

定了之后后端再动。
