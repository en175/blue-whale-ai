# Frontend feature delivery

用于 `web/` 的新功能交付。先遵守仓库根目录 `CLAUDE.md`，并在进入实施阶段前加载 `frontend-delivery` skill。

## Non-negotiable rules

- 工单是可选上下文，不是入口条件。用户直接说明的需求只要足够表达目标和主流程，即可进入需求澄清。
- 未获用户对“前端可执行需求”的明确确认，不创建 worktree、不写代码、不安装依赖、不启动服务。
- 需求确认后默认继续产出计划并实施；只有出现实质性方案取舍或高风险改动时才暂停确认。
- 仅可交付 `web/**`。若需要 backend、共享契约、根工具、根规则或 PR 模板改动，停止并要求另建范围明确的 Issue；不得用前端绕过替代跨边界设计。
- 人工 `dev:test` 回归是交付关口。没有用户明确的通过结论，不得宣称功能完成、创建/更新 PR 或合并。
- 不编造登录账号、权限、测试数据、接口行为或验收结论。没有这些信息时，标记为未知，并只提出会改变实现的聚焦问题。

## 0. Intake

接受三种来源，按以下优先级记录事实：

1. 用户给出的 PRD 或需求说明；
2. 可选的 Gitee Issue（先按仓库 Issue 规则读取）；
3. 为澄清歧义而进行的只读代码调查。

没有工单时，不要求用户补工单或套模板。需求至少能说明用户目标、入口或主要使用路径、期望结果；其余信息在需求澄清中补齐。若缺失信息导致两种以上安全但实质不同的前端行为，集中提问，等待回答。

## 1. Gate A — 前端可执行需求

先输出下列 Markdown，不写业务代码。将每一项标为 **已确认**、**合理推断** 或 **待确认**；推断必须说明来自哪条需求或只读代码证据。

```md
# <功能名>｜前端可执行需求

## 目标与范围
- 用户/业务目标：
- 本次包含：
- 明确不做：
- 需求来源：<PRD | 工单 #... | 直接说明；工单可选>

## 用户路径
1. 入口：
2. 主要操作与页面反馈：
3. 成功后的结果或去向：

## 页面与交互规则
- 页面/路由/入口：
- 字段、展示规则和默认值：
- 操作、校验、确认和反馈：
- 状态：加载、空态、无权限、异常、成功：

## 依赖与约束
- API / 数据 / 权限：
- 埋点、兼容性、性能或设计约束：
- 已知测试数据或前置条件：

## 验收清单
- [ ] <可由人工观察的结果>

## 需要你确认的问题
- <只列会改变范围、用户行为、契约或验收标准的问题；没有则写“无”>
```

结尾明确请用户确认或修订该需求，例如：`请确认以上前端需求；确认后我会完成计划并开始实施。`

用户明确确认前，只能继续澄清和只读调查。不要把沉默、继续讨论或“看一下”当作确认。

## 2. Confirmed requirement → worktree and plan

收到确认后：

1. 若有符合状态机前置条件的 Issue，以 `--issue <编号>` 运行仓库的 `start-task-worktree.sh --type feature`；无工单则以 `--no-issue` 运行。所有写入只在新 worktree 和任务分支内进行。
2. 在该 worktree 中加载 `frontend-delivery`。新增服务端状态读写、页面或轮询时，同时读取其 `references/request.md`，采用 TanStack Query 约定。
3. 通过只读代码调查产出完整计划。计划不写笼统步骤，必须包含：
   - 目标、非目标及与 Gate A 验收清单的逐项映射；
   - 受影响/新增的准确文件路径及各自职责；
   - 页面结构、数据流、状态与错误处理；
   - API、权限、路由、埋点和兼容性影响；
   - 测试用例、执行命令及人工回归路径；
   - 风险、假设及不覆盖的内容。
4. 在对话中展示计划和“实施前检查”结论。正常页面功能默认直接实施，不再制造第二个确认关口。

遇到以下任一情况，展示备选方案、影响与推荐项并暂停，等待用户选择：接口/共享契约变更、路由或权限模型变更、公共组件大规模重构、新依赖、数据删除/迁移、安全或隐私风险，或验收标准仍无法确定。代码调查发现需求需要实质改写时，回到 Gate A。

## 3. Implement and verify

按已确认需求与计划实施，始终保持改动在 `web/**`。

1. 为关键业务规则、状态转换、请求参数或组件交互补充可自动化的测试；视觉、登录或跨页面链路留给人工回归。
2. 在开发过程中运行与改动直接对应的测试、类型检查和 lint；如有失败，修复或如实说明，不能跳过。
3. 完成实现后，按 `docs/agents/testing-strategy.md` 运行仓库的验证选择器与它选择的检查。报告实际命令、HEAD 和结果，不把未运行的检查写成已通过。
4. 自动化检查通过后，仅从 `web/` 启动 `npm run dev:test`，等待 Vite 输出 Local URL。它使用测试环境接口；不要同时启动本地 backend、数据库或测试库隧道。
5. 保持服务运行，并交付以下人工回归包：

```md
## 人工回归
- 地址：<Vite Local URL + 目标路由>
- 环境：`dev:test`（测试环境接口；未启动本地 backend）
- 前置条件：<仅列已提供的账号、权限或数据；未知则明确未知>
- 建议回归：
  1. <验收清单对应路径>
  2. <异常/空态/权限等关键边界>
- 已知限制或未覆盖项：<无则写“无”>

请回复“通过”，或回复“不通过 + 复现步骤/现象”。
```

不使用浏览器自动化代替这一步。服务启动失败或 URL 不可用即为未验证，先修复再交付回归。

## 4. Regression loop and closure

- 用户回复“不通过”后，先将现象映射到需求/计划；若信息足够，修复、运行针对性验证、停止旧服务并重新启动 `dev:test`，再提供新的 URL 和回归清单。若问题改变需求范围或存在多种合理行为，回到 Gate A。
- 用户明确回复“通过”后，按仓库 Git 与测试规则完成本地提交、收口验证和交付报告。推送、创建/更新 PR、合并或发布仍需用户的明确授权。
- 最终报告包含：需求来源（含“无工单”）、实际范围与非范围、验收清单结果、改动摘要、自动化验证证据、`dev:test` URL、人工回归结论、已知风险/未验证项以及是否产生本地提交。没有人工通过时，明确报告为“等待人工回归”，而非完成。

## Invocation example

```text
使用 feat 工作流：
在项目列表页增加“只看我创建的”筛选。入口在筛选区；默认关闭；开启后列表只显示当前用户创建的项目；加载、空态和接口失败需要有明确反馈。本次不改后端接口，也没有工单。
```
