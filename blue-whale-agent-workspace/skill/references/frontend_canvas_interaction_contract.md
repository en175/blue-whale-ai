# Frontend Canvas Interaction Contract

这份文件定义 Video Agent Canvas 在前端应该如何展示 Agent 编排结果。

目标：前端不是普通聊天窗口，而是「Agent 过程 + 画布素材 + 用户确认」的工作台。

## 核心展示边界

**画布 = 素材，对话 = 过程。**

- **Canvas 只展示素材节点**：图片 / 视频生成结果（中间结果或最终结果）。
- **AgentChatPanel 对话流展示所有过程**：思考过程、Brief、Skill 推荐、图片理解、阶段计划、脚本分镜、Review、文字回复，以及图片/视频结果卡（引用画布 asset）。
- **确认 / 修改 / 重试一律走对话自然语言**，画布与对话区都不设确认按钮。

## 页面基本结构

```text
左侧 / 中央：Canvas 画布（只放图 / 视频 素材）
右侧 / 底部：Agent 对话与思考过程（所有过程内容 + 确认）
顶部 / 节点旁：当前阶段状态（文字提示，无按钮）
```

## Agent 消息结构（对话区）

每一轮 Agent 回复在对话区展示：

1. 思考过程：展示 `visible_reasoning`（可折叠，1-3 条短句）
2. 正式回复：展示 `user_message_out`（以及 brief / skill / 分镜 / review 等过程消息）
3. 确认提示：用文字告诉用户「现在可以确认 / 修改 / 重做」，**不渲染按钮**

示例：

```text
[思考过程]
我看到画布里已有一张保温杯产品图。
这个需求更适合使用「电商产品图」Skill。
我会先生成 3 个商品图方向供你确认。

看到你的保温杯产品图了。我会先做 3 个商品图方向：户外露营、桌面质感、功能卖点展示。
确认这版方向？或告诉我要怎么改。
```

## 思考过程展示规则

### 默认展示

建议默认展示一个可折叠区域：

```text
思考过程 v
```

展开后显示 1-3 条短句。

### 不展示内容

前端不得展示：

- `trace_event`
- worker 名称
- prompt（含 `prompt_draft` / `optimized_prompt`）
- tool 参数
- JSON payload
- 本地文件路径
- 模型真实推理链

如果后端意外返回这些内容，前端也应做兜底过滤。

## Canvas 节点展示（仅素材）

画布上只有图片 / 视频素材节点。每个节点展示：

- 素材预览（图 / 视频缩略，视频可 hover 播放）
- 状态标记（queued 排队中 / generating 生成中 / ready 可确认 / failed 失败 / confirmed 已确认 / rejected 已拒绝）
- 所属阶段（可选，轻量标注）

**画布节点不挂任何按钮**。确认、局部修改、重新生成都在对话里用自然语言完成。

状态展示：

- `queued`：占位 + 「排队中」
- `generating`：占位 + 「生成中」（不允许确认）
- `ready`：成品 + 状态条提示「可确认」
- `failed`：占位 + 「生成失败，可在对话里要求重做」
- `confirmed` / `rejected`：轻量标记

## 对话消息展示（过程内容）

以下内容在 AgentChatPanel 对话流展示，**不进画布**：

### Brief 消息

展示为文字摘要：视频目标 / 主体 / 核心卖点 / 风格方向 / 素材情况。
末尾文字提示：「确认这个理解？或告诉我要改哪里。」

### Skill 推荐消息

文字展示：推荐 Skill 名称 + 推荐原因 + 可能风险。
末尾文字提示：「用这个方向？还是换其他风格？」

### 图片理解消息

文字展示：主体 / 外观特征 / 场景背景 / 可保留 / 可改变 / 不确定点。
无法识别时，展示用户补充表单，不假装已识别。

### 阶段计划消息

文字展示步骤清单（1. 脚本分镜 2. 首批视觉 3. 视频生成 4. 审核修改）。

### 脚本 / 分镜消息

展示为可读文字（脚本摘要 + 分镜表 + 关键帧），不要只显示原始 JSON。

### Review 消息

文字展示审核结论：「这版可用」/「需修改：…」。

### 结果卡（image_card / video_card）

引用画布上的 asset node，在对话里同步出现一张结果卡（图 / 视频预览 + 状态）。
**卡上不挂按钮**，确认 / 修改 / 重做在对话里用自然语言。

## 确认交互（对话式，无按钮）

确认、修改、重试、切换 Skill 全部通过**对话自然语言**完成。
前端**不渲染任何确认 / 修改 / 重试按钮**，也不发送结构化 action。

后端按 `rules/confirmation_gate.md` 的四分类处理用户自然语言：

- 明确确认（「确认 / 满意 / 就这个」）→ 推进下一步
- 弱继续（「继续 / 好了 / 下一步」）→ 不推进，二次确认
- 修改意图（「改一下 / 换风格」）→ 进入 revise
- 等待中（节点 generating）→ 拦住

前端唯一要做的是：把后端返回的 `visible_reasoning`、`user_message_out`、
当前阶段状态用文字展示出来，让用户知道「现在可以确认 / 修改 / 重做」。
用户用自己的话回复即可。

## 阶段状态提示

前端用文字明显展示当前阶段：

```text
当前阶段：脚本和分镜
状态：等待确认
```

或：

```text
当前阶段：首批关键视觉
状态：生成中
```

## 禁止体验

- 不要让用户只能通过聊天猜当前进度。
- 不要在画布上放过程内容（brief / skill / 分镜 / review / 思考）。
- 不要在画布节点或对话卡上挂确认 / 修改 / 重试按钮。
- 不要把所有结果堆在聊天里，最终素材必须以画布节点可见。
- 不要在生成中显示「已完成」。
- 不要用一个「继续」按钮代表所有确认动作。
- 不要在用户未确认脚本 / 分镜时展示完整视频生成。
- 不要把内部调试日志展示给普通用户。

## 验收标准

前端完成后至少验证：

1. Agent 每轮回复有可折叠的「思考过程」。
2. 画布只展示图 / 视频素材节点，带 status 标记。
3. brief / skill / 分镜 / review / 图片理解等过程内容在对话流展示，不在画布。
4. `ready` 状态在对话里用文字提示可确认；`generating` 状态提示不可确认。
5. 用户用自然语言确认 / 修改 / 重做，前端无确认按钮。
6. `trace_event`、prompt、worker 名不出现在普通用户界面。
