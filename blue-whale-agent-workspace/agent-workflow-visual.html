Agent router and workflow map

一条消息怎么落到正确的链路

判定分层后，一条消息怎么落到正确链路：后端算硬状态铁闸（零 LLM），L1 给意图软建议，主 Agent switch 收口。两条入口——BottomDock 直生（要快）vs Agent 对话编排（要好）。

三层判定

状态与意图的判定权下沉：硬事实归后端，软建议归 L1，主 Agent 只在 switch 里收口。

① 后端代码 · 算 context

读 canvas / stage / nodes / job 算 decision_context。零 LLM，硬事实。

② L1 classifier · 给建议

haiku 级轻量分类，产 decision_branch 软建议。主 Agent 可推翻。

③ 主 Agent · switch 收口

switch(decision_branch) 走 8 枚举之一。硬状态类不可推翻。

铁闸 · generation_in_progress

生成中，禁重入

后端检测到 active GenerationJob。主 Agent 不开新任务、不重复触发。

  • 读 job 状态
  • 等待或追问
  • 不可推翻
铁闸 · generation_failed

失败，先恢复

上次 job 失败。主 Agent 不盲目重试，先给恢复路径。

  • 读失败原因
  • 重试或改参数
  • 不静默跳过
铁闸 · confirm_pending

等确认，卡 advance_stage

有 ready 节点待确认。advance_stage 由后端铁闸守，主 Agent 不能口头推进。

  • has_ready_node 校验
  • 用户明确确认
  • 后端才 advance
L1 · product_switch

切换产品 / Skill

用户要换 Skill、换套路（UGC / 品牌 / 短剧）。

  • forced 优先
  • auto 候选其次
  • 低置信反问
L1 · new_task

新建生成任务

新需求。按目标判 BottomDock 直生 还是 Agent 对话链路。

  • 判直生 vs 对话
  • 建 workflow_run
  • 必要时补问
L1 · consult

咨询 / 讨论

只问方法、规则、建议。

  • 直接答
  • 不建 workflow_run
  • 不写 Canvas
L1 · revise_canvas

修改当前画布

改一下、重做、换风格、保留 A 重做 B。

  • 进 revise flow
  • 不覆盖原节点
  • 局部重跑
L1 · clarify

意图不明，先澄清

不猜测、不硬跑生成。

  • 问关键问题
  • 确认目标
  • 再进路由

两条入口怎么分流

判定分层后不再有 6 条平级 workflow——按「要快 / 要好」分两条入口：BottomDock 直生（用户自负责 prompt，零 Agent）承担所有直接生成；Agent 对话（L1 → 主 Agent switch）做编排，永远走 Prompt Optimizer。老的 Confirm / Revise / Prompt-only 降为 branch 出口，不是独立 workflow。

BottomDock 直生

直接生成（要快）

用户手填参数 + prompt，直传 Provider。承担 Direct Image / Direct Video / Image-to-Video。

1
Dock 选 type + 填参数image / video / image-to-video，附 prompt + reference_asset。
2
零 Agent 编排不判链路、不跑 understanding、不跑 Prompt Optimizer。
3
直传 ProviderProvider 自消费图，纯参数透传。
4

5

边界（零 Agent）

  • 零优化、零 understanding（要快，用户自负责 prompt）
  • 不经 L1 / 主 Agent，无路由判定
  • Image-to-Video：图 + prompt 直传，Provider 自消费
Agent 对话

对话编排（要好）

L1 给 suggested_route，主 Agent switch 收口。永远走 Prompt Optimizer，有图时先 understanding。

1
后端算 decision_context硬状态铁闸先判（has_generating 短路），零 LLM。
2
L1 classifier（haiku 级）给 intent_direction + suggested_route 软建议。
3
主 Agent switch(decision_branch)8 枚举收口，可推翻 L1、推翻不了铁闸。
4
new_task + lightweight轻量编排：Brief 补全 → understanding（有图）→ Optimizer → Job。
5
new_task + full_canvasFull Canvas：Brief → Skill → 分镜 → 视觉 → 视频，4 硬停。

branch 出口（非生成）

  • confirm_pending：确认门四分类，advance_stage 铁闸
  • revise_canvas：局部修改，保留原节点不覆盖
  • consult / clarify：直接答 / 澄清，不启 Job
  • Prompt-only：只走 Optimizer，不调 Provider
  • generation_in_progress / failed：硬状态铁闸

生成链路怎么跑：Dock 直生 vs Agent 编排

两条入口：BottomDock 直生（要快——用户自负责 prompt，零 Agent、零优化、零 understanding，直传 Provider）vs Agent 对话（要好——L1 给 suggested_route，主 Agent 路由到轻量编排或 Full Canvas，永远走 Prompt Optimizer）。分叉是判断，主线下行是推进。

Full Video Canvas 阶段链

完整视频项目必须经过这些确认点，每个硬停由 advance_stage 后端铁闸独立校验 has_ready_node——主 Agent 误判也拦。每个过程产物在 ChatMessage 中展示，只有图片/视频素材进入 Canvas。

Brief 收集

只收集启动创作必须的信息，不一次性抛长问卷。目标是把模糊需求变成可确认的最小 Brief。

1
输入视频目标、主体、平台/时长、素材、卖点或情绪方向。
2
WorkerBrief Agent。
3
输出brief ChatMessage + missing_fields + assumptions。

Skill 匹配

Skill Selector 从用户指定、auto 候选池或 Brief 推断中选择主 Skill。低置信度时反问，不默认兜底成固定 Skill。

1
forced_skill_id用户点 Use，本 turn 最高优先级。
2
auto 候选池后端自读我的 Skills 中 auto=true 的 Skill。
3
输出skill_recommendation ChatMessage，等待用户确认。

阶段计划与脚本分镜

先完成内容结构，不直接烧生成资源。用户只改局部时，只重写对应镜头。

1
Director生成阶段计划：脚本分镜、首批视觉、视频生成、审核修改。
2
Storyboard Agent脚本、分镜表、关键帧清单、每镜头提示方向。
3
确认门（confirm_pending）明确确认 + has_ready_node → advance_stage 铁闸；弱继续二次确认。

首批视觉

先生成最关键的视觉锚点，而不是直接生成整条视频。如果依赖上传图，必须先完成图片理解。

1
Image Understanding如有图，先得到 asset_understanding。
2
Image Prompt + Optimizer生成可执行的首批视觉提示词。
3
Canvas写入 image 节点，ready 后进确认门（advance_stage 铁闸校验 has_ready_node）。

视频生成与审核

基于已确认脚本、分镜和视觉锚点生成视频，再由 Review Agent 做质量检查和修改建议。

1
Generation Agent组织视频任务，Seedance 语法只做模型适配。
2
GenerationJob创建 video job，完成后绑定 video asset。
3
Review Agent检查是否符合 Brief、Skill、镜头结构和质量要求。

Skill 如何被调用

Skill 不是提示词模板。它决定内容结构、表达方式和广告策略；Prompt Optimizer 只把已确认内容翻译成模型语法。

Skill Selector 的输入来源

Agent 在 Skill 匹配阶段按优先级选择：用户手动 Use 最高，auto 候选池其次，最后才由 Brief 推断。无法确定时必须反问。

forced_skill_id用户点 Use，本 turn 必须使用，不改变 auto 状态。
auto 候选池后端从我的 Skills 中读取 auto=true，作为可选范围。
Brief 推断没有指定时，根据目标、品类、平台、卖点匹配。
用户确认推荐 Skill 后必须允许用户改选或调整方向。

每一步产物落到哪里

这部分是前后端最容易混乱的地方：过程内容不进画布，任务不是节点，素材节点只表示图片或视频事实。

ChatMessage

过程内容

  • visible_reasoning（含 decision_branch + 可推翻理由）
  • brief / skill_recommendation
  • asset_understanding
  • stage_plan / storyboard / review
  • optimized_prompt_preview
Canvas Node

素材节点

  • type 只能是 image / video
  • status: queued / generating / ready / failed
  • 绑定 stage_id 和 asset_ref
  • ready 后才能确认
GenerationJob

生成任务

  • 承载 prompt / model / params
  • queued → processing → succeeded / failed
  • 输出 Asset
  • 任务不作为 canvas node
Workflow Run

阶段状态

  • current_stage_id
  • selected_skill
  • brief / stage_plan
  • awaiting_confirm / completed / failed
decision_context

每轮判定上下文

  • 硬事实：has_generating / has_ready_node / has_failed / awaiting_confirm
  • L1 软建议：intent_direction + suggested_route
  • 组合结果：decision_branch（8 枚举之一）
  • 后端每轮算好整体喂主 Agent

压缩后的硬规则

这些是实现时不能破的护栏。它们决定系统是否稳定、是否可控、是否不会泄露内部信息。

Canvas

画布只放素材

Brief、Skill、分镜、Review、思考过程都进对话消息，Canvas 只展示图片/视频节点。

Gate

advance_stage 后端铁闸

明确确认 + has_ready_node 才推进；铁闸独立校验，主 Agent 误判也拦。弱继续只二次确认。

Weak continue
